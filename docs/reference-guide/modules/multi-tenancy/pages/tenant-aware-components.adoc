= Tenant-Aware Components
:navtitle: Tenant-aware components
:reftext: Tenant-aware components

Besides routing messages and storing events per tenant, an application usually has its own tenant-scoped resources: a read-model repository, a SQL datasource, or any service that must not mix data between tenants.
Tenant-aware components let you register such a resource once and have the correct tenant's instance injected into your message handling methods, so a handler never has to look up the tenant itself.

A tenant-aware component is described by two types:

* `TenantComponentFactory<T>` builds (and cleans up) the instance of your component for a single tenant.
* `TenantComponentProvider<T>` holds one instance of the component type `T` per tenant, creating each instance lazily through the factory on first use.

Each provider is generic over a single component type. To expose several tenant-scoped types, register one provider per type. Each provider is matched to handler parameters by its component type.

== Registering a tenant-scoped component

Implement a `TenantComponentFactory` describing how the component is built for a tenant, and register the provider obtained through `TenantComponentProvider.withFactory`.

[tabs]
====
Declarative - Configuration API::
+
--
Register the provider as a component on your `MessagingConfigurer`, passed in from the place it is created:

[source,java]
----
public void registerTenantComponents(MessagingConfigurer configurer) {
    configurer.componentRegistry(registry ->
        registry.registerComponent(
                TenantComponentProvider.class,                                     // <1>
                config -> TenantComponentProvider.withFactory(
                        CourseStatsRepository.class,                               // <2>
                        tenant -> new InMemoryCourseStatsRepository(tenant.tenantId())
                )
        )
    );
}
----
<1> Register the provider under the `TenantComponentProvider` type so it is discovered during parameter resolution.
<2> The component type, used to match the provider against handler parameters. The lambda is the `TenantComponentFactory` building the tenant's instance.
--
Autodetected - Spring Boot::
+
--
Expose the provider as a bean of type `TenantComponentProvider`.
Axon's Spring Boot integration registers it as a component, where the same parameter resolution detects it:

[source,java]
----
@Bean
public TenantComponentProvider<CourseStatsRepository> courseStatsRepository() {
    return TenantComponentProvider.withFactory(
            CourseStatsRepository.class,
            tenant -> new InMemoryCourseStatsRepository(tenant.tenantId())
    );
}
----
--
====

Both approaches do the same thing: they provide one `TenantComponentProvider` component, and message handlers can then declare the component type as a parameter.

== Injecting the tenant's instance into a handler

Declare a parameter of the component type on a message handling method.
During handling, the parameter is resolved to the instance belonging to the tenant of the message being handled.

[source,java]
----
@EventHandler
public void on(CourseCreated event, CourseStatsRepository repository) { // <1>
    repository.save(new CourseStatistics(event.courseId()));
}
----
<1> `repository` is the `CourseStatsRepository` instance of the current tenant.

The tenant is taken from the message metadata under the `tenantId` key.
That key is populated automatically for messages flowing through a multi-tenant application (see xref:multi-tenancy:index.adoc#_tenant_management[Tenant management]), so handlers do not have to set it themselves.
When a custom `TenantResolver` is registered in the `TenantResolverRegistry`, injection honors it instead, including resolvers registered for a specific message type such as commands.
When a handled message carries no tenant, or a tenant that is not known to the application, resolving the parameter fails with a `TenantNotResolvedException`.
This guarantees that no tenant-scoped resource is ever created for an unknown tenant.

== Registering multiple component types

An application can register several tenant-aware components, one provider per type.
Every provider is matched to a handler parameter by its own component type, and a single exact type match settles the choice even when assignable supertype candidates exist.
When the choice cannot be settled by an exact match, because two providers serve the same exact type or, absent an exact match, several assignable candidates remain, handler registration fails with an `AxonConfigurationException`.
Register a single provider per component type, or narrow the parameter type, to resolve such an ambiguity.

[tabs]
====
Declarative - Configuration API::
+
--
Register each provider under its own name:

[source,java]
----
configurer.componentRegistry(registry -> registry
    .registerComponent(TenantComponentProvider.class, "courseStatsRepository", // <1>
            config -> TenantComponentProvider.withFactory(
                    CourseStatsRepository.class,
                    tenant -> new InMemoryCourseStatsRepository(tenant.tenantId())))
    .registerComponent(TenantComponentProvider.class, "reportingDataSource",   // <2>
            config -> TenantComponentProvider.withFactory(
                    DataSource.class,
                    tenant -> buildDataSource(tenant)))
);
----
<1> A provider for the `CourseStatsRepository` read model.
<2> A second provider, for a per-tenant reporting `DataSource`, registered under a different name.
--
Autodetected - Spring Boot::
+
--
Declare one bean per component type.
The bean name serves as the component name:

[source,java]
----
@Bean
public TenantComponentProvider<CourseStatsRepository> courseStatsRepository() {
    return TenantComponentProvider.withFactory(
            CourseStatsRepository.class,
            tenant -> new InMemoryCourseStatsRepository(tenant.tenantId()));
}

@Bean
public TenantComponentProvider<DataSource> reportingDataSource() {
    return TenantComponentProvider.withFactory(
            DataSource.class,
            tenant -> buildDataSource(tenant));
}
----
--
====

== Lifecycle and cleanup

Providers follow the tenant lifecycle of the application automatically.
Every registered provider is subscribed to the `TenantProvider`, so tenants known at startup and tenants discovered at runtime become available to the provider without further configuration.
Instances are created lazily: a provider only builds a tenant's component the first time a handler for that tenant requests it, and caches it for subsequent messages.
When a tenant is removed, its cached instance is discarded and destroyed through `TenantComponentFactory#destroy`.

The default `destroy` closes components that implement `AutoCloseable`, which covers pooled datasource implementations and other connection-backed resources.
Override it to release other resources or to add custom shutdown logic.

[source,java]
----
TenantComponentFactory<CourseStatsRepository> factory = new TenantComponentFactory<>() {

    @Override
    public CourseStatsRepository create(TenantDescriptor tenant) {
        return new JdbcCourseStatsRepository(dataSourceFor(tenant));
    }

    @Override
    public void destroy(TenantDescriptor tenant, CourseStatsRepository repository) {
        repository.flush();
        repository.close();
    }
};
----
