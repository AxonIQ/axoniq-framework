= MongoDB Dead-Letter Queue
:navtitle: Dead-Letter Queue

The `MongoSequencedDeadLetterQueue` is an implementation of the `SequencedDeadLetterQueue` that persists dead letters in MongoDB.
Read the xref:dead-letter-queue:index.adoc[dead-letter queue guide] first for what a dead-letter queue does and how event processors use it.
This page covers what is specific to MongoDB.

Note that the `MongoSequencedDeadLetterQueue` is part of Axoniq Framework and requires a xref:axoniq-platform-reference:ROOT:licensing/index.adoc[license] for production use.

The queue is in the optional `axoniq-dead-letter` module, which you need to add next to `axoniq-mongo`.

== Stored documents

Each dead letter is a document in the collection the queue is constructed with, which is `deadletters` when the xref:mongo:mongo-template.adoc[`MongoTemplate`] provides it.
The document holds the event, with its payload and metadata, the sequence identifier, the index of the letter within its sequence, the cause of the failure, the diagnostics, and the timestamps of when it was enqueued and last touched.
All letters are scoped by the processing group of the queue, so queues of different event handling components do not see each other's letters.
The xref:dead-letter-queue:index.adoc#_queue_scoping_and_naming[queue scoping and naming] section describes how the processing group is derived.

The queue converts events and diagnostics with the `EventConverter` and the generic `Converter` that you give it.
It does not support upcasters, so avoid breaking changes to events that are in the queue.

== Claims

Processing a dead letter requires a claim, so that only one node works on a sequence at a time.
The claim is a single atomic update that only matches a letter that has not been claimed, or whose claim has expired.
A claim lasts 30 seconds by default.
Once it has expired, another node may process the sequence.

The MongoDB driver is blocking, so the operations of the queue block the calling thread while they interact with MongoDB.

[#transactions]
== Transactions

Every operation of the queue runs with the MongoDB `ClientSession` that is bound to the `ProcessingContext` it is invoked with, exactly as the `JpaSequencedDeadLetterQueue` and `JdbcSequencedDeadLetterQueue` do with their `EntityManager` and `Connection`.
The `DeadLetteringEventHandlingComponent` passes the `ProcessingContext` of the event handling to the queue.
When the `ClientSessionTransactionManager`, or in Spring the `SpringMongoTransactionManager`, binds the session, a dead letter is therefore enqueued, requeued or evicted in the same MongoDB transaction as the token update and the writes of your event handlers.
See xref:mongo:token-store.adoc#_transactions[Transactions] of the token store for how that transaction is set up.

Keep in mind that:

* The queue is as strict as the JPA and JDBC queues: an operation fails when no session is bound to its `ProcessingContext`.
* Only one `TransactionManager` serves an application.
When MongoDB is combined with JPA or JDBC, for instance JPA projections with a MongoDB queue, you are in charge of registering the `TransactionalExecutorProvider` and `TransactionManager` that fit your setup.
The Mongo transaction managers only bind a MongoDB session, and the JPA and JDBC transaction managers do not.
* MongoDB only supports multi-document transactions on a replica set or sharded cluster.
* The session and the dead letter collection must come from the same `MongoClient`, as a session only works with the client that started it.
* Without a `ProcessingContext`, the queue uses a session that the provider starts for the operation alone, without a transaction.
* Creating the indexes on construction uses a session of its own as well, and is never part of a transaction.

== Configuration

When `axoniq-dead-letter` is on the classpath, and a `MongoTemplate` and a `MongoTransactionalExecutorProvider` are registered, the module registers a `MongoSequencedDeadLetterQueueFactory` as a component.
Register the `MongoTransactionalExecutorProvider`, and the `ClientSessionTransactionManager` as the `TransactionManager`, as shown for the xref:mongo:token-store.adoc#_configuration[token store].
Enabling the dead-letter queue for a processor does not select it automatically in plain Java.

In Spring Boot, the `MongoSequencedDeadLetterQueueFactory` bean is auto-configured when a `MongoDatabaseFactory` bean exists.
It is a bean, instead of a component that the module registers, as the dead-letter queue support of Axoniq Framework only acts when a `SequencedDeadLetterQueueFactory` bean exists.
Enabling the dead-letter queue for a processor only requires a property:

[source,properties]
----
axon.eventhandling.processors.my-processor.dlq.enabled=true
----

Next to the factory, the auto-configuration registers the transaction components, as Axon Framework 4 did: Spring's `MongoTransactionManager` wrapped in a `SpringMongoTransactionManager` as the `TransactionManager`, and the `MongoTransactionalExecutorProvider`, unless beans of those types exist.
It does not replace the `TransactionManager` of a JPA or JDBC setup, so keep the xref:mongo:mongo-template.adoc#_mixing_mongodb_with_relational_components[mixing of components] in mind, see also <<Transactions>>.
The JPA factory takes precedence over the JDBC factory, which takes precedence over the MongoDB factory, in the same order as for the token store.
The following properties are available:

[cols="<,<,<"]
|===
|Property |Default |Description

|`axon.mongo.dead-letter-queue.max-sequences`
|`1024`
|The maximum number of unique sequences a queue may contain.

|`axon.mongo.dead-letter-queue.max-sequence-size`
|`1024`
|The maximum number of letters in a sequence.

|`axon.mongo.dead-letter-queue.query-page-size`
|`100`
|The number of letters fetched per query while iterating the queue.

|`axon.mongo.dead-letter-queue.claim-duration`
|`30s`
|How long a claim on a letter holds before another node may take it.

|`axon.mongo.dead-letter-queue.ensure-indexes`
|`true`
|Whether a queue creates the indexes of the dead letter collection when it is constructed.

|`axon.mongo.dead-letter-queue.allow-disk-use`
|`true`
|Whether the aggregations that select the first letter of every sequence may spill to disk.
Dead-lettering itself is still enabled per processor.

|`axon.eventhandling.processors.<processorName>.dlq.enabled`
|`false`
|Whether the dead-letter queue is enabled for the processor.
|===

Declare your own `SequencedDeadLetterQueueFactory` bean to replace the auto-configured one.

=== Changing the settings

The settings of the queues are held by a `MongoSequencedDeadLetterQueueConfiguration`.
The module registers its default as a component, which the `MongoSequencedDeadLetterQueueFactory` creates the queues with.
To change a setting, register your own `MongoSequencedDeadLetterQueueConfiguration` component instead, starting from `MongoSequencedDeadLetterQueueConfiguration.DEFAULT`.
The following settings are available:

[cols="<,<,<"]
|===
|Setting |Default |Description

|`converter`
|`EventMessageDeadLetterMongoConverter`
|The converter between a dead letter and its stored document.

|`maxSequences`
|`1024`
|The maximum number of sequences in the queue.

|`maxSequenceSize`
|`1024`
|The maximum number of letters in a sequence.

|`queryPageSize`
|`100`
|The number of letters fetched per query while iterating the queue.

|`claimDuration`
|30 seconds
|How long a claim on a letter holds before another node may take it.

|`ensureIndexes`
|`true`
|Whether the queue creates the indexes of the dead letter collection when it is constructed.

|`allowDiskUse`
|`true`
|Whether the aggregations that select the first letter of every sequence may spill to disk. MongoDB limits the memory of the sort in these aggregations to 100 megabytes. When you set this to `false`, a large dead letter collection can make the aggregation fail instead of getting slower.
|===

Read xref:dead-letter-queue:index.adoc#_capacity_and_overflow[Capacity and overflow] before you change `maxSequences` or `maxSequenceSize`, as exceeding either limit stalls a segment of the processor.

The `MongoSequencedDeadLetterQueue` itself takes the `processingGroup`, the dead letter `MongoCollection<Document>`, the `TransactionalExecutorProvider<ClientSession>` (see <<Transactions>>), the `EventConverter` and generic `Converter`, and the `MongoSequencedDeadLetterQueueConfiguration` as constructor arguments.
Register your own `SequencedDeadLetterQueueFactory` when you want to construct the queues yourself.

=== Managing the indexes

The queue creates its indexes on construction, which is a no-op when they exist.
If your deployment does not allow the application to create indexes, create them in advance on the dead letter collection, and disable `ensureIndexes`.
The queue uses these indexes, on the fields `processingGroup`, `sequenceIdentifier` and `index`:

* `processingGroupIdentifierIndex`: `processingGroup`, not unique,
* `processingGroupAndSequenceIdentifierIndex`: `processingGroup` and `sequenceIdentifier`, not unique,
* `uniqueDeadLetterEntryIndex`: `processingGroup`, `sequenceIdentifier` and `index`, unique.
