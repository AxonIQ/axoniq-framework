= Understanding Steps
:navtitle: Understanding Steps

In the previous sections you saw `awaitExecute` and `awaitEvent` in action.
This section covers the full configuration available across all step types: timeouts, payload mapping, event naming, and execution semantics.

[NOTE]
====
Everything in this section applies to all step primitives, unless noted otherwise.
====

[IMPORTANT]
====
Primitives cannot be nested.
Do not call `execute`, `awaitExecute`, `awaitEvent`, `sleep`, `fail`, or `cancel` from *inside* an action passed to another primitive.
Each primitive must be called directly from the workflow method—the engine tracks execution through the top-level call sequence, and nesting would break event ordering and replay.

[source,java]
----
// WRONG — do not nest primitives
ctx.awaitExecute("outer", Map.of(), (pc, payload) -> {
    ctx.awaitExecute("inner", ...);  // this will not work correctly
    return Map.of();
});

// CORRECT — call primitives sequentially from the workflow method
ctx.awaitExecute("stepA", Map.of(), ServiceA::doWork);
ctx.awaitExecute("stepB", Map.of(), ServiceB::doWork);
----
====

[[workflow-step-result]]
== `WorkflowStepResult`

The `WorkflowStepResult` returned by `execute` and `waitForEvent` lets you inspect, wait for, or cancel a running step.

.Blocking methods wait until the step reaches a terminal state
[cols="2,3"]
|===
|Method |Description

|`await()`
|Blocks until the step finishes. Use when you don't need the outcome, just the guarantee it's done.

|`success()`
|Blocks, then returns `true` if the step completed successfully.

|`failure()`
|Blocks, then returns `true` if the step threw an exception.

|`timeout()`
|Blocks, then returns `true` if the step exceeded its timeout.

|`canceled()`
|Blocks, then returns `true` if the step was cancelled.
|===

.Non-blocking methods return immediately
[cols="2,3"]
|===
|Method |Description

|`getStepName()`
|Returns the step name.

|`isCompleted()`
|Returns `true` if the step has already reached a terminal state.

|`result()`
|Returns `Optional<Map<String, Object>>` with the result payload. Use `resultAs(Class)` for a typed result. Empty if the step hasn't finished yet.

|`error()`
|Returns `Optional<StepFailedException>` describing the failure. Check `failure()` first.

|`cancel()` / `cancel(reason)`
|Cancels the step if still running. No-op if already in a terminal state. See <<cancelling-a-step>>.
|===

[[timeouts]]
== Timeouts

Every step has a timeout.
If the action doesn't complete in time, the engine records a TIMED_OUT event and the step is considered failed.
This applies to `awaitExecute`, `execute`, and `awaitEvent` alike.

[horizontal]
Default:: **5 seconds**, used when you don't pass an explicit `Duration`.
Override per step:: Customize the step definition with `timeout(...)`.

[IMPORTANT]
====
The timeout is measured from the timestamp of the STARTED event.
That is the step's start time.
On replay after a crash, the remaining timeout is recalculated: `startTime + timeout - now`.
If the remaining time is already negative, the step times out immediately.
====

[[payload-reducers]]
== Payload reducers

Every workflow has a *global payload*.
This is the shared state that lives for the entire workflow.
When you call a step, you can also pass a *local payload*.
This data is specific to that step.

The question is: what does the step's action actually receive as input, and what happens to the step's result?
That's what payload reducers control.

=== The two reducers

Each step has two reducers:

[horizontal]
`parameterPayloadReducer`:: Controls the *input*, so what payload the step's action receives.
`resultPayloadReducer`:: Controls the *output*, so what happens to the step's result after it completes.

=== Available options

[cols="1,2,2"]
|===
|Reducer |As input (`parameterPayloadReducer`) |As output (`resultPayloadReducer`)

|`LocalOnlyPayloadReducer.INSTANCE` _(default for input)_
|The action receives only the local payload you passed in. It doesn't see the global workflow state.
|The step's result replaces the global payload. Previous global values are dropped.

|`GlobalOnlyPayloadReducer.INSTANCE` _(default for output)_
|The action receives only the global workflow payload. The local payload is ignored.
|The step's result is discarded. The global payload stays as-is.

|`CombineGlobalAndLocalPayloadReducer.INSTANCE`
|The action receives both merged. Local values overwrite global values with the same key.
|The step's result is merged back into the global payload.
|===

=== Why does this matter?

With the defaults (`LocalOnlyPayloadReducer.INSTANCE` for input and `GlobalOnlyPayloadReducer.INSTANCE` for output), steps are isolated.
They only see what you explicitly pass them, and their results don't leak into the global state.
This keeps things predictable.

Sometimes you want a step to see the full workflow context, or you want the result to update the global payload for subsequent steps.
That's when you change the reducer.

[[execution-semantics]]
== Execution semantics

Steps execute with **at most once** semantics.
Each attempt of a step's action runs **at most once**, including across crashes and replays.
An attempt is never re-run after a crash.
Only a configured `RetryPolicy` starts a new attempt.

The action runs *before* its COMPLETED event is persisted.
If the application crashes in that window (action ran, COMPLETED not yet committed), the engine **does not** re-run the action on recovery: the durable STARTED record means an attempt was already opened and may have run, and re-running it would break the at-most-once guarantee.
Because the outcome of the interrupted attempt is unknown, the engine resolves it through the **regular error flow** instead of re-executing it (see below).

The trade-off of at-most-once is that an interrupted action may run **zero or one** times.
Hence, it may not run at all.
If a step's effect *must* eventually happen, make it **idempotent** and configure a `RetryPolicy` (a retry is a fresh attempt) and/or compensate when the step fails.

Events can reach the workflow more than once, for example after a restart or a rebalance.
A step that already reached a terminal status ignores a later matching event.
For external side effects, use the workflow id and the step name as the idempotency key.
Both are stable across restarts.

[[crash-interrupted-steps]]
=== Crash-interrupted steps: which error, and how to retry

When a step's action is interrupted by a crash and not re-run, the engine resolves it exactly like any other failed attempt:

* **No retry policy**: the step records a terminal **FAILED** status.
The failure is surfaced to your workflow body as a `StepIndeterminateException`, a subtype of `StepFailedException` (the dedicated "in-flight at a crash, not re-run, outcome indeterminate" marker). `awaitExecute(...)` throws it; a non-blocking `execute(...)` handle reports it via `result.failure()` / `result.error()`.
* **With a retry policy**: the interrupted attempt is treated as a failed attempt and the step goes to **RETRYING**; the engine schedules the next attempt per the policy (backoff included).
This is identical to the normal retry-on-failure flow, so a step you *want* re-attempted after a crash should carry a `RetryPolicy` (and an idempotent action, since a retry runs the effect again).
Each retry attempt records **RETRY_STARTED** before it runs, and runs only if the event store accepted that record.
A node that lost the workflow instance during the backoff is rejected there and never runs the action.

<.> If the step fails or times out, the engine retries up to 3 times before marking it as FAILED (or TIMED_OUT if the last attempt timed out).
Each attempt gets its own full timeout. `maxRetries=3` means up to 4 total executions (1 initial + 3 retries).
<.> `onRetry` is called before each retry.

=== Backoff strategies

[cols="1,2"]
|===
|Strategy |Behavior

|`BackoffStrategy.NONE`
|No delay between retries (default).

|`BackoffStrategy.fixed(Duration)`
|Constant delay between retries.

|`BackoffStrategy.linear(Duration base)`
|Delay increases linearly: `base * attempt`.

|`BackoffStrategy.exponential(Duration base, Duration max)`
|Delay doubles each attempt: `base * 2^(attempt-1)`, capped at `max`.
|===

=== Cancellation during retry

[NOTE]
====
If a step throws `StepCancellationException` during any retry attempt, the step immediately transitions to `CANCELLED`.
Any remaining retries are skipped.
Cancellation always takes precedence over the retry policy.
This also applies when the workflow cancels a step through `ctx.cancelStep()` or when the workflow itself is cancelled: any in-flight backoff delay is interrupted and the step moves to a terminal state.
====

=== Crash recovery

Retries are maintained too.
On crash recovery, the engine replays retry events and recalculates backoff from persisted timestamps.
If the process restarts while a step is in `RETRYING` state, the engine resumes from the correct attempt number with the remaining backoff delay.
If it restarts while a step is in `RETRY_STARTED` state, that attempt was running at the crash.
It is treated as a failed attempt with the recorded attempt number, so the step goes to `RETRYING` and the retry count is not reset.

=== Defaults and Inheritance

Axon Workflows defines sensible defaults for naming workflow events.
The workflow-level customizer propagates selected properties to steps via `forStepInheritance()`.
When a step also has its own customizer, the two are merged.
The **step-level wins** when it differs from defaults, otherwise the workflow-level value is used.
The table below explains the naming settings defaults and inheritance in detail.

|===
|Property |Description |Default |Inherited?

|`namespace`
|The prefix for all event names (for example, `io.myapp.orders`)

|Yes, set it once, all steps use it

|`true`
|Yes

|Step status suffixes
|The suffix appended for each status (`stepStarted`, `stepCompleted`, `stepFailed`, `stepTimedOut`, `stepCancelled`, `stepRetrying`, `stepRetryStarted`)
|`Started`, `Completed`, `Failed`, `TimedOut`, `Cancelled`, `Retrying`, `RetryStarted`
|Yes

|`baseName`
|Replaces the step name in the event name
|The step name itself
|No—each step uses its own step name

|`workflowBaseName`

[[kotlin-dsl-equivalents]]
== Kotlin DSL equivalents

The Kotlin DSL exposes the same options as concise overloads, while still allowing direct definition objects when needed:

[source,kotlin]
----
val result = execute(
    stepName = "shipOrder",
    inputPayload = mapOf("address" to address),
    timeout = 5.minutes,
    retryPolicy = RetryPolicy.NONE
) { pc, p ->
    ShippingService.shipOrder(pc, p)
}

val reservation = awaitExecute(
    stepName = "reserveStock",
    timeout = 10.seconds
) { _, _ ->
    mapOf("reserved" to InventoryService.reserveStock())
}
----

For advanced cases, you can still pass `ExecuteStepDefinition`, `WaitForStepDefinition`, and `PayloadStepDefinition` directly to `Kontext`.
The convenience overloads simply build those same definitions with Kotlin defaults applied up front.
When you want to pass step-local data as a named argument in Kotlin, use `inputPayload = ...` to match the Java DSL terminology.
