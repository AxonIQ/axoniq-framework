= Configuration
:navtitle: Configuration

Throughout this tutorial, workflows have been defined using the `@Workflow` annotation.
This section covers the declarative (programmatic) configuration API, which gives you full control over how workflows are wired up—and how to customize the context, event naming, ID resolution, and more.

A start condition must give the same answer for the same event, every time.
The engine evaluates it twice per event: once to pick the segment the event goes to, and once when that segment handles the event.

[[running-on-several-nodes]]
== Running on several nodes

Each `WorkflowModule` runs its engine on its own pooled streaming event processor, named after the module.
The history projector runs on a second processor named `WorkflowHistoryProjector[<module name>]`.
Each workflow instance belongs to one segment of the engine processor, chosen by the hash of its workflow id.
Subscribing processors, including Axon Server persistent streams, cannot back workflows.

=== Token store

The processor claims its segments in the unnamed `TokenStore` component of your application.
Register a durable store, for example `JpaTokenStore`, as an unnamed component.
Without one, the engine falls back to an in-memory token store and logs a warning.
Claims then stay inside the process, so run a single node only.
A <<workflow-index,workflow index>> belongs in the database of this token store.

=== Processor settings

After the workflow definitions, the module builder accepts `processorConfiguration(...)` for the engine processor and `historyProcessorConfiguration(...)` for the history processor.
Both take a function that receives and returns a `PooledStreamingEventProcessorConfiguration`.
Only the initial segment count is applied to a new token store. To change it later, split or merge the stored tokens.

=== Failover

When a node stops, another node claims its segments and resumes the unfinished workflow instances.
Every event an instance appends carries an append condition on its workflow id.
A node that lost its claim without noticing has its append rejected, logs a warning, and stops that instance.

On every segment claim, the node learns which workflow instances of the segment are running and which waits are open.
Without a workflow index, it sources both from the event store, for all segments.
With a <<workflow-index,workflow index>>, it reads only the rows of the claimed segment.

[[snapshots]]
=== Snapshots

The engine sources three event-sourced entities: the state of each workflow instance, the list of running workflows, and the list of open waits.
With snapshots, a node sources an entity from its latest snapshot and the events after it.
Without snapshots, a node replays the full event history of an entity each time it loads it.
Without a <<workflow-index,workflow index>>, a node loads both lists on every segment claim, so a node that claims many segments loads them once per segment.

Snapshots are on by default when the application can take snapshots.
The application can take snapshots when it has a `SnapshotStore` component and a `GeneralConverter` component, and its `MessageTypeResolver` resolves the entity.
Axon Server and PostgreSQL each register a `SnapshotStore`.
An application that cannot take snapshots starts without them.

The `enabled` setting of the snapshot configuration has three states:

[cols="1,3"]
|===
|`enabled` |Behavior

|Not set
|The engine snapshots an entity when the application can take snapshots. This is the default.

|`true`
|The engine snapshots all three entities. An application that cannot take snapshots fails to start.

|`false`
|The engine takes no snapshots.
|===

[[hibernation]]
== Hibernation

A workflow that waits for days or months holds memory the whole time it waits.
With hibernation enabled, the engine removes such a workflow from memory while it waits, and restores it from the event store when it is needed again.

[source,java]
----
include::example$workflows/configuration/ConfigurationExamples.java[tag=hibernation,indent=0]
----

Hibernation is a setting of the workflow module, and it's disabled by default.
It applies to every workflow of the module.
Workflows that need different settings go into separate workflow modules.

A workflow hibernates only while it waits for events or deadlines, never while an `execute` step runs.
It wakes up when an event it waits for arrives, when the nearest timeout of its waits expires, or when a cancellation is requested for it.
Hibernating writes no events.

Every 30 seconds, the engine asks the workflows in memory to hibernate.
Set `hibernationInterval` on the module, in milliseconds, to change that.
A wake that failed, for example because the event store was unreachable, is tried again after the same interval.

Hibernation trades memory for load time, because every wake replays the history of the workflow.
Enable it for workflows that wait for days or months.
Keep it disabled for many short-lived workflows, or for workflows with short timeouts, because they would load again and again.

A restart or a segment claim keeps hibernated workflows out of memory, instead of replaying them, in two setups:

* With a <<workflow-index,workflow index>> in the database of the token store. This also holds after a crash.
* Without a workflow index and with a `SnapshotStore` configured. This holds only after a clean release of the segment, for example when the application stops.

In every other setup, a segment claim replays every unfinished workflow of the segment, which then hibernates again.

Hibernation relies on the workflow body being deterministic, like every replay does.
The engine stops a hibernating body the way it stops the workflows of a released segment, so a body that catches exceptions around a step result must rethrow the `StepInterruptedException`.

See xref:workflow-internals.adoc#hibernation[Hibernation internals] for how the engine decides when a workflow hibernates, and how it records and wakes hibernated workflows.

[[workflow-index]]
== Workflow index

When a node claims a segment, the engine must learn three things: which workflow instances of that segment are running, which waits are open, and which workflows are hibernated.
Without a workflow index, a segment claim sources the list of running workflows and the list of open waits from the event store.
Both lists hold all segments, so the cost of a segment claim grows with the whole application, not with the claimed segment.

The workflow index is an optional store of rows: one row per running workflow and one row per open wait.
A segment claim reads only the rows of its own segment, and then the few wait and lifecycle events published after its stored token.
The engine writes the rows that changed each time the processor stores its token.
The events stay the source of truth.

In a Spring Boot application with JPA, the workflow index is on by default, see <<spring-boot,Spring Boot>>.
Without Spring Boot, register it on the `WorkflowConfigurer`, as shown below.
It pays off most with many running workflows, with many segments, and with <<hibernation,hibernated workflows>> that must stay out of memory after a crash.

=== Tables

`JpaWorkflowIndex` keeps its rows in the tables of three entities from the package `io.axoniq.framework.workflow.index.jpa`.
Add the three entities to the persistence unit that the `JpaWorkflowIndex` uses.

[cols="2,1,3"]
|===
|Entity |One row per |Content

|`WorkflowIndexEntry`
|Running workflow
|The name of the workflow module, the workflow id, the segment key, and the time a hibernated workflow wakes at.

|`WorkflowIndexWaitEntry`
|Open wait
|The name of the workflow module, the workflow id, the step name, the segment key, the event name, and the associations of the wait.

|`WorkflowIndexSegmentEntry`
|Segment
|The name of the workflow module, the range of segment keys of the segment, and the position in the event store its rows are correct at.
|===

A row holds a module name and a workflow id of at most 255 characters, a step name of at most 1024 characters, and at most 10,000 bytes of associations per wait.
A database that enforces these lengths rejects a longer value, and the segment then fails to store its token.

=== Database of the token store

Keep the workflow index in the database of the token store.
The engine then writes the rows in the transaction of the token, so the rows and the token are committed together.
For this, the processor must run its unit of work in a JPA transaction of that database.
Storing the token checks that the node still owns the segment, so a node that lost its segment claim writes nothing.

The time a hibernated workflow wakes at is a fact of one node, not of an event.
The engine stores it only under that check.
When the workflow index is in another database than the token store, configure `storesWithToken(false)`:

[source,java]
----
include::example$workflows/configuration/ConfigurationExamples.java[tag=workflow-index-other-database,indent=0]
----

The engine then writes the rows in a transaction of their own, before the processor stores the token.
A segment claim still reads its running workflows and open waits from the rows.
The rows hold no wake time.
The engine then records the hibernated workflows of a segment when it releases that segment, as it does without a workflow index.

=== First segment claim

A workflow index starts empty, while workflows may be running already.
A segment without a stored position is claimed as without a workflow index: the segment claim sources both lists.
The running workflows and the open waits of the segment then become its rows, and the engine stores them, and the position of the segment, with the next token.
From then on, a segment claim reads the rows of its segment.

The rows of that first segment claim hold no wake times.
So the segment claims of that first start load every running workflow into memory, including the hibernated ones.
Those workflows hibernate again, and the engine then stores their wake times.

=== Rollout

The workflow index can be turned on during a rolling restart, and nodes with and without it can run together.
A node without the workflow index writes no rows, and moves the token of a segment past events the rows do not hold.
A segment claim with the workflow index reads the events from the position the rows are correct at, not from the token.
So it also applies what a node without the workflow index handled, and the rows catch up with the next stored token.

Turning the workflow index off and on again needs no step of its own either.

See xref:workflow-internals.adoc#segment-claims[Segment claims] for how a segment claim reads the rows, and how the engine writes them.

[[performance-tuning]]
== Performance tuning

The engine processor handles each segment on one thread at a time.
After every batch it waits until every workflow of the segment is at a safe point, and only then stores its position.
Throughput therefore grows with the number of segments processed in parallel, and with fewer of these waits.
The event store usually sets the limit, so change one setting at a time and measure.

=== Segments and threads

The number of segments caps how many threads can process workflows at the same time, across all nodes.
In most scenarios, a segment segment count matching the total number of threads of all nodes is advised for high-throughput applications.
The initial segment count only applies when the token store has no tokens yet. To change it later, split or merge the stored tokens.

The thread count sets how many threads process the claimed segments of one node.
A node claims segments regardless of its thread count, so segments beyond it wait for a free thread.
Raise segments and threads together.
More threads help until the event store is busy. After that point they add load without adding throughput.

=== Database connections

With a JDBC or JPA event store or token store, every busy processor thread holds a database connection during its batch.
Workflow steps that use the same database need connections of their own.
Size the connection pool above the thread count, with room for those steps, so that threads never wait for a connection.

=== Batch size

The batch size sets how many events the processor handles before it commits and checkpoints.
A larger batch means fewer commits and fewer waits for a safe point.
Each wait can take longer, because a batch touches more workflows.

=== Checkpoint interval

The engine requests a checkpoint after every event it handles.
A positive checkpoint interval forwards at most one request per segment within that interval, so the processor waits less often under load.
The stored position then lags by at most the events of one interval, and those events are processed again after a crash.
The interval is in milliseconds. It defaults to `0`, which forwards every request.

=== Segment claims

Without a workflow index, every segment claim loads the list of running workflows and the list of open waits, which hold all segments.
The time and memory of a restart or a failover then grow with the number of segments and with the number of workflows of the whole application.
With a <<workflow-index,workflow index>>, a segment claim reads only the rows of its own segment.
Turn the workflow index on when restarts or failovers take long.

Keep <<snapshots,snapshots>> on as well.
A snapshot shortens the load of a single workflow instance, which the workflow index does not do.

With a workflow index, each stored token also writes the rows that changed since the token before it.
A larger batch size or a checkpoint interval groups more changes into one write.

=== Java version

Workflow steps run on virtual threads.
On Java 21 to 23, a virtual thread that blocks inside `synchronized` code keeps its carrier thread, and under load every carrier thread can end up blocked.
Java 24 and later do not have this limitation, so prefer them for workflows under load.

[[metadata-and-correlation-data]]
== Metadata and correlation data

Every workflow event carries metadata—key-value pairs attached to the event message alongside the payload.
The engine manages a set of internal metadata keys automatically, and Axon Framework's `CorrelationDataProvider` mechanism lets you propagate additional metadata from triggering events through the entire workflow.

=== Engine-managed metadata

The engine attaches the following metadata to every workflow and step event:

[cols="1,2"]
|===
|Key |Description

|`workflowId`
|The unique identifier of the workflow instance.

|`stepName`
|The name of the step (step events only).

|`stepType`
|The step's lifecycle phase: `STARTED`, `RETRYING`, `RETRY_STARTED`, `COMPLETED`, `FAILED`, `TIMED_OUT`, or `CANCELLED` (step events only).

|`stepPrimitive`
|Internal step classification used by the engine: `WAIT_FOR_EVENT` on `waitForEvent` step events, `PUBLISH` on events published with `publish` / `awaitPublish`.

|`workflowStatus`
|The workflow status: `STARTED`, `COMPLETED`, `FAILED`, `TIMED_OUT`, or `CANCELLED` (workflow events only).

|`workflowDefinitionName`
|The qualified name of the workflow definition (workflow events).

|`workflowDefinitionVersion`
|The version of the workflow definition (workflow events).

|`versionChangeId`, `version`
|The recorded version change identifier and the workflow version, on version marker events.

|`modifyPayload`
|The payload reducer name, if one was configured on a completed step (for example, `COMBINE_GLOBAL_AND_LOCAL`).
|===

These keys are managed by the engine and cannot be overridden.

=== Engine-managed event-store tags

Engine-published workflow events are also written with event-store tags.

[cols="1,2"]
|===
|Tag |Description

|`workflowId=<id>`
|Added to every engine-published event that carries `workflowId` metadata, including business events published with `publish` / `awaitPublish` (their own tags are kept).

|`workflowEvent=lifecycle`
|Added to workflow lifecycle events.

|`workflowEvent=waitForStep`
|Added to `waitForEvent` and `sleep` step events with status STARTED, COMPLETED, TIMED_OUT or CANCELLED.
|===

These tags are intended for event-sourced read models such as "currently running workflow executions" and "currently
waiting steps".
The engine reads the same tags to route events to waiting workflows, see xref:workflow-internals.adoc#event-routing[Event routing].

=== How it works

The propagation path:

1. An incoming event with metadata arrives and triggers a new workflow.
2. The `CorrelationDataProvider` extracts correlation data and attaches it to the `ProcessingContext`.
3. The engine passes this `ProcessingContext` to the workflow execution.
4. When a step publishes events, the engine creates a child `UnitOfWork` and copies all resources from the parent context.
5. The correlation data flows through to the published event's metadata.

This means correlation data propagation is *transparent*—workflow code does not need to know about it.

[NOTE]
====
Correlation data propagation carries metadata that originates from the *triggering event*.
If you need to attach metadata that doesn't come from the triggering event (for example, computed values, workflow-specific tags), a dedicated `MetadataCustomizer` API is planned—see https://github.com/AxonIQ/extension-workflow/issues/103[#103].
====

== Custom workflow context

You don't have to use `SimpleWorkflowContext`. `WorkflowContext` is the shared author-facing contract, and
`BaseWorkflowContext` is the canonical Java DSL layer implementing it with Java-friendly named overloads.
`SimpleWorkflowContext` adds helpers such as typed `awaitEvent`, `sleep(Duration)`, `setPayload`, and `cancel(String)`.
