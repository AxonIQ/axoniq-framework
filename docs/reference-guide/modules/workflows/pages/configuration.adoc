= Configuration
:navtitle: Configuration

This section covers the declarative (programmatic) configuration API, which gives you full control over how workflows are wired up—and how to customize the context, event naming, ID resolution, and more.

[[workflow-id-rules]]
=== Valid workflow IDs

Whichever provider you use, a workflow ID must be valid:

* It has at least one and at most 255 characters: an empty ID is not allowed.
* Every character is printable ASCII: from the space (`0x20`) up to the tilde (`~`, `0x7E`).
Letters with accents, other non-ASCII characters, tabs, and line breaks are not allowed.

These rules apply with and without a <<workflow-index,workflow index>>.
They keep every workflow ID storable in a `VARCHAR(255)` column, and readable in logs and in your database.
The engine checks the ID that the provider derives from a start event.
When the ID is invalid, the engine does not start the workflow and logs an error naming the workflow, its version, the event, why the ID is invalid, and the first 64 characters of the ID.
The event itself is handled as usual, so later events, including starts of other workflows, are not affected.

The default `MessageWorkflowIdProvider` derives a valid ID: an event identifier is a UUID, unless your application assigns identifiers of its own.
With `idProperty`, a `PayloadPropertyWorkflowIdProvider`, or a provider of your own, make sure the derived ID is valid.
When your business key may be longer than 255 characters, or contain other characters, derive a valid ID from it.
For example, pass an ID processor to the `PayloadPropertyWorkflowIdProvider` that hashes the key with SHA-256, which always yields 64 hexadecimal characters:

[[running-on-several-nodes]]
== Running on several nodes

Each `WorkflowModule` runs its engine on its own pooled streaming event processor, named after the module.
The history projector runs on a second processor named `WorkflowHistoryProjector[<module name>]`.
Each workflow instance belongs to one segment of the engine processor, chosen by the hash of its workflow id.
Subscribing processors, including Axon Server persistent streams, cannot back workflows.

=== Token store

The processor claims its segments in the unnamed `TokenStore` component of your application.
Register a durable store, for example `JpaTokenStore`, as an unnamed component.
Without one, the engine falls back to an in-memory token store and logs a warning.
Claims then stay inside the process, so run a single node only.
A workflow module whose engine keeps a durable <<workflow-index,workflow index>> refuses to start with an in-memory token store.

=== Processor settings

After the workflow definitions, the module builder accepts `processorConfiguration(...)` for the engine processor and `historyProcessorConfiguration(...)` for the history processor.
Both take a function that receives and returns a `PooledStreamingEventProcessorConfiguration`.
Only the initial segment count is applied to a new token store. To change it later, split or merge the stored tokens.

=== Failover

When a node stops, another node claims its segments and resumes the unfinished workflow instances.
Every event an instance appends carries an append condition on its workflow id.
A node that lost its claim without noticing has its append rejected, logs a warning, and stops that instance.

[[snapshots]]
=== Snapshots

The engine sources two event-sourced entities: the list of running workflows and the state of each workflow instance.
Without snapshots, a node that takes over replays the full event history of both.
Snapshots are off by default.
Enable them on the `WorkflowConfigurer`:

----

<.> The policy for the workflow state. Each workflow instance has a snapshot of its own, stored under its workflow id.

Both policies default to a snapshot after 50 sourced events.
The setting applies to every `WorkflowModule` of the application, because all modules share both entities.
The history projector does not source these entities, so snapshots do not affect it.

Snapshots need a `SnapshotStore` component.

An application that enables snapshots without a `SnapshotStore` fails to start.
A snapshot is taken while an entity is sourced, so the first restore after enabling snapshots still replays the full history.
See xref:snapshotting:index.adoc[Snapshotting] for snapshot policies and snapshot stores.

[[workflow-index]]
=== Workflow index

When a node claims a segment, the engine restores the workflow instances of that segment that are still running.
To find them without reading every workflow lifecycle event ever written, it keeps a workflow index: the running workflow instances, stored by workflow id.
A claim loads the entries of its segment and only reads the workflow lifecycle events after the token the segment resumes from.

The index has no position of its own: the token of the processor is its position.
The engine keeps the changes of the index in memory, and writes them whenever the processor takes a checkpoint, before the processor stores the token.
So a claim always finds the index complete up to the token it resumes from, and the lifecycle events after that token complete it.
When the index cannot be written, the checkpoint fails: the processor releases the segment and claims it again after a back-off, restoring its running workflows from the event store as on any claim.
After a crash, the processor reprocesses the events after its last stored token, which brings the index up to date again.
So with an index, the engine decides when the processor of the workflow module stores its tokens.
An application whose customization of that processor adds ordinary event handling components to it, which do not decide on their own when to store tokens, or replaces how it stores its tokens, fails to start.

The workflow index is derived data.
The event store remains the source of truth, and as long as every node that runs the workflow module writes the index, it never makes the engine lose a running workflow.
An index starts out empty and not initialized.
The first claim then reads the list of running workflows from the event store, and initializes the index with it.
From then on, every claim uses the index.
This also applies when you introduce the index into an application that already runs workflows, or when you empty its tables.

The index must be shared by every node that runs the workflow module, and must survive a restart whenever the tokens do.
In turn, the tokens of the processor of the workflow module must survive a restart whenever the index does.
A processor without stored tokens starts at the head of the event stream, while the index is still initialized, so its claims miss the running workflows whose start the index did not store yet.
A workflow module with an index other than an `InMemoryWorkflowIndex` therefore fails to start when its processor keeps its tokens in an `InMemoryTokenStore`, as it does without a token store.
That processor takes its token store from the unnamed `TokenStore` component, or from the `processorConfiguration(...)` of the workflow module: a token store set through the event processing defaults does not reach it.
For the same reason, when you delete or reset the tokens of that processor, empty the index as well: its entries and its initialization marker.
By default, the engine keeps no index, so every claim reads the running workflows from the event store.

WARNING: Enable the index only once every node that runs the workflow module runs a version that writes it.
A node that does not write the index, such as a node of an earlier version, or one without the index configured, can advance the token of a segment while workflows start in it.
The index then misses those workflows, and a later claim that uses the index does not restore them.
If that happened, stop every node that runs the workflow module, and empty both tables of the index: the entries and the initialization marker.
The next claim of each segment then initializes the index again from the event store.

Enabling the index needs no reset or replay of the processor of the workflow module: the first claim initializes the index from the event store.
Do not reset that processor to build the index: a reset is not a supported way to build it.

To keep the index in your database, use a `JpaWorkflowIndex`:

[source,java]
----
include::example$workflows/configuration/ConfigurationExamples.java[tag=jpa-workflow-index,indent=0]
----
<.> The entity manager factory of the persistence unit that holds the index. Use `transactionalExecutorProvider(...)` instead to provide the transactions yourself.

When the processor of the workflow module runs its batches in a JPA transaction, as it does in Spring Boot with JPA, or with an `EntityManagerTransactionManager`, the `JpaWorkflowIndex` writes the changes of a checkpoint within that transaction.
The changes and the token are then committed together, and a checkpoint needs no database connection besides the one the processor already holds.
Like the JPA token store, the index then assumes that it lives in the database of that transaction.
To keep the index in another database, pass a `transactionalExecutorProvider(...)` that ignores the processing context, such as `context -> provider.getTransactionalExecutor(null)`.

Without such a transaction, for loading and initializing the index, and for the changes it writes when the processor releases a segment, the index runs every operation in a transaction of its own.
The builder accepts an `executor(...)` that runs that database work, by default four daemon threads, and a `timeout(...)`, by default ten seconds.
The timeout bounds how long an operation may wait for the executor before it fails, and each query of an operation that started.
It does not bound the whole operation: a started operation completes once its transaction has ended.
Such a write needs a connection of its own, see <<database-connections,Database connections>>.

An `InMemoryWorkflowIndex` keeps the index in memory.
Use it only in tests, or when a single node runs the workflow module: the index of one node does not know the changes the other nodes made.

[[workflow-index-tables]]
The `JpaWorkflowIndex` stores its data in two entities, `WorkflowIndexEntry` and `WorkflowIndexInitialization` from the `io.axoniq.framework.workflow.index.jpa` package.
Add them to your persistence unit.
If you manage your schema yourself, for example with Flyway or Liquibase, create their tables.
Table and column names follow the naming strategy of your JPA provider:

[cols="1,3"]
|===
|Entity |Columns

|`WorkflowIndexEntry`
|`indexName VARCHAR(255)` and `workflowId VARCHAR(255)` as primary key, `segmentKey BIGINT NOT NULL`, and an index on (`indexName`, `segmentKey`).

|`WorkflowIndexInitialization`
|`indexName VARCHAR(255)` as primary key.
|===

The `workflowId` column holds the workflow ID itself, so you can look up the entry of a workflow by its ID.
It fits every <<workflow-id-rules,valid workflow ID>>: the engine never starts a workflow with an invalid one.

[[workflow-index-collation]]
The `workflowId` column must compare IDs exactly: case-sensitively, and without ignoring trailing spaces, as a binary collation does.
The index deletes and inserts its entries by workflow ID.
Under a case-insensitive or pad-space collation, the entries of `ORDER-1` and `order-1`, or of `order-1` and `order-1` followed by a space, overwrite each other, and a running workflow silently drops out of the index.
When such IDs are written together, they fail on a duplicate key instead: at initialization, which keeps the index uninitialized, or in one checkpoint of the segment that owns both, which fails that checkpoint.
Some databases use such a collation by default, so declare the column with a binary collation there:

[cols="1,3"]
|===
|Database |`workflowId` column

|MySQL 8.0.17 or later
|`workflowId VARCHAR(255) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_bin NOT NULL`.
The default collation, `utf8mb4_0900_ai_ci`, is case-insensitive.
The older binary collations `utf8mb4_bin` and `ascii_bin` are case-sensitive, but ignore trailing spaces.

|SQL Server
|`workflowId VARCHAR(255) COLLATE Latin1_General_100_BIN2 NOT NULL`, or another `_BIN2` collation.
The default collations are case-insensitive.
SQL Server ignores trailing spaces when it compares strings, whatever the collation, so do not use workflow IDs that differ only in trailing spaces.

|PostgreSQL, H2
|`workflowId VARCHAR(255) NOT NULL`.
The default collations already compare exactly.
|===

WARNING: Enable the `JpaWorkflowIndex` only when no running workflow has an invalid ID, such as a workflow that an earlier version of the engine started with an ID longer than 255 characters.
The index cannot hold such a workflow, and rejects it with an error that names the first 64 characters of its ID.
The segment that owns the workflow then makes no progress: every checkpoint fails, so its token does not advance past the first event it handles, and the processor keeps claiming that segment again and reprocessing the same events.
Because the index is initialized with every running workflow, it also stays uninitialized, so every claim of every segment reads the full list of running workflows.
This lasts until that workflow is cancelled or has ended, or until you disable the index.
Let such workflows end, or cancel them, before you enable the index.

Several workflow modules share one workflow index, each under its own name.
To store the index elsewhere, implement the `WorkflowIndex` interface and register it with `registerWorkflowIndex(...)`.
Its Javadoc describes the contract an implementation must meet, such as completing a write only once it is durable.

IMPORTANT: The workflow index types are marked `@Internal`.
They are usable and supported to configure the index and to write your own implementation, but their shape may still change in a minor release.

[[performance-tuning]]
== Performance tuning

The engine processor handles each segment on one thread at a time.
After every batch it waits until every workflow of the segment is at a safe point, and only then stores its position.
Throughput therefore grows with the number of segments processed in parallel, and with fewer of these waits.
The event store usually sets the limit, so change one setting at a time and measure.

=== Segments and threads

The number of segments caps how many threads can process workflows at the same time, across all nodes.
In most scenarios, a segment segment count matching the total number of threads of all nodes is advised for high-throughput applications.
The initial segment count only applies when the token store has no tokens yet. To change it later, split or merge the stored tokens.

The thread count sets how many threads process the claimed segments of one node.
A node claims segments regardless of its thread count, so segments beyond it wait for a free thread.
Raise segments and threads together.
More threads help until the event store is busy. After that point they add load without adding throughput.

[[database-connections]]
=== Database connections

With a JDBC or JPA event store or token store, every busy processor thread holds a database connection during its batch.
Workflow steps that use the same database need connections of their own.
Size the connection pool above the thread count, with room for those steps, so that threads never wait for a connection.

A `JpaWorkflowIndex` that writes within the processor's JPA transaction needs no extra connection for its checkpoints.
Only when the processor releases a segment does it write the remaining changes on a connection of its own, waiting at most three seconds for it.
When it cannot, for example because the processor runs its batches in a JDBC transaction of the same database, every checkpoint waits for a write on a connection of its own while its thread holds the batch connection.
Then size the pool for at least one connection per busy processor thread plus the threads of the index, four by default.
Otherwise, checkpoints wait for connections their own threads hold, and fail once the index times out.

=== Batch size

The batch size sets how many events the processor handles before it commits and checkpoints.
A larger batch means fewer commits and fewer waits for a safe point.
Each wait can take longer, because a batch touches more workflows.

=== Checkpoint interval

The engine requests a checkpoint after every event it handles.
A positive checkpoint interval forwards at most one request per segment within that interval, so the processor waits less often under load.
The stored position then lags by up to the events of one interval, and those events are processed again after a crash.
A segment that goes idle keeps that lag until its next event, or until the processor releases it.
With a <<workflow-index,workflow index>>, every checkpoint also writes the changes of the index, so fewer checkpoints mean fewer, larger writes.
The interval is in milliseconds. It defaults to `0`, which forwards every request.

=== Java version

Workflow steps run on virtual threads.
On Java 21 to 23, a virtual thread that blocks inside `synchronized` code keeps its carrier thread, and under load every carrier thread can end up blocked.
Java 24 and later do not have this limitation, so prefer them for workflows under load.

[[metadata-and-correlation-data]]
== Metadata and correlation data

Every workflow event carries metadata—key-value pairs attached to the event message alongside the payload.
The engine manages a set of internal metadata keys automatically, and Axon Framework's `CorrelationDataProvider` mechanism lets you propagate additional metadata from triggering events through the entire workflow.

=== Engine-managed metadata

The engine attaches the following metadata to every workflow and step event:

[cols="1,2"]
|===
|Key |Description

|`workflowId`
|The unique identifier of the workflow instance.

|`stepName`
|The name of the step (step events only).

|`stepType`
|The step's lifecycle phase: `STARTED`, `RETRYING`, `RETRY_STARTED`, `COMPLETED`, `FAILED`, `TIMED_OUT`, or `CANCELLED` (step events only).

|`stepPrimitive`
|Internal step classification used by the engine: `WAIT_FOR_EVENT` on `waitForEvent` step events, `PUBLISH` on events published with `publish` / `awaitPublish`.

|`workflowStatus`
|The workflow status: `STARTED`, `COMPLETED`, `FAILED`, `TIMED_OUT`, or `CANCELLED` (workflow events only).

|`workflowDefinitionName`
|The qualified name of the workflow definition (workflow events).

|`workflowDefinitionVersion`
|The version of the workflow definition (workflow events).

|`versionChangeId`, `version`
|The recorded version change identifier and the workflow version, on version marker events.

|`modifyPayload`
|The payload reducer name, if one was configured on a completed step (for example, `COMBINE_GLOBAL_AND_LOCAL`).
|===

These keys are managed by the engine and cannot be overridden.

=== Engine-managed event-store tags

Engine-published workflow events are also written with event-store tags.

[cols="1,2"]
|===
|Tag |Description

|`workflowId=<id>`
|Added to every engine-published event that carries `workflowId` metadata, including business events published with `publish` / `awaitPublish` (their own tags are kept).

|`workflowEvent=lifecycle`
|Added to workflow lifecycle events.

|`workflowEvent=waitForStep`
|Added to `waitForEvent` step STARTED and terminal events.
|===

These tags are intended for event-sourced read models such as "currently running workflow executions" and "currently
waiting steps".

=== Correlation data propagation

=== How it works

The propagation path:

1. An incoming event with metadata arrives and triggers a new workflow.
2. The `CorrelationDataProvider` extracts correlation data and attaches it to the `ProcessingContext`.
3. The engine passes this `ProcessingContext` to the workflow execution.
4. When a step publishes events, the engine creates a child `UnitOfWork` and copies all resources from the parent context.
5. The correlation data flows through to the published event's metadata.

This means correlation data propagation is *transparent*—workflow code does not need to know about it.

[NOTE]
====
Correlation data propagation carries metadata that originates from the *triggering event*.
If you need to attach metadata that doesn't come from the triggering event (for example, computed values, workflow-specific tags), a dedicated `MetadataCustomizer` API is planned—see https://github.com/AxonIQ/extension-workflow/issues/103[#103].
====
