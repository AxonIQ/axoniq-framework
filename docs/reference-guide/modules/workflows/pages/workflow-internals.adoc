= Workflow Internals
:navtitle: Workflow internals

This page explains how the workflow engine works inside, for when you need to reason about its behavior.
You don't need it to define or configure workflows.

[[event-routing]]
== Event routing

An event a workflow writes for its own steps reaches only the segment that owns that workflow.
An event that starts exactly one workflow reaches only the segment that owns the new workflow.
Every other event, including an event published with `publish` / `awaitPublish`, reaches every segment.

A segment hands the event only to the workflows it owns that need it:

* the workflows waiting for the event, matched on event name and equality associations, see xref:waiting-for-events.adoc#_filtering_with_associations[Filtering with associations],
* the publisher of a published event, which records its publish step on it,
* the workflows the event starts.

To match waits, each node keeps the open waits of the workflows on the segments it holds.
It loads them when it claims a segment, see <<segment-claims,Segment claims>>.
Without a workflow index, it loads them from the event store, from the events tagged `workflowEvent=waitForStep` and `workflowEvent=lifecycle`.
With a workflow index, it loads them from the rows of the segment.
Until a segment has loaded its open waits, when loading them fails, and while it processes the backlog stored before the node started, that segment hands each event to every workflow it owns.

A segment that receives no events still stores its token, on the processor's claim-extension cycle, once its workflows have no work in progress.

[[hibernation]]
== Hibernation

=== When a workflow hibernates

At every hibernation interval, the engine asks the workflows in memory to hibernate.
A workflow hibernates only at a safe point:

* its body waits on a step result, or on `anyMatch`, `allMatch` or `noneMatch` of step results,
* every step it has not finished is a `waitForEvent` or a `sleep`,
* no step call is still in progress, no task is queued, and no cancellation is pending.

A running `execute` step keeps the workflow in memory, also while it waits for a retry.
A hibernating workflow stops the way the workflows of a released segment stop, so it writes no events.

=== How a workflow wakes up

For each hibernated workflow, the engine keeps a timer for the nearest timeout of its waits, and a stand-in for its cancellations.
The workflow wakes up when one of these happens:

* an event it waits for arrives,
* that timer fires,
* a step or workflow cancellation is requested for it.

The engine then loads the workflow from the event store and replays its history to the point where it waited.
A lock per workflow keeps a wake, an event and a cancellation of the same workflow apart, so none of them gets lost while the workflow leaves memory.

[[hibernation-claims]]
=== Restarts and segment claims

When a node releases a segment, also when the application stops, it forgets the hibernated workflows of that segment.
A workflow does not hibernate while its segment is being released.

A segment claim keeps a hibernated workflow out of memory when it can tell that the workflow hibernated.
How it can tell depends on the xref:configuration.adoc#workflow-index[workflow index].

With a workflow index in the database of the token store, the row of a hibernated workflow carries the time the workflow wakes at.
The engine writes that time the next time the segment stores its token, and on the release of the segment.
It removes that time when the workflow wakes up.
A segment claim, on any node, keeps a workflow out of memory when its row carries a wake time and no event after the stored token belongs to that workflow.
A workflow that made progress after it hibernated closed a wait or ended, and the segment claim reads both events.
The rows are committed with the token, so this also works after a crash.
For each workflow it keeps out of memory, the segment claim starts the timer for the wake time and keeps the open waits.

The rows of a workflow index in another database than the token store hold no wake time.
With such a workflow index, or without a workflow index, a segment claim replays every unfinished workflow of the segment, which then hibernates again at the same wait.

A segment split or merge replaces segments without releasing them.
The claim of a new segment first forgets the hibernated workflows it owns that were kept for the old segment, and then restores them or keeps them out of memory again.
With a workflow index, the rows stay valid after a split or a merge, because the segment key of a row does not depend on the segments.

[[segment-claims]]
== Segment claims

When a node claims a segment, the engine learns three things: which workflow instances of the segment are running, which waits are open, and which workflows are hibernated.
It restores the running workflows that are not hibernated, and keeps the open waits for <<event-routing,event routing>>.

=== Without a workflow index

The engine sources the list of open waits and the list of running workflows from the event store.
Both lists hold all segments, so the engine keeps only the entries of the workflows that the claimed segment owns.
It keeps no workflow hibernated, see <<hibernation-claims,Restarts and segment claims>>.

=== With a workflow index

The xref:configuration.adoc#workflow-index[workflow index] holds one row per running workflow and one row per open wait.
It also marks each workflow module that was initialized, and keeps the token position of each segment for the <<workflow-manager-index,workflow manager>>.
A segment claim takes three steps:

. It reads the rows of the claimed segment with one range query per table on the segment key.
. It reads the events published after the stored token of the segment. It reads only the events tagged `workflowEvent=waitForStep` or `workflowEvent=lifecycle`.
. It applies those events to the rows. A started workflow is added. An ended workflow is removed with its waits. An opened wait is added. A closed wait is removed.

The rows plus those events are the running workflows and the open waits as of the segment claim.
Applying an event twice changes nothing, because a workflow starts once and ends once, and a wait opens once and closes once.

After a split, both new segments resume from the token of the old segment.
After a merge, the new segment resumes from the lower token of the two.
So a segment claim reads every event its rows may miss after a split or a merge too.

A segment claim sources both lists instead, as without a workflow index, in three cases:

* the workflow module is not initialized: the workflow index started empty or was emptied. That segment claim initializes the workflow index with both lists, for every segment of the module,
* the segment has no stored token to read the events from,
* reading the rows or the events after the token fails.

A segment claim that sources does not know which rows carry a wake time.
So every workflow it loads into memory loses the wake time in its row, and a later segment claim does not take a workflow that moved on for a hibernated one.

A segment claim that sources stores the sourced workflows and waits of its segment as the rows of that segment, with the next token.
A row of the segment whose workflow it did not source is removed.

=== The segment key

A segment owns the workflow ids whose hash ends in the bits of its segment id.
Each row stores the segment key of its workflow id: that hash with its bits reversed, read as an unsigned number.
Reversed, the workflow ids of one segment form one contiguous range of segment keys.
A split halves the range, and a merge joins two neighboring ranges.
So the segment key of a row never changes, and the rows of a segment survive a split and a merge.

=== How the rows are written

While a segment handles events, the engine notes what changes in its rows: a workflow started or ended, a wait opened or closed, a workflow hibernated or woke up.
Each time the processor stores the token of the segment, the engine first writes the noted changes that this token covers.
With a workflow index in the database of the token store, the rows and the token are committed in one transaction, or neither is.
In another database, the rows are committed before the token.
Either way, the rows hold every change up to the stored token, so the token is the position of the rows.
Rows ahead of the token, as after a crash between the two commits, are harmless: applying the events after the token again gives the same rows.

A node that lost its segment claim writes nothing:

* Storing a token checks that the node still owns the segment, and fails the transaction when it does not.
* A token that did not advance is not stored. The processor then extends the claim in the same transaction, which makes the same check.
* On the release of a segment, the processor checks the claim before the engine writes.

With a workflow index in another database than the token store, the engine writes the rows in a transaction of their own, before the processor stores the token.
The rows are then never behind the token.
They can be ahead of it, and the events a segment claim reads correct that.

[[workflow-manager-index]]
=== Workflow manager

The workflow manager uses the same rows when a query targets live workflows, for example to cancel them.
It cannot read the tokens of the workflow processor without claiming their segments.
So with each token, the engine also writes the position of that token: one row per segment, with the range of segment keys of the segment.
A merged token gives its lower position.
A new position replaces every stored position whose range overlaps it, as after a split or a merge.
While a segment changes no row, its position moves at most every 10 seconds.

The workflow manager reads the rows of its candidates by workflow id, and the lifecycle events after the lowest position of the module.
While a segment key has no position, as right after a split, or when the read fails, it sources the list of running workflows instead.
A segment claim never reads these positions.
