= Distributed Tracing
:navtitle: Tracing

Distributed Tracing enables you to track the path of a message through your system to see how the system behaves and performs.
Axon Framework ships built-in tracing decorators for commands, events, queries, repositories, state managers, event storage and snapshots, plus a per-method handler enhancer that records every annotated handler invocation.

Tracing decorators wrap the framework's components by composition.
A single `SpanFactory` is the only public abstraction for span creation; per-component span shapes (names, kinds, attributes, cross-process metadata propagation) are implementation details of the internal decorators registered via `ConfigurationEnhancer` (discovered through Java's `ServiceLoader`).
The decorators ship inside the framework modules themselves, so registering a `SpanFactory` component is enough to enable tracing for every component on the classpath.

A *trace* is a collection of one or more *spans* that together form a complete journey through your software; each span records one timed operation and its relationship to the others.
Rendered in a tool such as link:https://www.jaegertracing.io/[Jaeger,role=external,window=_blank], a single user action becomes one navigable tree.
The following capture shows an HTTP request that dispatches a command through Axon Server: the handler loads the entity, publishes an event, and event processors update a projection, emit a subscription-query update, and dispatch a follow-up command, all within the same trace:

image::jaeger-command-trace.png[A command dispatched through Axon Server rendered in Jaeger, including event processors and a follow-up command in the same trace]

This capture uses `axon.tracing.event-processor.distributed-in-same-trace=true` to render everything as one trace; with the default settings, event processors record their work in separate traces that link back to the publication (see <<Streaming consumer trace topology>>).

Migrating from Axon Framework 4 tracing? Follow the xref:migration:paths/distributed-tracing.adoc[Distributed Tracing migration path].

[NOTE]
====
Sagas, process managers and deadlines are not available in Axon Framework 5.0. They will be reintroduced in later versions. Tracing today covers the messaging, modelling and event-sourcing surfaces that exist in 5.0.
====

== Modules

Tracing lives inside the framework modules whose components it covers, so a consumer gets tracing for exactly the parts of the framework it uses:

[cols="<,<"]
|===
|Module |Contents

|`axon-messaging` |The public SPI in `org.axonframework.messaging.tracing`: `SpanFactory`, `Span`, `SpanScope`, `SpanAttributesProvider`, the `SpanAttributesProviderRegistry`, the built-in attribute providers, `NoOpSpanFactory`, and `LoggingSpanFactory`. It also contains decorators for `CommandBus`, `EventSink`, `EventHandlingComponent`, and `QueryBus`, plus the handler enhancer.
|`axon-modelling` |Decorators for `Repository` and `StateManager`.
|`axon-eventsourcing` |Decorators for `EventStore`, `EventStorageEngine`, and `SnapshotStore`, plus the event-tag span attributes.
|`axoniq-distributed-messaging` |Decorators for the distributed `CommandBusConnector` and `QueryBusConnector`, tracing the transport leg between the bus-level dispatch and handle spans.
|`axoniq-tracing-micrometer` |The Micrometer Tracing implementation of `SpanFactory`. It uses the `Tracer` and `Propagator` supplied by the application's OpenTelemetry or Brave bridge.
|===

The Spring Boot starter wires everything up automatically from `axon.tracing.*` properties.
Outside Spring, the same wiring is done by the per-module `ConfigurationEnhancer` discovered by `ServiceLoader`; no explicit registration is required.

== Configuration

=== Spring Boot

Add the Micrometer binding, Spring Boot Actuator, an OpenTelemetry bridge, and an OTLP exporter:

[source,xml]
----
<dependency>
    <groupId>io.axoniq.framework</groupId>
    <artifactId>axoniq-tracing-micrometer</artifactId>
    <version>${axoniq-framework.version}</version>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-otel</artifactId>
</dependency>
<dependency>
    <groupId>io.opentelemetry</groupId>
    <artifactId>opentelemetry-exporter-otlp</artifactId>
</dependency>
----

Spring Boot supplies the Micrometer `Tracer` and `Propagator`.
The Axoniq Framework binding uses them to register `MicrometerSpanFactory` as the active `SpanFactory`.
Every component the framework creates is then decorated for tracing.

Because the binding consumes Spring Boot's standard observability stack, everything Spring Boot manages applies to Axon Framework spans as well:

* Sampling and propagation follow the standard `management.tracing.*` properties.
* Traces started by Spring Boot's own instrumentation, such as an incoming HTTP request handled by Spring MVC or WebFlux, continue seamlessly into the framework's dispatch and handler spans.
* Log correlation works out of the box: Spring Boot prefixes log lines with the current trace and span identifiers, and the worker-thread bridge keeps them correct inside asynchronous framework work.
* Exporters are configured once, at the Spring Boot level, and apply to Axon Framework spans and every other instrumented library alike.

For local experimentation you can use the SLF4J implementation:

[source,java]
----
@Configuration
public class TracingConfig {

    @Bean
    public SpanFactory spanFactory() {
        return LoggingSpanFactory.INSTANCE;
    }
}
----

=== Plain `MessagingConfigurer`

[source,java]
----
MessagingConfigurer.create()
                   .componentRegistry(registry -> registry
                           .registerComponent(Tracer.class, c -> tracer)
                           .registerComponent(Propagator.class, c -> propagator))
                   .registerCommandHandlingModule(...)
                   .start();
----

The Micrometer and component tracing enhancers are picked up via `ServiceLoader`.
The Micrometer enhancer creates the `SpanFactory` from the registered `Tracer` and `Propagator`.

=== Toggles

Every component can be opted out individually through the `axon.tracing.*` namespace:

[cols="<,<,<"]
|===
|Property |Default |Effect when set to `false`

|`axon.tracing.enabled` |`true` |Whole tracing auto-configuration backs off; no `SpanFactory` is registered.
|`axon.tracing.command-bus.enabled` |`true` |The `CommandBus` is not decorated.
|`axon.tracing.event-sink.enabled` |`true` |The `EventSink` is not decorated.
|`axon.tracing.event-store.enabled` |`true` |The `EventStorageEngine` is not decorated.
|`axon.tracing.event-processor.enabled` |`true` |Event-handling components are not decorated.
|`axon.tracing.query-bus.enabled` |`true` |The `QueryBus` is not decorated.
|`axon.tracing.repository.enabled` |`true` |`Repository` components are not decorated.
|`axon.tracing.state-manager.enabled` |`true` |The `StateManager` is not decorated.
|`axon.tracing.snapshot-store.enabled` |`true` |The `SnapshotStore` is not decorated.
|`axon.tracing.command-bus-connector.enabled` |`true` |The distributed command connector is not decorated.
|`axon.tracing.query-bus-connector.enabled` |`true` |The distributed query connector is not decorated.
|`axon.tracing.thread-local-context-propagation.enabled` |`true` |The worker-thread bridge is disabled. Span creation and message metadata propagation remain enabled.
|`axon.tracing.attribute-providers.*` |`true` |Disable individual built-in attribute providers (`message-id`, `message-type`, `metadata`, `aggregate-identifier`, `event-tags`).
|===

== Multiple tracing destinations

Axon Framework uses one active `SpanFactory`; sending spans to several destinations is the export layer's job.
With the OpenTelemetry bridge, Spring Boot picks up every `SpanExporter` bean, so a second backend is one extra dependency or bean away:

[source,java]
----
@Bean
public SpanExporter zipkinSpanExporter() {
    return ZipkinSpanExporter.builder()
                             .setEndpoint("http://zipkin:9411/api/v2/spans")
                             .build();
}
----

All registered exporters receive the same spans.
Individual exporters can be toggled per environment through `management.tracing.export.<name>.enabled`, and `management.tracing.export.enabled=false` turns off export entirely without touching the Axon configuration.

[NOTE]
====
Axon Framework 4 offered a `MultiSpanFactory` for this purpose.
It no longer exists: fanning out to multiple destinations is a responsibility of the tracing setup rather than of the framework's span lifecycle, which keeps every Axon span created and ended exactly once.
====

== Span attribute providers

Tracing implementations attach attributes to spans for searchability and debugging.
The `SpanAttributesProvider` SPI lets components contribute attributes; Axon Framework ships five built-in providers.
The first four are enabled by default; event-tag attributes are added whenever a `TagResolver` is available in the Axon configuration (see the note below).

[cols="<,<,<"]
|===
|Provider |Default key |Description

|`MessageIdSpanAttributesProvider` |`axoniq.message.id` |The identifier of the message.
|`MessageTypeSpanAttributesProvider` |`axoniq.message.type` |The type of the message (its qualified name plus version).
|`MetadataSpanAttributesProvider` |`axoniq.metadata.{key}` |Each entry of the message metadata.
|`AggregateIdentifierSpanAttributesProvider` |`axoniq.aggregate.identifier` |The identifier of the legacy aggregate the message is bound to, when known. Absent on Dynamic Consistency Boundary or entity-based paths.
|`EventTagsSpanAttributesProvider` |`axoniq.event_tag.{key}` |Each tag of an event, resolved through a `TagResolver` (the `@EventTag`-annotated members of the payload by default). Best-effort; see the note below.
|===

Event tags are recorded on both sides of the event flow:

* On the publish side, `EventTagsSpanAttributesProvider` resolves tags when the span is created, while the payload is still the concrete object.
* On the handling side, streamed events arrive in serialized form, so span-creation-time resolution finds nothing.
The `TracingEventTagsHandlerEnhancerDefinition` (discovered automatically from the classpath) therefore enriches the active handler span at `@EventHandler` invocation time, resolving tags against the payload converted to the handler's declared parameter type.
`@EventSourcingHandler` methods are excluded: during a replay they would flood the enclosing span with tags from every replayed event.

Tags are resolved from the *current* payload-class declaration through the configured `TagResolver` (for example the `AnnotationBasedTagResolver`, which reads `@EventTag`-annotated members); without a `TagResolver` no tag attributes are added.
Tag resolution is *best-effort*: a resolved value can be absent or differ from what was physically stored, for example after the payload class evolved (a tag member was renamed, added or removed).
Only event messages contribute tag attributes.
Both sides honor the same `axon.tracing.attribute-providers.event-tags` toggle.

The default keys follow the OpenTelemetry-style dotted layout with `snake_case` leaves.
Each provider takes a constructor that overrides its attribute key (or, for `MetadataSpanAttributesProvider`, its prefix), so you can restore the Axon Framework 4 keys (`axon_message_type` and so on) without losing the typed contract.

You can also register your own:

[source,java]
----
@Bean
public SpanAttributesProvider tenantSpanAttributesProvider() {
    return (message, context) -> {
        if (message.metadata().containsKey("tenant")) {
            return Map.of("axoniq.tenant", message.metadata().get("tenant"));
        }
        return Map.of();
    };
}
----

Auto-configuration bridges every `SpanAttributesProvider` bean into the `SpanAttributesProviderRegistry`; the `SpanFactory` receives the registry's complete provider list at construction time. In plain Java, contribute a provider with `SpanAttributesProviderRegistry.register(componentRegistry, config -> provider)`.

== Traced components

The following span trees are produced when the corresponding decorator is active.
Span names use the layout `<Component>.<operation> <messageName>`; the kinds follow the OpenTelemetry convention (`PRODUCER` for dispatch, `CONSUMER` for handling, `INTERNAL` for everything else).

[NOTE]
====
Each `Tracing*` decorator class owns its span-name prefixes as `public static final String` constants, for example `TracingCommandBus.DISPATCH_SPAN` / `HANDLE_SPAN`, `TracingQueryBus.DISPATCH_SPAN` / `HANDLE_SPAN`, `TracingRepository.LOAD_SPAN`, and so on. The tables below mirror those constants.
====

=== Commands

[cols="<,<,<"]
|===
|Span name |Kind |Description

|`CommandBus.dispatchCommand <commandName>` |`PRODUCER` |The bus is dispatching the command.
|`CommandBus.handleCommand <commandName>` |`CONSUMER` |The bus is handing the command to its handler. Nests under the dispatch span via the W3C tracing context propagated on the command's metadata.
|`<HandlerClass>.<method>(<PayloadClass>)` |`INTERNAL` |The annotated `@CommandHandler` invocation produced by the per-method enhancer.
|===

=== Events

[cols="<,<,<"]
|===
|Span name |Kind |Description

|`EventSink.publish <eventName>` |`PRODUCER` |Short-lived per-event span opened while publishing through an `EventSink`. Propagates the tracing context onto the event's metadata.
|`EventProcessor.process <eventName>` |`CONSUMER` |The handler invocation by an event processor. For a streaming processor, it is a child of `StreamingEventProcessor.batch` and has a span link back to the publication trace (through the metadata-propagated context). If batch tracing is disabled, it starts a new trace with the same publisher link. Set `axon.tracing.event-processor.distributed-in-same-trace=true` to nest it under the publication trace instead. Carries the owning processor's name in the `axoniq.event-processor.name` attribute.
|`StreamingEventProcessor.batch` |`INTERNAL` |Root span enclosing one streaming-event-processor batch and its `EventProcessor.process` children; gated on the segment resource so subscribing processors don't produce it. Carries the owning processor's name in the `axoniq.event-processor.name` attribute.
|`<HandlerClass>.<method>(<EventClass>)` |`INTERNAL` |The annotated `@EventHandler` invocation produced by the per-method enhancer.
`@EventSourcingHandler` invocations are suppressed by default (they fire once per event during entity replay and would flood traces) and appear only with `axon.tracing.show-event-sourcing-handlers=true`.
|===

==== Streaming consumer trace topology

Streaming processors handle events asynchronously, possibly long after publication.
The guiding rule for their `EventProcessor.process` spans: the parent is the operation that structurally owns the execution, while the publisher is causal provenance carried on a span link.
Subscribing processors run inside the publisher's processing context and always continue its trace.

[cols="<,<,<"]
|===
|Configuration (streaming) |`EventProcessor.process` parent |Publisher relationship

|`disable-batch-trace=false`, `distributed-in-same-trace=false` (default) |`StreamingEventProcessor.batch` |Span link
|`disable-batch-trace=true`, `distributed-in-same-trace=false` |None; new trace root |Span link
|`distributed-in-same-trace=true`, event within the time limit |Publisher span (propagated metadata) |Parent
|`distributed-in-same-trace=true`, stale event (replay, catch-up) |None; new trace root |Span link
|===

Because the publisher is a link rather than a parent in both non-same-trace modes, an event handled long after publication starts a temporally coherent trace at processing time and never stretches the publisher's finished trace.
Same-trace mode is the only shape with that risk, so it is guarded per event by `axon.tracing.event-processor.distributed-in-same-trace-time-limit` (default `PT2M`): older events, typically replays or downtime catch-up, become linked trace roots instead.
In same-trace mode no batch span is opened at all, which makes `disable-batch-trace` irrelevant there.
Events that carry no propagated trace metadata simply get no link; the process span is still created and parented correctly.

=== Queries

[cols="<,<,<"]
|===
|Span name |Kind |Description

|`QueryBus.query <queryName>` |`PRODUCER` |The bus is dispatching a direct query.
|`QueryBus.subscriptionQuery <queryName>` |`PRODUCER` |The bus is dispatching a subscription query.
|`QueryBus.handleQuery <queryName>` |`CONSUMER` |The bus is handing the query to its handler.
|`QueryBus.emitUpdate` |`INTERNAL` |An update is being emitted to subscription queries.
|`QueryBus.completeSubscriptions` |`INTERNAL` |Matching subscription queries are completed.
|`QueryBus.completeSubscriptionsExceptionally` |`INTERNAL` |Matching subscription queries are completed exceptionally.
|`<HandlerClass>.<method>(<QueryClass>)` |`INTERNAL` |The annotated `@QueryHandler` invocation produced by the per-method enhancer.
|===

[NOTE]
====
In Axon Framework 5 `QueryUpdateEmitter` is a thin layer on top of `QueryBus` (its `emit` / `complete` / `completeExceptionally` calls delegate to the bus). Tracing the bus therefore also traces the emitter; no separate tracing surface is needed.
====

=== Event Sourcing

[cols="<,<,<"]
|===
|Span name |Kind |Description

|`EventStorageEngine.appendTransaction` |`INTERNAL` |The complete storage append transaction, from staging the events through commit and after-commit processing. Instrumented storage calls, such as Axon Server gRPC append or database writes, nest under this span.
|`SnapshotStore.store <name>` |`INTERNAL` |A snapshot is being persisted.

=== Distributed connectors

When the distributed messaging module is present, the transport leg between the bus-level dispatch and handle spans is traced as well:

[cols="<,<,<"]
|===
|Span name |Kind |Description

|`CommandBusConnector.dispatch <commandName>` |`PRODUCER` |The connector is sending the command over the transport (for example Axon Server). Child of `CommandBus.dispatchCommand`.
|`CommandBusConnector.handle <commandName>` |`CONSUMER` |The connector received the command on the handling node. Parent of `CommandBus.handleCommand`.
|`QueryBusConnector.query <queryName>` |`PRODUCER` |The connector is sending a direct query. The span stays open until the result stream terminates, so lazily consumed responses are timed.
|`QueryBusConnector.subscriptionQuery <queryName>` |`PRODUCER` |The connector is setting up a subscription query. Covers subscription setup only, not the unbounded update stream.
|`QueryBusConnector.handle <queryName>` |`CONSUMER` |The connector received the query on the handling node.
|`QueryBusConnector.queryUpdate <updateType>` |`PRODUCER` / `CONSUMER` |One producer span on the emitting node and one linked consumer span on the subscribing node per delivered update. The consumer span carries a span link back to the originating `QueryBus.subscriptionQuery`.
|===

== Context propagation

Axon Framework carries trace context through its `ProcessingContext` and message metadata rather than thread-locals, so parent/child relationships survive thread hops, asynchronous composition, and process boundaries.
A handler running on a different thread than its dispatcher, or in a different application entirely, still nests correctly under the dispatch span, for imperative and reactive call paths alike.

The Axoniq Framework Micrometer binding extends this to everything else in the application:

* **Instrumented libraries**: work performed inside a traced framework operation, such as Axon Server gRPC calls, JDBC statements, or WebClient requests instrumented by Micrometer or the OpenTelemetry agent, nests under the correct Axon span.
* **Log correlation**: MDC-based trace and span identifiers are correct on whichever thread framework work runs, so log lines written by handlers and framework internals link to the right span.
* **Reactor pipelines**: the binding registers a `ProcessingContext` accessor with Micrometer's context propagation, so Reactor's automatic context propagation carries the active Axon span across reactive operators; spans created inside a `Mono` or `Flux` chain keep the correct parent and MDC values.
* **Ambient fallback**: when neither the context nor message metadata yields a parent, framework work entered from an instrumented HTTP request joins that request's trace.

The worker-thread bridge behind the first two points can be disabled with `axon.tracing.thread-local-context-propagation.enabled=false`; span creation and message metadata propagation remain active without it.
See xref:tracing:opentelemetry.adoc[] for the mechanics.

== OpenTelemetry

Axoniq Framework integrates https://opentelemetry.io/docs/concepts/what-is-opentelemetry/[OpenTelemetry] through `axoniq-tracing-micrometer` and `micrometer-tracing-bridge-otel`.
Spring Boot configures the OpenTelemetry SDK, propagation, sampling, and exporters.
The OpenTelemetry Java instrumentation https://github.com/open-telemetry/opentelemetry-java-instrumentation/blob/main/docs/supported-libraries.md[covers many surrounding libraries], so traces started by an HTTP framework or messaging client outside Axon Framework continue through the Axon decorators seamlessly.

== Logging

For local development without an APM backend, the `LoggingSpanFactory` emits each span lifecycle event to SLF4J.
Use it as a standalone local-development backend.
Exporting spans to tracing backends is configured through Micrometer Tracing and its exporters.
