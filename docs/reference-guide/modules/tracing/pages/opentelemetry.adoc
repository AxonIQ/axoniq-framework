[.axoniq-feature]
= OpenTelemetry
:navtitle: OpenTelemetry

Axoniq Framework integrates OpenTelemetry through Micrometer Tracing, the same tracing facade used by Spring Boot.
`axoniq-tracing-micrometer` implements the Axon Framework `SpanFactory` against Micrometer's `Tracer` and `Propagator`.
The `micrometer-tracing-bridge-otel` bridge connects those APIs to the OpenTelemetry SDK.

== Dependencies

[source,xml]
----
<dependency>
    <groupId>io.axoniq.framework</groupId>
    <artifactId>axoniq-tracing-micrometer</artifactId>
    <version>${axoniq-framework.version}</version>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-otel</artifactId>
</dependency>
<dependency>
    <groupId>io.opentelemetry</groupId>
    <artifactId>opentelemetry-exporter-otlp</artifactId>
</dependency>
----

Spring Boot configures the OpenTelemetry SDK and exposes Micrometer `Tracer` and `Propagator` beans.
The Axoniq Framework binding discovers those beans as framework components and registers `MicrometerSpanFactory`.
When either component is absent, the binding backs off and no `SpanFactory` is registered.

== OTLP configuration

[source,yaml]
----
management:
  tracing:
    enabled: true
    sampling:
      probability: 1.0
  otlp:
    tracing:
      endpoint: http://localhost:4318/v1/traces
----

Production sampling and exporter settings should follow the application's observability requirements.

== Plain Java configuration

Outside Spring, construct the `Tracer` and `Propagator` through the selected Micrometer bridge and register them with the configurer:

[source,java]
----
MessagingConfigurer configurer = MessagingConfigurer.create()
        .componentRegistry(registry -> registry
                .registerComponent(Tracer.class, c -> tracer)
                .registerComponent(Propagator.class, c -> propagator));
----

The ServiceLoader-discovered enhancer creates `MicrometerSpanFactory` and supplies the attribute providers collected by `SpanAttributesProviderRegistry`.

== Cross-process propagation through message metadata

The binding injects the started dispatch span's trace context into the outgoing message's `Metadata` through the configured Micrometer `Propagator`.
With the OpenTelemetry bridge, the default propagation format is W3C `traceparent` and `tracestate`.
The receiving decorator extracts that metadata before creating its consumer span.

This mechanism is independent of the transport and thread.
It works for local asynchronous dispatch and for messages sent through Axon Server.

Parent selection is explicit:

* Dispatch spans prefer the active scope on the supplied `ProcessingContext`, then existing propagation metadata, then the ambient Micrometer trace context.
* Handler spans prefer propagation metadata, then the active scope, then the ambient context.
* Context-parent handler spans use the active `ProcessingContext` scope as their parent and add a link to propagation
  metadata. This is how a streaming consumer belongs structurally to its batch while preserving its causal relationship
  to the publisher without consulting ambient thread-locals.
* Root and disconnected-handler spans start a new trace and link to the triggering context when one is available.
* Linked-handler spans add a link to the second message's propagated W3C context.

Missing or invalid propagation metadata never prevents message handling.

== Automatic instrumentation and context propagation

The durable trace context lives on the `ProcessingContext`; a thread-local is only installed for the duration of an operation.
While a framework operation executes, the Micrometer implementation makes that operation's span the current span through `Tracer.withSpan` and restores the previous span afterwards.
The worker-thread bridge additionally restores the captured context snapshot and the correct Axon span around framework actions that run on worker threads.

This makes the current Axon span visible to instrumented JDBC, WebClient, and gRPC clients and to MDC logging, without using a thread-local as the durable carrier: a database call issued inside an event handler, or the Axon Server gRPC append inside the storage transaction, becomes a child of the correct Axon span automatically.

Reactive code is covered as well.
The binding registers a `ProcessingContext` accessor with Micrometer's `ContextRegistry`, so a `ContextSnapshot` captured from a `ProcessingContext` includes the active Axon span.
When enabled, Reactor's automatic context propagation restores it across reactive operators.
Spans created inside a `Mono` or `Flux` chain therefore keep the correct parent, and MDC log correlation stays intact through asynchronous boundaries.

With the worker-thread bridge enabled, Axoniq Framework registers the Micrometer context accessors, but the application must enable Reactor's automatic context propagation.
In a Spring Boot application, set `spring.reactor.context-propagation=auto`.
The default `limited` mode restores thread-locals only for the `handle` and `tap` operators.
Without Spring Boot, call `Hooks.enableAutomaticContextPropagation()` once during application startup, before reactive pipelines are subscribed.
In both cases, Reactor captures the current Axon span when the handler result is subscribed and restores it around operator callbacks after scheduler thread hops.

[source,yaml]
----
spring:
  reactor:
    context-propagation: auto
----

[source,java]
----
Hooks.enableAutomaticContextPropagation();
----

Disable only the worker-thread bridge with:

[source,yaml]
----
axon:
  tracing:
    thread-local-context-propagation:
      enabled: false
----

Message metadata propagation and Axon span creation remain enabled when the bridge is off.

OpenTelemetry's https://github.com/open-telemetry/opentelemetry-java-instrumentation/blob/main/docs/supported-libraries.md[Java instrumentation library] covers many surrounding libraries.
An HTTP server span created outside Axon Framework can become the lowest-precedence ambient parent of a framework dispatch span.

== Span kinds and links

[cols="<,<"]
|===
|`SpanFactory` method |OpenTelemetry result through the Micrometer bridge

|`createDispatchSpan` |`PRODUCER`
|`createHandlerSpan` |`CONSUMER`
|`createContextParentHandlerSpan` |`CONSUMER`, child of the active `ProcessingContext` scope with a link to the producer
|`createDisconnectedHandlerSpan` |`CONSUMER`, new trace with a link to the producer
|`createInternalSpan` |`INTERNAL`
|`createRootSpan` |`INTERNAL`, new trace with a link to the triggering context when present
|`createLinkedHandlerSpan` |`CONSUMER` with a link to a second message
|===

Span links require a W3C `traceparent` in message metadata.
The OpenTelemetry bridge exports those links to backends such as Jaeger.

== Log correlation

When Micrometer Tracing is active, Spring Boot includes the current trace and span identifiers in every log line by default.
Because the worker-thread bridge installs the active Axon span around framework actions, log statements written by message handlers and framework internals carry the identifiers of the span they belong to, on whichever thread the work runs.
Customise the format with the standard `logging.pattern.correlation` property.
