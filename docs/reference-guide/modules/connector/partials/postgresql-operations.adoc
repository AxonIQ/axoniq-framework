== PostgreSQL operations

=== Schema

By default, the `PostgresqlEventStorageEngine` checks whether its schema is complete on startup, and creates or repairs whatever is missing.
For production deployments, managing the schema through a migration tool such as Flyway or Liquibase gives you full control over schema changes across versions.

The complete DDL is as follows:

[source,sql]
----
CREATE TABLE IF NOT EXISTS events (
  global_index INT8        NOT NULL GENERATED BY DEFAULT AS IDENTITY (INCREMENT BY -1),
  timestamp    TIMESTAMPTZ NOT NULL,
  payload      BYTEA,
  metadata     JSON        NOT NULL,
  identifier   VARCHAR     NOT NULL,
  type         VARCHAR     NOT NULL,
  type_version VARCHAR     NOT NULL,
  PRIMARY KEY (global_index)
);

CREATE TABLE IF NOT EXISTS tags (
  global_index INT8    NOT NULL,
  key          VARCHAR NOT NULL,
  value        VARCHAR NOT NULL,
  PRIMARY KEY (key, value, global_index)
);

CREATE TABLE IF NOT EXISTS consistency_tags (
  tag_hash     INT4 NOT NULL,
  global_index INT8 NOT NULL,
  PRIMARY KEY (tag_hash)
);

CREATE SEQUENCE IF NOT EXISTS events_monotonic_seq
  INCREMENT BY 1
  CACHE 1
  OWNED BY events.global_index;

CREATE INDEX IF NOT EXISTS consistency_tags_global_index_idx
  ON consistency_tags (global_index);

CREATE INDEX IF NOT EXISTS tags_global_index_idx
  ON tags (global_index);

CREATE UNIQUE INDEX IF NOT EXISTS tags_type_unique
  ON tags (global_index) WHERE key = '__T';
----

The `events` table is the main event log; `payload` holds the serialized event as bytes, `metadata` is stored as JSON, and `type`/`type_version` together form the event's message type.
The `tags` table associates DCB tags with events.
The `consistency_tags` table is a bounded conflict-detection structure used when appending events with consistency requirements; it does not grow with event volume.

[NOTE]
.Table and sequence names are fixed
====
Table and sequence names cannot be configured.
All tables and sequences use the fixed names shown above.
====

=== Controlling schema initialization

The engine's schema handling is controlled by a `SchemaInitialization` value, passed as an optional constructor argument (or, in Spring Boot, through the `axon.postgresql.schema-initialization` property):

* `CREATE_IF_MISSING` (the default)—creates or repairs any missing tables, indices, or migrations.
* `VALIDATE`—checks that the schema is complete and fails startup with an exception if it is not, without creating or changing anything.
* `SKIP`—skips the check entirely, trusting that the schema is already complete and correct. This option is not recommended: see the warning below.

[source,java]
----
new PostgresqlEventStorageEngine(dataSource, converter, SchemaInitialization.VALIDATE)
----

[WARNING]
.Writing to an incomplete schema can corrupt data
====
Appending events against a schema that is missing part of an internal migration can silently produce corrupted or incomplete data that is hard to recover from.
`SKIP` is not recommended: because it performs no check at all, this failure mode is silent even when it is the schema, not the deployment process, that is actually out of date.
Prefer `VALIDATE` when the schema is managed independently (for example through Flyway or Liquibase)—it gives the same fast, lock-free startup without that blind spot, since an incomplete schema still fails startup with a clear exception instead of corrupting data later.
====

=== Connection pool sizing

The engine holds one dedicated connection open for the lifetime of the application to receive event arrival notifications from other instances.
When sizing your connection pool, add one to whatever your application otherwise requires.

=== Multi-instance coordination

Multiple instances sharing the same PostgreSQL database coordinate automatically.
Events appended by any instance are immediately visible to all other instances with no polling delay.
A new instance determines the current event position immediately on startup: it subscribes to notifications before running an initial position query, so no events can be missed between the two steps.
If the monitoring connection is lost, the engine reconnects and re-establishes the current position automatically.
