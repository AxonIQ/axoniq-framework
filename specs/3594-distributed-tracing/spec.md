# Feature Specification: Distributed Tracing Support

**GitHub Issue**: [#3594](https://github.com/AxonIQ/AxonFramework/issues/3594)

**Feature Branch**: `feat/3594-DistributedTracing`

**Spec Directory**: `specs/3594-distributed-tracing`

**Created**: 2026-05-26

**Status**: Draft

**Input**: Port distributed tracing support from Axon Framework 4 — which is the only place a working implementation currently exists — into AxoniqFramework, using Axon Framework 5 idioms (`DecoratorDefinition`, `ConfigurationEnhancer`) and avoiding the proliferation of bus/component-specific span factory specializations. The tracing source files in upstream Axon Framework 5 are **not** a working or half-working implementation — they were merely relocated into new package layouts (and, where required, commented out) to keep the AF5 build green; they are dead code and are not a viable starting point. Includes Spring Boot auto-configuration, an OpenTelemetry integration module, reference-guide documentation, and a final clean-up phase removing all of those dead tracing files from the upstream Axon Framework 5 repository.

## Clarifications

### Session 2026-05-27

- Q: The tracing decorators initially leaned on OpenTelemetry's thread-local `Context.current()` / `makeCurrent()` for in-process parent/child. Is that acceptable, and is `io.opentelemetry.context.Context` itself a problem? → A: **No ThreadLocal, ever — but the `Context` object is fine.** The constitution forbids ThreadLocal in framework code; only the *static ambient accessors* `Context.current()` / `Context.makeCurrent()` (and the default thread-local `ContextStorage`) are the problem — the `io.opentelemetry.context.Context` **value object** is an explicit immutable carrier and is exactly the right tool. This is confirmed by the OpenTelemetry-Java maintainers: *"all of the OpenTelemetry Java APIs allow you to pass in `Context` explicitly (so that you don't need to use ThreadLocals)"* and *"the OpenTelemetry SDK never calls `Context.makeCurrent()`, making thread locals entirely opt-in by users"* ([discussion #6584](https://github.com/open-telemetry/opentelemetry-java/discussions/6584)); the recommended reactive / non-thread-per-request pattern is to carry the `Context` value in a request-scoped carrier and pass it to `spanBuilder.setParent(context)` ([context-propagation docs](https://opentelemetry.io/docs/concepts/context-propagation/), [#2884](https://github.com/open-telemetry/opentelemetry-java/discussions/2884)). **AF5's `ProcessingContext` is exactly that scoped carrier**, so the redesign stores the active OTel `Context` as a `ProcessingContext` resource and resolves parents from it — never from `Context.current()`. Concrete API consequences (all landed): (1) **B** — `createInternalSpan` gains a `@Nullable ProcessingContext` so internal spans nest via the context resource; (2) **C** — new `createRootSpan(String, @Nullable ProcessingContext)` forces a new trace for batch/snapshot boundaries on pooled threads; (3) `propagateContext` moved off `SpanFactory` onto `Span` (a span injects its own context — a factory can't find "which span" without a thread-local); (4) `Span.start()` records the span's `Context` as the context's active span and restores the previous on close, instead of `makeCurrent()`; (5) `MetadataContextPropagator.inject()` takes a `ProcessingContext`. Validated end-to-end: an OTel unit test proves a child span nests under its parent purely through the `ProcessingContext` resource (no thread-local), and the command-bus slice parents the handler span under the dispatch span via message metadata. See `contracts/public-api.md` §1.1–1.2 and `plan.md` Constitution Check (§V).
- Q: AF4's command/query reference-guide span kinds were documented here as `CLIENT`/`SERVER`. What kinds does the implementation actually use? → A: **AF4's real OpenTelemetry binding uses `PRODUCER` (dispatch), `CONSUMER` (handler), and `INTERNAL` (internal/root) — not `CLIENT`/`SERVER`** (verified in `AxonFramework4` `tracing-opentelemetry/.../OpenTelemetrySpanFactory.java`: `createDispatchSpan`→`PRODUCER`, `createHandlerSpan`→`CONSUMER`, `createInternalSpan`/`createRootTrace`→`INTERNAL`). The new module follows AF4 exactly. The `CLIENT`/`SERVER` wording previously in `quickstart.md`, `af4-span-inventory.md` §1, `research.md`, and `plan.md` P3 was inaccurate and has been corrected to `PRODUCER`/`CONSUMER`. (The general enumerations that list all five kinds — including `CLIENT`/`SERVER` — are left intact, since a future distributed transport may legitimately use them.) **One nuance preserved from AF4:** the command/query *dispatch* span was `INTERNAL` for the in-process leg (`DefaultCommandBusSpanFactory` called `createInternalSpan`) and `PRODUCER` for the distributed leg (`createDispatchSpan`); the consolidated `TracingCommandBus` emits `PRODUCER` for both until distributed/in-process branching is added when the distributed command bus is wired.
- Q: AF4 used flat-underscore span attribute keys (`axon_message_name`, `axon_payload_type`, …). The implementation uses dotted `axoniq.*` keys instead — which convention should the feature follow? → A: **Option B — OpenTelemetry-style dotted namespaces with the `axoniq.` prefix** (`axoniq.message.id`, `axoniq.message.name`, `axoniq.message.type`, `axoniq.message.payload_type`, `axoniq.metadata.<key>`, `axoniq.aggregate.identifier`). Rationale: OpenTelemetry's [attribute-naming convention](https://opentelemetry.io/docs/specs/semconv/general/naming/) uses dot-separated namespaces (lowercase, snake_case leaf segments, e.g. `messaging.message.id`, `http.response.status_code`); AF4's flat underscore keys predate/ignore it, and the `axoniq.` prefix matches the new `io.axoniq.framework` group. The leaf `payloadType` was corrected to `payload_type` for snake_case consistency. **Each built-in provider exposes a constructor that overrides its attribute key** (for `MetadataSpanAttributesProvider`, the prefix), so the exact AF4 keys can be restored for drop-in dashboard compatibility — e.g. `new MessageNameSpanAttributesProvider("axon_message_name")`. **Deferred future improvement — Option C:** map onto OpenTelemetry's official messaging *semantic conventions* (`messaging.message.id`, `messaging.message.conversation_id`, `messaging.operation.name`, …) where they exist, keeping `axoniq.*` only for Axon-specific attributes; most standards-aligned but most divergent from AF4. Addable later without breaking changes (just different default keys behind the same providers). See `contracts/public-api.md` §1.7.
- Q: Can the per-method handler-enhancer span (`TracingHandlerEnhancerDefinition`) be auto-wired in AF5 the way AF4 did it, and should it land in slice 1? → A: **It can be wired, but not via AF4's mechanism, and it is deferred to slice 2 (the `@EventHandler` slice).** AF5 has **no** config-aware handler-enhancer registration API (no equivalent of AF4 `Configurer.registerHandlerEnhancerDefinition(Function<Configuration, HandlerEnhancerDefinition>)`). In AF5, handler enhancers are applied only through a `HandlerDefinition` (`MultiHandlerDefinition` bundles a `HandlerEnhancerDefinition`), and annotated handling components pick it up via `c.getOptionalComponent(HandlerDefinition.class).orElse(ClasspathHandlerDefinition.forClass(...))` (`CommandHandlingModule:202`, `QueryHandlingModule:204`, `EventHandlingComponentsConfigurer:107/130`); the default enhancer source is ServiceLoader-only (no-arg constructors), so a no-arg enhancer cannot receive the configured `SpanFactory`. The only seam is to register a `HandlerDefinition` **component** that bundles a `SpanFactory`-bearing `TracingHandlerEnhancerDefinition` on top of the AF5 defaults — a single **global** slot shared by command/query/event handling. Because that wiring is global and is first genuinely exercised through the live annotation pipeline in slice 2, it is introduced and validated **once** there (plan.md P4.3a + appendix "Handler-enhancer auto-wiring in AF5"). `TracingHandlerEnhancerDefinition` with `@CommandHandler` coverage is implemented + unit-tested in slice 1; only its auto-wiring moves. **When the slice-2 wiring lands it retroactively activates the per-method span for `@CommandHandler` as well as `@EventHandler`** (the enhancer self-gates per message type), so slice 2 re-verifies the `@CommandHandler` per-method span. Limitations (global slot, collision with a user-supplied `HandlerDefinition`, reconstruction fragility) and the proposed mitigations are recorded in plan.md's appendix; an upstream AF5 request for a first-class config-aware enhancer hook is a candidate follow-up (track with the P10 upstream work).

### Session 2026-05-26

- Q: What is the actual state of tracing in upstream Axon Framework 5? → A: Not half-migrated. Files were moved into new package layouts and code was commented out (or otherwise neutralised) just enough to keep AF5 compiling. The AF5 tracing source is dead code: no wiring, no functional behavior, no working autoconfig. AF4 is the only repository with a working implementation, so the port reads from AF4 — AF5 tracing source is treated as scrap to be deleted in the cleanup phase, not as a baseline to build on.
- Q: How should Story 4 / FR-016 consolidate per-bus and per-component span factories? → A: Option A — single generic `SpanFactory` plus **private** per-component `DecoratorDefinition`s registered by one `TracingConfigurationEnhancer`. Per-component span naming, attributes, span kinds (`CLIENT`/`SERVER`/`PRODUCER`/`CONSUMER`/`INTERNAL`), and cross-process metadata-based context propagation all live inside those internal decorators. No per-bus / per-component span-factory interface is part of the public API. Option B (exposing a small public helper SPI — e.g., `SpanNames`, `OperationKinds`, `MetadataContextPropagator` — so advanced users can author their own decorators with identical span shapes) is acknowledged as a **deferred future improvement**, not in scope for this feature; it can be added later without breaking changes by graduating selected internals to public API.
- Q: What is the module structure in AxoniqFramework for the new tracing code? → A: *(**SUPERSEDED 2026-05-26** by the five-module clarification later in this session — the two-module answer below is retained as the dated record; the current structure is `axoniq-tracing-api` + `-messaging` + `-modelling` + `-eventsourcing` + `-opentelemetry`.)* **Two flat sibling modules under a new top-level `tracing/` directory** (mirroring the existing per-concern top-level convention used by `messaging/`, `connector/`, `dependency-injection/`, `testing/`): `tracing/axoniq-tracing-core` (artifact `axoniq-tracing-core`, group `io.axoniq.framework`) and `tracing/axoniq-tracing-opentelemetry` (artifact `axoniq-tracing-opentelemetry`). The core module holds the public abstractions and the private per-component `DecoratorDefinition`s; the OpenTelemetry module holds `OpenTelemetrySpanFactory` and the metadata text-map propagators. Tracing is **not** placed under `messaging/` — it is a cross-cutting concern that legitimately depends on messaging, modelling, and event sourcing (e.g., `TracingHandlerEnhancerDefinition` wraps any handler including `@EventSourcingHandler`, plus repository load/save and snapshot create/read). Spring Boot auto-configuration classes are added to the **existing** `dependency-injection/spring/spring-boot-autoconfigure` module (artifact `axoniq-spring-boot-autoconfigure`); no separate spring-tracing module is created.
- Q: How are the per-component tracing wrappers implemented — what pattern and what hook strategy? → A: **Delegating decorators**, following AF5's `TracingCommandBus` / `InterceptingCommandBus` / `InterceptingQueryBus` pattern: each tracing wrapper class implements the target component interface (`CommandBus`, `EventBus`, `QueryBus`, `QueryUpdateEmitter`, `EventHandlingComponent`, `Repository`, `Snapshotter`, etc.) **by composition** — holding a `delegate` reference plus the generic `SpanFactory`, calling through to the delegate, and declaring itself a wrapper via `ComponentDescriptor.describeWrapperOf(delegate)`. Wrappers are registered through `DecoratorDefinition` so they stack cleanly with other decorators (interception, metrics, distributed transport, security). This **explicitly rejects** the AF4 anti-pattern where classes such as `DistributedCommandBus` directly implemented the bus interface without delegation, making it impossible to compose additional concerns without forking. Where the wrapped operation already participates in a `ProcessingContext` (e.g., the AF5 `CommandBus#dispatch(message, ProcessingContext)` signature), span open/close **SHOULD** ride on `ProcessingContext` lifecycle callbacks rather than try/finally / `runSupplier` blocks — so span scope aligns with the framework's lifecycle phases and survives async boundaries naturally. When no `ProcessingContext` is available at the relevant hook point, falling back to a direct `Span.run...` style is acceptable.
- Q: Should deadline scheduling / firing be traced? → A: **No.** `DeadlineManager` is not part of Axon Framework 5 — it never carried over from AF4, so there is no component to wrap. Tracing deadlines is permanently out of scope for this feature. Specifically: no `TracingDeadlineManager` wrapper, no `ifClassPresent("org.axonframework.deadline.DeadlineManager", …)` guard in `TracingConfigurationEnhancer`, no `DeadlineManagerOptions` in `TracingProperties`, no `deadlines` toggle, no deadline-specific edge cases, and no deadline mention in user-facing scenarios. If a deadlines port ever lands in AxonFramework 5 in the future, tracing for it is a pure addition (new `DecoratorDefinition`) — not a regression of this spec.
- Q: Should saga / process-manager invocation be traced? → A: **No.** Same status as deadlines — out of scope for this feature. Reason: sagas / process-managers are not part of Axon Framework 5 today (their AF4 implementations did not carry forward, and no AF5 port currently exists in either AxonFramework or AxoniqFramework). There is no component to wrap. Specifically: no `TracingSagaManager` wrapper, no `SagaManagerOptions` in `TracingProperties`, no `sagas` toggle in `ComponentToggles`, no saga-specific edge cases, no `@SagaEventHandler` wrapping in `TracingHandlerEnhancerDefinition`, and no saga mention in user-facing scenarios. If a saga / process-manager port ever lands in AxonFramework 5 or AxoniqFramework, tracing for it is a pure addition (new `DecoratorDefinition` registered by the existing `TracingConfigurationEnhancer`) — not a regression of this spec. FR-012 is withdrawn; the `*SagaManagerSpanFactory` forbid-list entry in FR-016 stays as a defensive guard.
- Q: How does `SpanAttributesProvider` interact with snapshot spans (and other non-Message internal spans)? Are providers invoked for them? → A: **No — providers do not fire on non-Message internal spans, and they do not need to.** The factory only iterates `SpanAttributesProvider`s on the Message-aware methods (`createDispatchSpan`, `createHandlerSpan`). `createInternalSpan(String)` skips provider iteration; the calling decorator (`TracingSnapshotter`, `TracingRepository`, etc.) attaches whatever attributes it needs via `Span#addAttribute(key, value)` from its own typed method parameters. This matches AF4's behavior — AF4's `SpanAttributesProvider#provideForMessage(Message)` was Message-only too; snapshot/repository attributes came from bespoke per-component factory methods, which we replace with local `addAttribute` calls inside our decorators. Concrete worked sequence diagrams (mermaid) for command dispatch, async event publication + handling with cross-thread W3C propagation, and snapshot creation are documented in [`flows.md`](./flows.md), including a "When does my `SpanAttributesProvider` fire?" cheat sheet. If a future need arises for providers to contribute to internal spans (e.g., a tenant-id provider that wants to attach `axoniq.tenant.id` to snapshot spans too), the response is a pure-addition extension — a new `createInternalSpan(String, ProcessingContext)` overload — not a redesign of the current SPI. Out of scope today.
- Q: Is `SpanAttributesProvider#provideForSubject(Object)` (plus the matching `SpanFactory.createInternalSpan(String, Object)` overload) actually needed? It was not present in AxonFramework 4, and snapshots being non-Message in AF5 was the reason given. → A: **No — remove both.** The "subject" indirection is a premature abstraction. Every operation that needs to contribute attributes to a non-Message span already has the relevant data either (a) as a local parameter on the decorator method itself (e.g., `TracingSnapshotter` knows the entity type and identifier; `TracingRepository` knows the entity id), in which case the decorator calls `Span#addAttribute(key, value)` directly with no SPI plumbing, or (b) on the surrounding `ProcessingContext` as a `LegacyResources` resource (per the previous clarification on aggregate-identifier sourcing), in which case `AggregateIdentifierSpanAttributesProvider` picks it up automatically through the standard message/context path. The `Object subject` parameter forces every `SpanAttributesProvider` to `instanceof`-switch on opaque types and serves no concrete use case in this feature's scope. AF4 did not have it (per-component span factories had bespoke typed methods instead). Conclusion: `SpanFactory` exposes a single `createInternalSpan(String operationName)`; `SpanAttributesProvider` exposes a single method `provideForMessage(Message<?>, @Nullable ProcessingContext)`. Snapshot-not-being-a-Message is **not** a design problem — the decorator owns the attribute attachment locally for the non-Message case. If a future need for a generic subject parameter ever emerges, it is a pure-addition extension at that time (Constitution §VIII open-for-extension), not a speculative shape today.
- Q: How does the new tracing module source the aggregate identifier now that AF5 has replaced AF4's `Aggregate` model with `Entity` / DCB (`@EventSourcedEntity(tagKey = …)` + `@EventTag`) and **completely removed** `DomainEventMessage`? → A: **From `ProcessingContext` via `LegacyResources`**, best-effort. The new `AggregateIdentifierSpanAttributesProvider` MUST NOT reference `DomainEventMessage` (forbidden — see constitution v2.1.0 §"Relationship to AxonFramework Upstream"). It reads `ProcessingContext.getResource(org.axonframework.messaging.core.LegacyResources.AGGREGATE_IDENTIFIER_KEY)`, mirroring the AF5 pattern used by `AggregateTypeParameterResolverFactory` (`messaging/.../core/annotation/AggregateTypeParameterResolverFactory.java`) and `SourceIdParameterResolverFactory`. Three follow-on consequences: **(1)** the `SpanAttributesProvider` SPI gets `ProcessingContext` as a second parameter — its single method becomes `Map<String, String> provideForMessage(Message<?> message, @Nullable ProcessingContext context)`; providers that don't need the context simply ignore it. **(2)** `SpanFactory.createDispatchSpan` / `createHandlerSpan` gain an additional `@Nullable ProcessingContext` parameter that decorators pass through (they already hold a `ProcessingContext` from the AF5 bus signatures). **(3)** The `axoniq.aggregate.identifier` attribute is **best-effort**: it appears on spans whose surrounding operation is on a legacy aggregate-based event stream (`AggregateBasedJpaEventStorageEngine`, etc.) and is intentionally absent on DCB/entity-based operations — the entity's identity flows through `@EventTag` keys on the events themselves. This is not a regression of AF4 fidelity; it is the correct AF5 model. A future `EntityTagSpanAttributesProvider` for the DCB path is a deferred future improvement, not in scope for this feature.
- Q: Can the decorator approach reproduce AF4 `AbstractEventBus`'s **two** event-publication spans (per-event `createPublishEventSpan` + UoW-scoped `createCommitEventsSpan`) without diving into the AF5 event-bus implementation? → A: **Yes.** `TracingEventSink` (the decorator wrapping `EventSink#publish(ProcessingContext, List<EventMessage>)`) MUST produce both spans from the method parameters alone — no access to bus internals required. Specifically: (1) for every event in the `events` list, open a short-lived **publish-event span** synchronously around `SpanFactory#propagateContext(event)` BEFORE calling `delegate.publish(...)`, mirroring `AbstractEventBus.java:121-122`; (2) bind a single **commit-events span** to the supplied `ProcessingContext` via `ProcessingContextSpanBinding` — open in `runOnPrepareCommit`, mark errored in `onError`, close in `whenComplete` — mirroring `AbstractEventBus.java:160-202` (which hooks the equivalent UoW phases). When `ProcessingContext` is `null` (no surrounding processing context), the commit-events span falls back to a synchronous `Span.run(...)` wrapper around `delegate.publish(...)`, mirroring the no-UoW path at `AbstractEventBus.java:144`. This pattern relies only on what is already part of the public `EventSink#publish` signature (the events list + the `ProcessingContext`), so the decorator does not need to know about, peek at, or replicate any internals of `SimpleEventBus` / `AbstractEventBus` / event staging / interceptor application. The same two-span pattern is the **default** template for any future component decorator whose AF4 counterpart opened both a per-message dispatch span and a UoW-scoped commit span.
- Q: How is `TracingEventHandlingComponent` scoped during `DecoratorDefinition` registration so that both `PooledStreamingEventProcessor` and `SubscribingEventProcessor` are covered without inventing a separate enhancer per processor type? → A: **Guard on the common `EventProcessorConfiguration` base class** (which both `SubscribingEventProcessorConfiguration` and `PooledStreamingEventProcessorConfiguration` extend). One `DecoratorDefinition.forType(EventHandlingComponent.class)` registration with a single `cfg.getOptionalComponent(EventProcessorConfiguration.class).isPresent()` guard covers both processor types and any future `EventProcessor` impl that adopts the common configuration base — no enhancer code changes needed when new processor types are added. This is broader than the DLQ enhancer's PSEP-only scope because tracing semantics legitimately apply to all event handling, not just pooled-streaming.
- Q: Has every AF4 `*SpanFactory` interface + method been verified to have an AF5 replacement in this spec (excluding deadlines and sagas)? Where is the full enumeration kept so an implementer doesn't miss a multi-span pattern (e.g., `QueryUpdateEmitter.emit` two-span schedule+emit, `Snapshotter` schedule+create, `Repository.load` outer + `obtainLock` + `initializeState` inner)? → A: **Yes — verified by an exhaustive audit recorded in [`af4-span-inventory.md`](./af4-span-inventory.md).** The audit covers 9 AF4 `SpanFactory` families (1 generic + 8 per-component) and 44 factory methods total, cross-referenced against every production caller in `AxonFramework4/messaging/`, `modelling/`, `eventsourcing/`, and `axon-server-connector/` source. Every method maps to an AF5 decorator + named span; multi-span patterns are explicitly enumerated. Every span name in the AF4 reference guide's "Traced components" section (`tracing.adoc:497-744`) is mapped to a row in the audit. Only `DeadlineManagerSpanFactory` (6 callers across `SimpleDeadlineManager` / `QuartzDeadlineManager` / `DbSchedulerDeadlineManager` / `JobRunrDeadlineManager` / `DeadlineJob` / distributed bridge) and `@SagaEventHandler` annotation handling remain unmapped — both intentionally out of scope (clarifications 2026-05-26) because the corresponding components do not exist in Axon Framework 5. Implementation MUST consult [`af4-span-inventory.md`](./af4-span-inventory.md) when building any `Tracing*` decorator and SHOULD include an integration test (`AF4SpanShapeParityIntegrationTest`) asserting span names + kinds for every entry in the inventory's §2 reference-guide cross-check table, so Story 4 acceptance criterion 3 ("the consolidation does not regress the observable trace shape") is verifiable rather than aspirational.
- Q: AF4's `SpanFactory` interface declares 9 methods; the AF5 plan exposes fewer. Is this consolidation OK, and what's the justification for each difference? → A: **Yes — consolidation is intentional, and one method was added back to close a real semantic gap.** Audit of every AF4 `SpanFactory` production caller (`AxonFramework4/messaging/`, `modelling/`, `eventsourcing/`, `axon-server-connector/`): (1) **`createRootTrace(Supplier<String>)` removed** — 2 production callers (`DefaultEventProcessorSpanFactory:83` batch root, `DefaultSnapshotterSpanFactory:63` snapshot scheduling); both replaced by `createInternalSpan(String)` opened at the imperative edge with no active OTel context, which the SDK naturally promotes to a root. Same trace shape, no semantic loss. (2) **`createLinkedHandlerSpan` / `createChildHandlerSpan` defaults removed**; **`boolean isChildTrace` removed from `createHandlerSpan`** — linked-vs-child decision moves from a per-call boolean to the existing `TracingProperties.eventProcessor.distributedInSameTrace` + `distributedInSameTraceTimeLimit` heuristic that AF4 already exposed at config level. Same observable behaviour, smaller surface area. (3) **`Message... linkedSiblings` varargs on `createDispatchSpan` removed** — zero non-empty production callers in AF4. No semantic loss. (4) **`createInternalSpan(Supplier<String>, Message)` overload removed** — 6 callers in `DefaultQueryBusSpanFactory` and `DefaultQueryUpdateEmitterSpanFactory`. Replaced by `createInternalSpan(String)` + decorator-attached attributes via `Span.addAttribute(...)` from local parameters (consistent with the snapshot / repository pattern already in the spec). Same observable attributes, no semantic loss. (5) **`Supplier<String>` → eager `String`** for span names — minor, the no-op factory still inlines (no measurable cost at the call site). (6) **`@Nullable ProcessingContext context` parameter added** — net new for AF5's context-aware attribute providers (e.g., `AggregateIdentifierSpanAttributesProvider` reading `LegacyResources.AGGREGATE_IDENTIFIER_KEY`). **The one real gap restored**: AF4's `Message... linkedParents` varargs on `createHandlerSpan` had exactly **one** production caller — `DefaultQueryBusSpanFactory:66`: `createChildHandlerSpan(() -> "QueryBus.queryUpdate", updateMessage, queryMessage)` — which links a subscription-query update span back to its originating query via an OTel SpanLink (clickable navigation in APM UIs). To preserve that behaviour without restoring over-broad varargs (option A) or losing OTel-native linking (option C), the AF5 `SpanFactory` gains a **narrow, purpose-built** method: `createLinkedHandlerSpan(String operationName, Message<?> message, Message<?> linkedMessage, @Nullable ProcessingContext context)` (option B). One named method, one named use case. The implementation MUST use an OTel `SpanLink` (not a parent-of relationship and not an attribute) so APM UIs render it as a clickable cross-trace navigation, matching AF4 trace shape. **Final AF5 `SpanFactory` shape**: 6 public methods — `createDispatchSpan`, `createHandlerSpan`, `createLinkedHandlerSpan` (new in this clarification), `createInternalSpan`, `propagateContext`, `registerAttributesProvider`. The net 9→6 reduction is purely consolidation (boolean overload, two default convenience methods, `Supplier<String>` wrapper, and unused varargs collapsed into config-driven or decorator-attached behaviour), not capability loss. Full per-method diff with per-row justification is recorded in [`af4-span-inventory.md`](./af4-span-inventory.md) §0.
- Q: With the common-base scope, does `SubscribingEventProcessor` get a batch root span, like `PooledStreamingEventProcessor` does via `Segment.RESOURCE_KEY`? → A: **No — and this is intentional AF4 parity.** AF4's `DefaultEventProcessorSpanFactory.createBatchSpan(boolean streaming, …)` returns `NoOpSpan.INSTANCE` when `!streaming` (line 82-84 of the AF5 dead-code copy at `messaging/.../tracing/DefaultEventProcessorSpanFactory.java`, identical to AF4). The AF4 reference guide explicitly documents this at `docs/old-reference-guide/modules/monitoring/pages/tracing.adoc:193-195`: subscribing event processors produce no batch span — per-event spans become "Child of the publishing span (synchronous invocation)" because the handler runs inside the publisher's unit of work. The AF5 mapping reproduces this exactly with zero special-casing: `SubscribingEventProcessor` does not write `Segment.RESOURCE_KEY` to the ctx (only `WorkPackage.processBatch` does), so `TracingEventHandlingComponent.openBatchSpan` falls through to `NoOpSpan.INSTANCE`. Per-event spans still open and parent themselves to whatever surrounds the call — the publisher's `ProcessingContext` when `SubscribingEventProcessor.process(events, context)` reuses it (`SubscribingEventProcessor.java:145-146`), or a fresh trace when `context == null` (line 148). Rationale for keeping AF4's design: (1) the publisher's existing `EventBus.commitEvents` span already groups the events at the UoW boundary, so a separate `SubscribingEventProcessor.batch` would be a redundant wrapper around an empty boundary; (2) Story 4's acceptance criterion 3 explicitly requires "span names, kinds, and attributes are equivalent … the consolidation does not regress the observable trace shape" — introducing a new batch span here is a regression in the other direction. A future deviation is a pure-addition extension (a new `axon.tracing.eventProcessor.subscribingBatchTrace` toggle plus a second sentinel resource key) — not in scope for this feature.
- Q: Should implementation proceed layer-by-layer (P3 = all decorators built together) or component-by-component as end-to-end vertical slices, and in what order? → A: **Component-by-component vertical slices.** Order: (1) `TracingCommandBus` + `@CommandHandler` enhancement, (2) `TracingEventSink` + `TracingEventHandlingComponent` + `@EventHandler` enhancement, (3) `TracingQueryBus` + `@QueryHandler` enhancement, (4) `TracingQueryUpdateEmitter`, (5) `TracingRepository` / `TracingStateManager`, (6) `TracingSnapshotter` + `@EventSourcingHandler` enhancement. Core abstractions (`SpanFactory`, `Span`, `SpanScope`, `SpanAttributesProvider`, `NoOp`/`Multi`/`Logging` factories, the six built-in attribute providers, `ProcessingContextSpanBinding`) remain built up-front in a single core-abstractions phase preceding slice 1 — "try to do core abstractions properly during first run"; modifying them mid-stream when a later slice exposes a real gap is permitted but MUST be flagged to the user before being committed. This replaces the original plan's P3 (all decorators in one phase) with six sequenced slices; the rest of the plan (P1 foundations, P2 core abstractions, P4 OpenTelemetry module, P5 Spring Boot autoconfig, P6 end-to-end + propagation tests, P7 example, P8 docs, P9 upstream cleanup) is preserved — slices interleave with P4 / P5 work where appropriate (autoconfig grows incrementally per slice). See FR-022b for the binding requirement.
- Q: What is the scope of each component vertical slice — what work moves into the slice vs. what gets batched at the end? → A: **Medium slice.** Each slice contains: the `Tracing*` decorator under `internal/`, the corresponding `TracingHandlerEnhancerDefinition` extension for that slice's annotation type (if applicable), unit tests for the decorator and the handler-enhancer addition, an autoconfig toggle on `TracingProperties` for that component group, the `TracingConfigurationEnhancer` registration entry for that decorator's `DecoratorDefinition`, and **one focused integration test** exercising that single component end-to-end through Spring Boot with an `InMemorySpanExporter` (asserting span name + kind + attributes + parent-child links produced by the slice's component in isolation). Batched at the end (after all six slices are validated): the reference-guide docs (FR-025 / FR-026 — moved to the final phase to avoid rewriting the same page six times), the cross-component end-to-end integration test covering command → event → query (FR-023), the testcontainers/Jaeger integration test (FR-023a), the example-application wiring (FR-027), and the upstream AxonFramework 5 cleanup (FR-028 / FR-029 / P9).
- Q: Which backend should the integration tests use — `InMemorySpanExporter` only, or `InMemorySpanExporter` plus a testcontainers-based real-backend run? → A: **Both, in two steps with an explicit human gate between them.** Step 1: the cross-component end-to-end test under FR-023 uses `InMemorySpanExporter` only (fast, no Docker dependency); after it passes the implementer presents the asserted span tree to the user for explicit approval. Step 2: only after that approval, add `TracingJaegerIntegrationTest` under FR-023a — a testcontainers-based test that runs the same command → event → query flow against `jaegertracing/all-in-one` (OTLP receiver + JSON query API), exporting spans via the OpenTelemetry OTLP exporter and asserting the same span tree shape by querying Jaeger's REST API. This second test runs in the `integration-test` Maven profile and is skipped automatically on environments without Docker (Testcontainers `@EnabledIfDockerAvailable` or equivalent).
- Q: How is `TracingHandlerEnhancerDefinition` sliced across components? → A: **Folded incrementally into each component slice as that component's annotation type comes online**, not built monolithically. Slice 1 (`TracingCommandBus`) introduces `TracingHandlerEnhancerDefinition` with `@CommandHandler` coverage; slice 2 (`TracingEventSink` / `TracingEventHandlingComponent`) extends it to cover `@EventHandler`; slice 3 (`TracingQueryBus`) extends it to cover `@QueryHandler`; slice 6 (`TracingSnapshotter`) extends it to cover `@EventSourcingHandler`. There is **no** standalone "annotation tracing" phase. Each extension lands together with its component slice's tests, so the slice is genuinely end-to-end for that component (a Boot app with `@CommandHandler` methods produces a full bus-span + annotated-handler-span trace after slice 1, without waiting for any later slice).
- Q: How is the per-component validation checkpoint between slices enforced? → A: **One feature branch (`feat/3594-DistributedTracing`), sequential commits per slice, explicit "STOP — request human validation" checkpoint task in `tasks.md` after each slice.** No separate PR per slice — one final PR rolls up all six slices plus the batched final phase. After each slice the implementer: (1) commits the slice's changes, (2) runs the slice's focused `InMemorySpanExporter` integration test, (3) posts the resulting span tree shape (names, kinds, attributes, parent-child structure) to the user in the conversation, (4) waits for explicit go/no-go from the user before starting the next slice. The `tasks.md` document MUST encode each checkpoint as a discrete task (e.g., "Slice 1 — human validation gate: post span tree, wait for go/no-go") that downstream task-executor agents respect.
- Q: How are AF4's nested batch + per-event spans (`createBatchSpan` wrapping `createProcessEventSpan` in `AbstractEventProcessor.processInUnitOfWork`) reproduced in AF5 without inventing a new public per-component span-factory interface, and **without** any upstream change to AxonFramework 5? → A: **`TracingEventHandlingComponent` lazy-opens the batch span on the shared `ProcessingContext`** (Option C). The same `DecoratorDefinition.forType(EventHandlingComponent.class)` decorator that opens the per-event span also opens the batch span lazily via `ctx.computeResourceIfAbsent(BATCH_SPAN_KEY, …)` on the **first** `handle()` call. Detection that we are inside a streaming-processor batch is `ctx.getResource(Segment.RESOURCE_KEY).isPresent()` — set by `WorkPackage.processBatch` at `WorkPackage.java:379` and the only writer of that key in AF5. The batch span is bound to the batch UoW via `ProcessingContextSpanBinding` (closes on `whenComplete`), so it correctly encloses all event-handler invocations PLUS the UoW's `runOnPrepareCommit` (token-store write) and `runOnAfterCommit` (segment-status update) — matching the AF4 batch-span coverage of `unitOfWork.executeWithResult(...)`. Per-event spans, opened by the same decorator after the lazy batch span is in place, become children. This works through `ResourceOverridingProcessingContext` because non-overridden keys (including `Segment.RESOURCE_KEY` and `BATCH_SPAN_KEY`) transparently fall through to the parent batch ctx — verified in `ResourceOverridingProcessingContext.java:185-228`. The `streaming` boolean from AF4's `EventProcessorSpanFactory.createBatchSpan(boolean streaming, …)` is replaced by the resource lookup; no boolean parameter survives. Three rejected alternatives — (A) `TracingEventProcessor` decorator on `EventProcessor` (impossible: the AF5 `EventProcessor` interface only exposes `start`/`stop`/`shutdown`, not batch processing), (B) upstream `BatchInterceptor` API on `PooledStreamingEventProcessorConfiguration` (cleaner architecturally but requires an upstream AxonFramework 5 PR and release — violates the plan's "no upstream changes" constraint), (D) `UnitOfWorkFactory` decoration (too broad — same factory serves non-batch callers), (F) drop batch span entirely (visible AF4 regression) — are documented with code snippets, pros/cons, and the verified AF4-coverage parity table in [`research-batch-tracing.md`](./research-batch-tracing.md). Worked sequence diagram added to [`flows.md`](./flows.md) as Flow 4. Implicit contracts that future framework maintainers must preserve: (1) any new `StreamingEventProcessor` impl MUST set `Segment.RESOURCE_KEY` on the batch UoW for the tracing decorator to recognize it as a batch; (2) `ResourceOverridingProcessingContext`'s transparent fall-through semantics for non-overridden keys is load-bearing.
- Q: The spec planned `TracingSnapshotter implements Snapshotter` via `DecoratorDefinition.forType(Snapshotter.class)`, but does AF5 actually have a `Snapshotter` component to decorate? → A: **No — and snapshot tracing is re-grounded on the real AF5 components.** Verification of AF5 main source shows there is **no `Snapshotter` component** — `Snapshotter` (with `scheduleSnapshot`) lives only in `stash/todo`, not ported. AF5's real snapshot architecture: (a) `SnapshotStore` (`@Internal`, `eventsourcing/.../snapshot/store/SnapshotStore.java`) — `store(QualifiedName, identifier, Snapshot)` / `load(QualifiedName, identifier)`, a **registered** component (resolved via `config.getOptionalComponent(SnapshotStore.class)` in `EventSourcingConfigurationDefaults` and `SimpleEventSourcedEntityModule`); (b) `SnapshottingEntityLifecycleHandler` (`@Internal`, generic `<I,E>`) — triggers snapshot creation **inline during sourcing**, gated by `SnapshotPolicy`, by calling a **private** `storeSnapshot(...)` → `snapshotStore.store(...)` inside its `source(...)` method (`SnapshottingEntityLifecycleHandler.java:182/190-193`). There is no standalone schedulable snapshot operation like AF4's `Snapshotter.scheduleSnapshot(type, id)`. **Resolution (option B3)**: snapshot tracing is delivered by a single `TracingSnapshotStore implements SnapshotStore` decorator registered via `DecoratorDefinition.forType(SnapshotStore.class)`, producing two spans — `SnapshotStore.store <entityType>` and `SnapshotStore.load <entityType>` — via `createInternalSpan(String)` + `Span.addAttribute("axoniq.entity.type", qualifiedName.name())` / `"axoniq.aggregate.identifier"` / `"axoniq.snapshot.version"` from the method parameters (no `Message` at this boundary — `store` receives a `Snapshot` record, not the `SnapshotEventMessage`). These spans **nest naturally** under the FR-009 entity-load/sourcing span (produced by decorating `EntityLifecycleHandler.source(...)`) via the active `ProcessingContext` — **no** separate outer "snapshot" decoration is added on the lifecycle handler (its only snapshot-relevant public method is `source(...)`, which is the load concern, not a snapshot-specific operation; wrapping it as a "snapshot outer span" would double-count the load). This is **not** strict AF4 trace-shape parity: AF4 produced a standalone `Snapshotter.createSnapshot` trace (executor-task model); AF5 nests the store under sourcing because that is literally how AF5 creates snapshots (inline, policy-gated). **Accepted risks / consequences**: (1) `SnapshotStore` is `@Internal` — the tracing module couples to an interface AF5 may change in a minor/patch release; this coupling is explicitly accepted as the only viable decoration point, with no modification of AxonFramework internals. (2) The AF4 two-level `scheduleSnapshot`→`createSnapshot` nesting does not survive; the AF5 nesting is `EntityLifecycleHandler.source`→`SnapshotStore.store`. (3) The `separateTrace` / `aggregateTypeInSpanName` AF4 toggles are dropped (no `Snapshotter` to host them); if needed later they become `TracingProperties.snapshotStore.*` additions. This supersedes all prior `TracingSnapshotter` / `forType(Snapshotter.class)` references in this spec, `research.md`, `af4-span-inventory.md` §1.8, `flows.md` Flow 3, and `plan.md` slice 6 — those now refer to `TracingSnapshotStore` / `forType(SnapshotStore.class)`. A future deviation (richer snapshot-creation span if AF5 ports a public `Snapshotter`, or `SnapshotEventMessage`-aware attributes) is a pure addition, not in scope.
- Q: Is the two-module tracing structure (`axoniq-tracing-core` + `axoniq-tracing-opentelemetry`) the right boundary, given a future consumer may want tracing for `axon-messaging` alone (without `axon-modelling`/`axon-eventsourcing`), and external modules (`axoniq-dead-letter`, or a separate `extension-workflows` repo) may want to add their own spans? → A: **No — replace with a five-module structure that mirrors AF5's own module layering.** Verified against AF5 source: AF5 ships `axon-messaging`, `axon-modelling`, `axon-eventsourcing` as **separate artifacts**, and the decorated components are partitioned across them (`CommandBus`/`EventSink`/`QueryBus`/`QueryUpdateEmitter`/`EventHandlingComponent` → `axon-messaging`; `Repository`/`StateManager` → `axon-modelling`; `SnapshotStore`/`EntityLifecycleHandler` → `axon-eventsourcing`). The new structure under `tracing/`: **(1) `axoniq-tracing-api`** — the public SPI (`SpanFactory`, `Span`, `SpanScope`, `SpanAttributesProvider`, `NoOpSpanFactory`, `MultiSpanFactory`, `LoggingSpanFactory`, the six built-in attribute providers) **plus public decorator-authoring helpers** (`ProcessingContextSpanBinding`, the span-name conventions, and the W3C metadata-propagation getter/setter SPI — this **realizes the previously-deferred DFI-001**). Depends only on `axon-messaging` (validated: every SPI type — `Message`, `ProcessingContext`, `ResourceKey` via `Context`, `QualifiedName`, `MessageType`, `LegacyResources`, `Map<String,String>` metadata — lives in `axon-messaging`, none in `axon-common`; this also matches where AF4 and AF5 themselves placed the tracing SPI). **(2) `axoniq-tracing-messaging`** — `TracingCommandBus`, `TracingEventSink`, `TracingQueryBus`, `TracingQueryUpdateEmitter`, `TracingEventHandlingComponent`, `TracingHandlerEnhancerDefinition` (`@CommandHandler`/`@EventHandler`/`@QueryHandler`) + `MessagingTracingConfigurationEnhancer` + ServiceLoader entry. Depends on api + `axon-messaging`. **(3) `axoniq-tracing-modelling`** — `TracingRepository`, `TracingStateManager` + `ModellingTracingConfigurationEnhancer` + ServiceLoader entry. Depends on api + `axon-modelling`. **(4) `axoniq-tracing-eventsourcing`** — `TracingSnapshotStore`, the `EntityLifecycleHandler.source` sourcing-span decorator, the `@EventSourcingHandler` enhancer extension + `EventSourcingTracingConfigurationEnhancer` + ServiceLoader entry. Depends on api + `axon-eventsourcing`. **(5) `axoniq-tracing-opentelemetry`** — `OpenTelemetrySpanFactory`, `OpenTelemetrySpan`, `MetadataContextSetter`/`Getter`. Depends on api + `io.opentelemetry:opentelemetry-api`. **Consequence — the single `TracingConfigurationEnhancer` becomes three per-module enhancers** (`MessagingTracingConfigurationEnhancer`, `ModellingTracingConfigurationEnhancer`, `EventSourcingTracingConfigurationEnhancer`), each `@Internal`, each discovered via its module's own `META-INF/services/org.axonframework.common.configuration.ConfigurationEnhancer` entry (the same ServiceLoader mechanism `axoniq-dead-letter` and `axoniq-distributed-messaging` already use). This is still consistent with Story 4 / FR-016 — that goal was "one public `SpanFactory`, no per-component public span-factory *interfaces*," which holds; "single enhancer" was a means, not the end. **External extensibility**: any module — `axoniq-dead-letter` for its `SequencedDeadLetterQueue`, or a separate `extension-workflows` repo — adds tracing by depending on `axoniq-tracing-api`, writing its own `Tracing*` decorators + a `ConfigurationEnhancer`, and dropping a ServiceLoader entry; nothing in the central modules changes. (License note: `axoniq-tracing-api` carries the AxonIQ commercial license like the rest of AxoniqFramework, so external consumers of the SPI are under AxonIQ ToS.) Supersedes the two-module structure in FR-017/FR-018; updates FR-013/FR-016 (single → per-module enhancers) and FR-019 (autoconfig conditionally wires whichever tracing modules are on the classpath). DFI-001 is no longer "deferred" — the public helpers ship in `axoniq-tracing-api`. **Rejected alternative — single `axoniq-tracing` module with `<optional>true</optional>` on `axon-modelling`/`axon-eventsourcing`, decorators wired only when those types are present:** considered and rejected. Maven `optional=true` correctly prevents transitive pull (a messaging-only consumer wouldn't drag in modelling/eventsourcing) — that half works. But it's rejected because (1) **the AF5 `ComponentRegistry` API is entirely `Class<?>`-typed** (`registerDecorator(Class,…)`, `hasComponent(Class)`, `registerIfNotPresent(Class,…)`, `getOptionalComponent(Class)`); a single enhancer that references `Repository.class`/`SnapshotStore.class` triggers `NoClassDefFoundError` at enhancer-discovery time when `axon-modelling`/`axon-eventsourcing` are absent at runtime — the JVM resolves the `ldc` class constant when the method links. There is **no `ifClassPresent`-style helper** in AF5 (verified: the only class-presence idiom in AF5 is hand-rolled `Class.forName(...)`, e.g. `ClasspathResolver`). So "don't decorate components we don't have" would require hand-rolled `ClassUtils.loadClass("…Repository")` string guards **plus** isolating each `registerDecorator(Repository.class,…)` call in a separate class loaded only after the guard passes (to stop the verifier eagerly resolving the type) — exactly AF4's `ifClassPresent(...)` dance, with zero API support. (2) `hasComponent(...)`/`getOptionalComponent(...)` answer "is a component *registered*," not "is the type *on the classpath*" — the wrong signal for optionality. (3) The single jar ships unused modelling/eventsourcing decorator bytecode to messaging-only users, and because `optional=true` doesn't pull those artifacts, a user who *wants* modelling tracing gets **silent under-coverage** (the decorator never wires, nothing signals the gap). The layered split is the **same messaging/modelling/eventsourcing partition expressed cleanly** — the compile dependency *is* the class-presence guard (no reflection, no `NoClassDefFoundError` risk) and ServiceLoader discovery *is* the conditional wiring (jar present ⇒ enhancer runs; absent ⇒ never discovered). The optional-single-module would only win if concerns were many/churning or publishing artifacts were costly; here it's a fixed 3 concerns mirroring stable AF5 artifacts, and AxoniqFramework already ships many small modules, so the marginal cost is low.

### User Story 1 - Out-of-the-box tracing with OpenTelemetry in a Spring Boot application (Priority: P1)

A developer building an event-driven application on AxoniqFramework with Spring Boot wants to observe how commands, events, and queries flow through their system. They add a single dependency, configure an OpenTelemetry exporter, start the application, and immediately see correlated spans for command dispatch, event publication and handling, query handling, snapshot creation, and aggregate / entity loading — including cross-service propagation when messages cross process boundaries.

**Why this priority**: This is the canonical "happy path" that almost all framework users want. Tracing only provides value when it appears automatically across the full messaging lifecycle without requiring developers to instrument each handler. Without P1, the feature has no business case.

**Independent Test**: Build an example application (`examples/university-java-springboot4` or a dedicated tracing example) that depends on the tracing OpenTelemetry module, exports spans to an in-memory exporter or a local collector (e.g., Jaeger/Zipkin via Testcontainers), exercises a representative command → event → query flow, and asserts that the resulting trace contains a connected hierarchy of spans with the expected names, attributes (message id, message name, payload type, aggregate identifier where applicable), and parent-child relationships including across an asynchronous event-handler boundary.

**Acceptance Scenarios**:

1. **Given** a Spring Boot 4 application that includes the AxoniqFramework tracing OpenTelemetry starter and an OpenTelemetry SDK on the classpath, **When** the application context starts, **Then** the framework auto-registers tracing decorators around the command bus, event bus, query bus, query update emitter, event-handling components, snapshotter, and repository / state manager components without the developer writing any tracing code.
2. **Given** a tracing-enabled application, **When** a command is dispatched that produces events that are consumed by an asynchronous event processor which in turn issues a query, **Then** the exported trace contains one root span for the command dispatch with child spans for command handling, event publication, event handling (correctly linked to the publishing span as a parent or producer-consumer link), and query handling — and each span carries attributes that identify the message.
3. **Given** a tracing-enabled application that sends a command to a remote node via the AxonServer connector (or another transport), **When** the remote node handles the command, **Then** the remote handler span is parented to the dispatcher span via trace context propagation through message metadata, producing a single connected trace across processes.
4. **Given** an application without an OpenTelemetry SDK on the classpath, **When** the tracing core module is on the classpath, **Then** the framework uses a no-op tracer by default and behaves identically to an untraced application (no exceptions, no measurable overhead beyond the no-op call sites).

### User Story 4 - Consolidation of per-bus / per-component span factories (Priority: P2)

A framework maintainer wants the new tracing module to avoid the proliferation of bus/component-specific span factory interfaces seen in AF4 / dead-coded in AF5 (`CommandBusSpanFactory`, `EventBusSpanFactory`, `QueryBusSpanFactory`, `EventProcessorSpanFactory`, `QueryUpdateEmitterSpanFactory`, `SnapshotterSpanFactory`, `SagaManagerSpanFactory`, `RepositorySpanFactory`). **Why this priority**: This is a structural goal of the migration. Not user-visible behavior, but it shapes the design and binds the implementation.

### Edge Cases

- **OpenTelemetry SDK absent**: The tracing core must default to a no-op factory; the application must function without an SDK on the classpath. No `ClassNotFoundException` may surface at runtime.
- **Multiple `SpanFactory` beans**: When a user supplies their own `SpanFactory`, it must replace the default. Behavior with multiple user-supplied factories is documented (composition via `MultiSpanFactory` or "last wins" — to be decided during planning).
- **Exception in handler**: When a handler throws, the surrounding span must be marked with error status and the exception recorded; the exception must still propagate to the caller unchanged.
- **Async event handling**: When an event is published synchronously but handled by an asynchronous event processor on another thread, the handling span must be linked to the publishing span (either as a parent via context propagation through metadata, or as a producer-consumer link — to be decided during planning based on OpenTelemetry semantic conventions for messaging).
- **Reactive code paths**: AxoniqFramework supports both imperative and reactive styles. Tracing must not assume a `ThreadLocal`-based active span (which would break in reactive pipelines); the implementation must use AF5's `ProcessingContext` to carry span scope through async boundaries.
- **Cross-process propagation**: When a message is sent through the AxonServer connector (or any other transport) to a remote node, the trace context must be serialised into message metadata on the sending side and rehydrated on the receiving side, producing a single connected trace.
- **Snapshotting on a background thread**: Snapshot creation runs outside the original processing context; its spans must still be attributable to a parent (the originating command or a standalone scheduled root) per documented conventions.
- **DCB / entity-based operation (no legacy aggregate identifier)**: When the surrounding operation is on a DCB / entity-based event stream (no `LegacyResources.AGGREGATE_IDENTIFIER_KEY` populated on the `ProcessingContext`), the `axoniq.aggregate.identifier` span attribute is intentionally **absent**. Tracing produces the message-id / message-name / payload-type attributes as usual; no exception, no warning. Trace consumers MUST not assume the attribute is always present.
- **Streaming-batch detection contract** (implicit): The batch span is opened only when `ctx.getResource(Segment.RESOURCE_KEY).isPresent()` on the per-event `ProcessingContext` (this works because `ResourceOverridingProcessingContext` falls through to its delegate for non-overridden keys — see `ResourceOverridingProcessingContext.java:185-228`). Today only `PooledStreamingEventProcessor` (via `WorkPackage.processBatch`) writes this key. Any future `StreamingEventProcessor` implementation that wants a batch root trace MUST set `Segment.RESOURCE_KEY` on the batch UoW. Custom `EventProcessor` implementations and `SubscribingEventProcessor` correctly produce no batch span — per-event spans inherit the surrounding publishing trace instead, matching AF4 behavior.
- **Disabled tracing at runtime**: A user must be able to disable tracing completely (either by not including the module, by using the no-op factory explicitly, or by a configuration flag), and the application must run with no tracing overhead.
- **Metadata-based context propagation collisions**: Trace context is written into message metadata under specific keys; these keys must not collide with user-defined metadata keys, and behavior on collision must be defined.

## Requirements *(mandatory)*

### Functional Requirements

#### Core abstractions

- **FR-001**: The framework MUST expose a single public `SpanFactory` abstraction in the new tracing module that supports creating internal, dispatch (producer), and handler (consumer) spans for any `Message` type — no bus-specific or component-specific span factory interfaces are exposed as public API.
- **FR-002**: The framework MUST expose a public `Span` abstraction with operations to start, end, mark as errored (recording an exception), set attributes, and run a `Runnable` / `Callable` inside the span's active scope, supporting both imperative and reactive execution.
- **FR-003**: The framework MUST expose a public `SpanAttributesProvider` SPI so that users can contribute additional attributes to any span created for a message.
- **FR-003a**: Because the AF5 `SpanFactory` takes an **eager** `String` operation name (not AF4's lazy `Supplier<String>` — see `af4-span-inventory.md` §0 rows 7 / 7a / 9), `TracingHandlerEnhancerDefinition` MUST NOT build its span name eagerly on every handler invocation. It MUST decide whether a span will be opened — enabled, and the handler type not suppressed (e.g. `@EventSourcingHandler` is suppressed when `axon.tracing.showEventSourcingHandlers=false`, the default) — **before** computing the (reflective, expensive) span name, and build the name only on the span-creating branch. Rationale: `@EventSourcingHandler` fires once per event during entity replay (a hot path); eagerly building `"ContainingClass.method(ArgType, …)"` for a span that will be discarded is a measurable regression. The eager `String` `SpanFactory` API is acceptable specifically because this single expensive-name caller guards its own name construction; the cheap-name decorators (commands, events, queries, repository, snapshot store) are unaffected and are not even installed when tracing is disabled.
- **FR-003b** *(added 2026-05-27)*: AF5 provides **no** config-aware registration API for `HandlerEnhancerDefinition` (no equivalent of AF4 `Configurer.registerHandlerEnhancerDefinition(Function<Configuration, HandlerEnhancerDefinition>)`). Enhancers are applied only through a `HandlerDefinition` (`MultiHandlerDefinition` bundles a `HandlerEnhancerDefinition`), which annotated handling components resolve via `c.getOptionalComponent(HandlerDefinition.class).orElse(ClasspathHandlerDefinition.forClass(...))`; the default enhancer source (`ClasspathHandlerEnhancerDefinition`) is ServiceLoader-only (no-arg), so it cannot carry the configured `SpanFactory`. Therefore `TracingHandlerEnhancerDefinition` MUST be auto-wired by **registering a `HandlerDefinition` framework component** that bundles a `SpanFactory`-bearing `TracingHandlerEnhancerDefinition` on top of the AF5 defaults (composing with, not replacing, the standard handler definitions and classpath enhancers). This is a single global slot shared by command/query/event handling; the enhancer self-gates per `Message` type so each handler kind is traced only once its slice enables it. This wiring is delivered in **slice 2** (the `@EventHandler` slice; plan.md P4.3a + appendix), and on landing it retroactively activates the per-method span for `@CommandHandler` (slice 1) as well as `@EventHandler` (slice 2). See clarification 2026-05-27.
- **FR-004**: The framework MUST ship built-in `SpanAttributesProvider` implementations covering at least: message identifier, message name (qualified name), message type, payload type, selected metadata entries, and aggregate identifier (where applicable). The aggregate-identifier provider MUST source its value from `ProcessingContext.getResource(LegacyResources.AGGREGATE_IDENTIFIER_KEY)` and MUST NOT reference `DomainEventMessage` (forbidden by constitution v2.1.0 — `DomainEventMessage` is removed from AxonFramework 5). On DCB / entity-based operations where no legacy aggregate identifier is available, the provider contributes no attribute. The `SpanAttributesProvider` SPI signature is `Map<String, String> provideForMessage(Message<?> message, @Nullable ProcessingContext context)` — providers that don't need the context ignore it.
- **FR-005**: The framework MUST default to a no-op `SpanFactory` when no other `SpanFactory` is configured, so that the tracing core module is safe to depend on even without an OpenTelemetry SDK.

#### Coverage of messaging components

- **FR-006**: The framework MUST trace command dispatch and command handling, producing one span on dispatch and a child span on handling (across process boundaries when applicable).
- **FR-007**: The framework MUST trace event publication and event handling, supporting both synchronous and asynchronous (streaming / pooled) event handling components. Cross-thread / cross-process links MUST follow OpenTelemetry messaging semantic conventions.
- **FR-007a**: The framework MUST trace event-handler invocations for **both** `PooledStreamingEventProcessor` and `SubscribingEventProcessor` through a **single** `TracingEventHandlingComponent` decorator, registered via `DecoratorDefinition.forType(EventHandlingComponent.class)` with a `cfg.getOptionalComponent(EventProcessorConfiguration.class).isPresent()` scope guard (the common configuration base of both processor types, so future `EventProcessor` impls that adopt the same configuration base inherit tracing automatically). Per-event spans (`EventProcessor.process <eventName>`, kind `CONSUMER`) MUST be produced for both processor types. The batch root span (`StreamingEventProcessor.batch`, kind `INTERNAL`) MUST be produced **only** for streaming-processor batches — detected via `ctx.getResource(Segment.RESOURCE_KEY).isPresent()`, which is written exclusively by `WorkPackage.processBatch` in `PooledStreamingEventProcessor`. **`SubscribingEventProcessor` MUST NOT produce a batch root span — this is intentional AF4 parity**, matching AF4's `DefaultEventProcessorSpanFactory.createBatchSpan(boolean streaming, …)` which returned `NoOpSpan.INSTANCE` when `!streaming`, and matching the AF4 reference guide (`tracing.adoc:193-195`) which documents subscribing processors as producing only per-event spans parented to the publisher's trace because the handler runs synchronously inside the publisher's unit of work; adding a separate batch span around a synchronous in-publisher invocation would be a redundant wrapper duplicating the publisher's `EventBus.commitEvents` span and would regress Story 4's "the consolidation does not regress the observable trace shape" criterion. When `SubscribingEventProcessor.process(events, context)` reuses the caller's `ProcessingContext` (`SubscribingEventProcessor.java:145-146`), per-event spans become children of the publisher's trace; when it creates a fresh UoW (line 148), per-event spans start a new trace. For streaming-processor batches, the batch span MUST enclose all event-handler invocations plus the UoW's prepare-commit (token-store write) and after-commit (segment-status update) phases — i.e., span coverage equivalent to AF4's `createBatchSpan(...).runCallable(() -> unitOfWork.executeWithResult(...))`. Implementation: `TracingEventHandlingComponent` lazy-opens the batch span on the shared `ProcessingContext` via `computeResourceIfAbsent(BATCH_SPAN_KEY, …)` on the first per-event `handle()` call; the span binds to the UoW lifecycle (closes on `whenComplete`). Per-event spans opened by the same decorator after the lazy batch span become children naturally. AF4's `disableBatchTrace` / `distributedInSameTrace` configuration toggles MUST be preserved as `axon.tracing.eventProcessor.disableBatchTrace` and `axon.tracing.eventProcessor.distributedInSameTrace` (with `distributedInSameTraceTimeLimit`, default `PT2M`) on `TracingProperties`, with the same semantics as AF4's `DefaultEventProcessorSpanFactory`. See [`research-batch-tracing.md`](./research-batch-tracing.md) for the full coverage matrix and rejected alternatives.
- **FR-008**: The framework MUST trace query dispatch, query handling, and query update emission (subscription queries).
- **FR-009**: The framework MUST trace aggregate / entity loading and saving through the `Repository` / `StateManager` mechanism.
- **FR-010**: The framework MUST trace event sourcing operations: replaying events for an entity (the `EntityLifecycleHandler.source(...)` sourcing span, shared with FR-009), snapshot writing, and snapshot reading. Snapshot tracing MUST be delivered by a `TracingSnapshotStore implements SnapshotStore` decorator registered via `DecoratorDefinition.forType(SnapshotStore.class)` — **not** via a `Snapshotter` decorator, because AF5 has no `Snapshotter` component (it lives only in `stash/todo`; snapshot creation in AF5 is an inline, `SnapshotPolicy`-gated side-effect of `SnapshottingEntityLifecycleHandler.source(...)`). See clarification 2026-05-26 (option B3) for the full rationale and accepted risks.

#### Design constraints

- **FR-013**: The framework MUST wire tracing into the framework components via **per-module `ConfigurationEnhancer`s** (one per tracing module — `MessagingTracingConfigurationEnhancer`, `ModellingTracingConfigurationEnhancer`, `EventSourcingTracingConfigurationEnhancer` — each implementing AF5's `ConfigurationEnhancer`, each `@Internal`, each discovered via its module's `META-INF/services/org.axonframework.common.configuration.ConfigurationEnhancer` entry) that register `DecoratorDefinition`s for the component types owned by that module's corresponding `axon-*` artifact. (Superseding the earlier "single `TracingConfigurationEnhancer`" wording — see clarification 2026-05-26 on the five-module structure. The consolidation goal is unchanged: one public `SpanFactory`, no per-component public span-factory interfaces.) Each `DecoratorDefinition` MUST produce a **delegating wrapper** following the AF5 decoration pattern: the wrapper class implements the target component interface (e.g., `CommandBus`, `EventBus`, `QueryBus`, `Repository`, `Snapshotter`) by composition, holds a `delegate` field of that same interface plus a `SpanFactory`, calls through to the delegate, and declares itself a wrapper via `ComponentDescriptor.describeWrapperOf(delegate)`. The AF4 anti-pattern of directly implementing a target interface without delegation (as `DistributedCommandBus` did) is explicitly disallowed because it prevents stacking with interception, metrics, distribution, security, and other concerns. No alternative wiring mechanism is used (no annotation processors, no per-bus configurer methods, no static wrapper subclasses).
- **FR-013a**: Where the wrapped operation already participates in a `ProcessingContext` — e.g., dispatch / handle methods that receive a `ProcessingContext` parameter — span open/close lifecycle SHOULD ride on `ProcessingContext` lifecycle callbacks (start / commit / rollback hooks) rather than `try/finally` or `Span.runSupplier(...)` blocks, so span scope aligns with the framework's processing phases and survives async / reactive boundaries naturally. Where no `ProcessingContext` is available at the relevant hook point (e.g., synchronous snapshot creation triggered outside a processing context), a direct `Span.run...` style is acceptable.
- **FR-014**: The framework MUST carry the active span / scope through AF5's `ProcessingContext` (using `ResourceKey<T>`) rather than `ThreadLocal`, so the implementation works correctly in reactive and asynchronous code paths.
- **FR-015**: The framework MUST propagate trace context across message boundaries by serialising it into message metadata on dispatch and rehydrating it on the receiving side, so distributed traces span multiple JVMs / processes. The serialisation/rehydration logic lives inside the per-component `DecoratorDefinition`s (not as a separate public propagator SPI in this feature; see DFI-001 under Story 4 for a future graduation path).
- **FR-016**: The framework MUST NOT introduce any public per-bus or per-component span factory interfaces such as `CommandBusSpanFactory`, `EventBusSpanFactory`, `QueryBusSpanFactory`, `EventProcessorSpanFactory`, `QueryUpdateEmitterSpanFactory`, `SnapshotterSpanFactory`, `SagaManagerSpanFactory`, or `RepositorySpanFactory`. (The forbid-list is defensive; `DeadlineManagerSpanFactory` is also implicitly forbidden because deadlines are out of scope — see clarification 2026-05-26.) All per-component span-creation logic (span names, span kinds, attributes, distributed-vs-in-process branching, propagation) MUST live inside **private** (package-private or `@Internal`-annotated) `DecoratorDefinition` implementations registered by the per-module enhancers (FR-013). Per-component span shapes (names, kinds, attribute keys) MUST remain equivalent to those produced by AF4 today, so that existing trace consumers/dashboards continue to work after the migration. The exhaustive AF4 → AF5 span mapping (9 `SpanFactory` families × 44 factory methods, cross-checked against every production caller in `AxonFramework4` and against the AF4 reference guide's "Traced components" section) is recorded in [`af4-span-inventory.md`](./af4-span-inventory.md); the implementation of each `Tracing*` decorator MUST consult that inventory and a defensive integration test (`AF4SpanShapeParityIntegrationTest`) SHOULD assert span name + kind for every row in §2 of the inventory.

### Key Entities

- **`SpanFactory`**: The single public abstraction for creating spans. Receives the message being processed (or descriptors of a non-message operation such as snapshot creation), the span kind (internal / dispatch / handler), and produces a `Span`.
- **`Span`**: A unit of traced work, with lifecycle (start, end, error) and the ability to host a runnable / callable inside its active scope.
- **`SpanScope`**: The "active span" lifetime, scoped to a `ProcessingContext` resource rather than a `ThreadLocal`.
- **`SpanAttributesProvider`**: Pluggable SPI that contributes attributes to a span based on the message being traced. Single method: `Map<String, String> provideForMessage(Message<?> message, @Nullable ProcessingContext context)`. The context is `@Nullable` because some span-creation points (e.g., an out-of-band snapshot trigger) have no `ProcessingContext` available. **There is no `provideForSubject(Object)` method** — non-Message spans (snapshot, repository load/save) have their attributes attached by the decorator directly via `Span#addAttribute(key, value)` from local method parameters, or picked up through `ProcessingContext` resources by the standard providers. See clarification 2026-05-26.
- **Tracing `ConfigurationEnhancer`**: AF5-style enhancer that registers `DecoratorDefinition`s wrapping the relevant messaging components with tracing behavior.
- **`OpenTelemetrySpanFactory`**: The OpenTelemetry implementation of `SpanFactory`, located in the OpenTelemetry integration module.
- **Trace context carriers**: Text-map getter / setter implementations that read trace context from / write it to message metadata using OpenTelemetry's propagation API.
- **`TracingProperties`**: Spring Boot `@ConfigurationProperties` controlling enable / disable per component group.
