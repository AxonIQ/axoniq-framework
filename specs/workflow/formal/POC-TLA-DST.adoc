= POC: TLA+ Design Verification + Deterministic Simulation Testing
:toc: left
:toclevels: 3
:icons: font
:source-highlighter: rouge

Single source of *architectural decisions* and *findings* for the POC that hardens
the axon-flow-spec engine's **task-leasing** and **crash-recovery** protocol with two
complementary techniques driven by ONE shared invariant set:

. **TLA+** — model-checks the _design_ of leasing + crash-recovery (small scope, exhaustive).
. **Deterministic Simulation Testing (DST)** — runs the _real engine_ in a seeded,
  single-threaded simulator under injected faults to verify the _implementation_.

Branch: `poc/tla_dst` (git worktree based on `feature/workflow-versioning`). +
Scope guard: the TLA+ model covers leasing + crash-recovery ONLY; the determinism work
adds injectable seams ONLY (no production behaviour change).

== Outcome (bottom line)

All six phases complete (plus a Phase 7 chaos-hardening pass); the existing test suite stayed green at
every step (runtime 410, examples/simple 46, new simulation module growing as DST-only invariants were
added) and **no production engine behaviour changed** — the only production-tree edits are injectable seams
(Phase 3) and a one-line `pom.xml` module registration (Phase 4). A separate **chaos campaign** (Phase 7)

`.tla` spec, and the DST assertions. This is the bridge that keeps the formal model and

== Phase 0 — Reconnaissance (DONE)

Full detail: `formal/ARCHITECTURE.md` (13 cited sections). Headlines:

* **Leasing.** Ownership is whole-engine, not per-instance: one Axon `pooledStreaming`
  processor with a *single segment* over all events
  (`WorkflowEventProcessingRegistrationEnhancer.java:102-157`). The "lease" is Axon
  pooled-streaming segment-token claiming — **but the processor `TokenStore` is a hardcoded
  `new InMemoryTokenStore()`** (`AllEventEventHandlingComponent.java:70`), so the lease is
  per-process and non-durable. Per-instance routing within the owning process is by
  `workflowId` (`WorkflowEngine.java:104`).
* **Crash-recovery.** A separate durable **`SafePointStore`** (engine token = lower bound
  of all active executions' restart tokens, ADR-004) drives recovery: on startup
  `resetTokens(safePoint)` (`...Enhancer.java:219-236`) rewinds, events replay through
  `EventSourcedWorkflowState.evolve`, then `switchToLiveMode` re-runs each body with
  recorded steps returning cached results so side effects aren't re-emitted
  (`WorkflowEngine.java:152-180`, `ExecuteDelegate.java:117`).
* **Replay determinism** is the engine's core assumption: the workflow body must be
  deterministic between primitives; only `execute` action lambdas may have side effects.
* **Retries.** `RetryPolicy.maxRetries(n)` = `n+1` total attempts; per-attempt timeout
  default 5s; backoff strategies in `RetryableExecuteDelegate`.

Design holes confirmed at the design level (complementing the code-level findings):

* **F-0 / `EffectAtMostOnce`** — p1 runs step-1's effect and records `STARTED`, *crashes
  before committing `COMPLETED`*, recovers; the volatile "already-applied" flag is gone, the
  step is still `STARTED`, so the effect runs **again** (`effect[1]=2`). Fix: bind the effect
  to the commit (transactional outbox / optimistic append-condition). `APPEND_CONDITION=TRUE` ⇒ `No error`.
* **F-1 / `AtMostOneOwner`** — with a non-durable claim store, p2 claims the segment while p1
  still holds it ⇒ split-brain. Fix: durable single-writer lease. `DURABLE_LEASE=TRUE` ⇒
  `No error`. Consequence: `AtMostOnceRecording` then also breaks (two owners commit the same
  terminal record); the append-condition closes that independently of the lease.

These TLA+ results are the source of the seeded regression scenarios bridged in Phase 5.

==== Phase 1' — Determinism-seam closure (post-campaign hardening, this increment)
Closes the two D5 residuals plus the two §8/§11 hash-order sources, as the first step of the
whole-system-determinism roadmap (full-virtual-time / deterministic-scheduler work). Seams only; the
default (`SystemWorkflowScheduler`) path is behaviour-preserving:

* **`WorkflowScheduler.withTimeout`** (new default method built on `delayedExecutor`) replaces the raw
  `CompletableFuture.orTimeout` in `ExecuteDelegate` — the last JDK-Delayer real-time timer. Under
  `ManualWorkflowScheduler` the per-attempt timeout now fires on virtual-time advance (pinned by
  `ManualWorkflowSchedulerWithTimeoutTest`); under `SystemWorkflowScheduler` it is `orTimeout`-equivalent
  (the armed timeout is not self-cancelled on early completion — it fires as a no-op; bounded retention,
  documented on the method).
* **`ProcessingContextUtils` honors the caller-supplied UoW id** (the workflowId / a seeded
  `WorkflowIdGenerator` id) instead of `UUID.randomUUID()` — resolves the existing FIXME; the engine
  already uses non-unique UoW ids elsewhere (`create(stepName, …)` in `ExecuteDelegate`).
* **`EventWaitConditions` multi-match dispatch is registration-ordered** (sequence number + sorted
  snapshot; map concurrency unchanged) — closes the §8 hash-order dispatch source (pinned by
  `EventWaitConditionsTest.multiMatchDispatchesInRegistrationOrder`).
* **`InMemoryWorkflowExecutionRepository.findAll()` returns a workflowId-ordered `LinkedHashSet`** —
  every consumer (`switchToLiveMode`, shutdown) iterates deterministically; `lowerBound` consumers are
  order-independent and unaffected.

The aligned-clock mode stays opt-in: default-mode scenarios still depend on the D5 era gap (documented
in `workflow/axoniq-workflow-simulation/README.md`); flipping that default is a separate, considered change.

**Consequence — F-20 re-pin.** Virtualizing the per-attempt timeout changes the F-20 expression in
`LoopAndStormTest.reusedNamesLoop_…` from "duplicates 2..25, timing-dependent" to **bimodal**: 0 (the
virtual sleep timer never fires before the spinning body exhausts its bound — the F-19 no-op-sleep face)
or ≥2 (the re-entry still races the timedOut evolve on real thread scheduling — the original F-20
duplicate-terminal face, load-dependent). Both modes ARE the gap; a fixed engine (F-19 blocking sleep +
F-20 durable-gated publish) yields exactly 1. The test is re-pinned to `isNotEqualTo(1)` with the full
history in a comment — green across both gap modes, flips exactly when the fixes land. The residual 0-vs-≥2
nondeterminism is real thread scheduling: precisely the dimension the Phase-2 deterministic scheduler makes
seeded and explorable, where the strict F-20 acceptance probe then lives.

==== Phase 2' — Deterministic single-carrier scheduler (spike, DONE; measured, not assumed)
`DeterministicVirtualThreadExecutor` (test module, `fakes`): every task the engine routes to
`WORKFLOW_ENGINE_EXECUTOR` runs on a virtual thread whose continuations execute on ONE carrier thread, in an
order the executor controls — FIFO (deterministic serialization) or seeded-random pick (reproducible
*interleaving fuzz*). Mounted via the JDK's `ThreadBuilders$VirtualThreadBuilder(Executor)` test constructor
(`--add-opens java.base/java.lang=ALL-UNNAMED`, wired in the simulation surefire config only). Opt-in through
`SimulationConfig.withDeterministicCarrier(interleavingSeed)` → `DstSimulation` wires it as the body-executor
override; default path untouched.

Measured (pinned by `DeterministicSchedulerSpikeTest` / `F20InterleavingProbeTest`):

* Single-instance world, same seed ×5 under FIFO carrier: **1 distinct GLOBAL fingerprint** — whole-log
  bit-for-bit, beyond the per-instance contract.
* Full smoke fuzz loop (16 instances, faults), same seed ×3 under the carrier: per-instance fingerprints
  identical (the harness contract holds under single-carrier execution; also identical to the production
  executor's content), GLOBAL fingerprints 3/3 distinct, avg run 727 ms vs 646 ms baseline (~12% slower, no
  regression class). **The residual global nondeterminism is Axon's pooled-streaming processor delivery
  threads** — enqueue timing from outside the carrier. That is the measured boundary: the next increment is
  scheduling the processor side (PSEP coordinator/work-package executors are Axon components) onto the same
  carrier, which is what would turn the global fingerprint deterministic and unlock full time compression.
* F-20 interleaving probe: 8 seeded schedules over the reused-names live-lock all yield 0 duplicates —
  body-side interleaving alone cannot reopen the F-20 window; it needs processor-side timing. The probe stays
  as the exploration substrate with the gap-alphabet pin (0 or ≥2, never the fixed-engine 1).
  *Superseded for acceptance:* the hunting campaign found that carrier + BUGGIFY *simultaneously* reopens the
  window on every schedule (44–50 duplicates per run; ≥2 in 80/80 observations across 5 JVM runs) — the strict
  F-20 acceptance lived in `F20BuggifyInterleavingProbeTest` until 2026-09-07 (removed, see the F-20 status note), no longer
  parked on the processor-side increment.

Design honesty: JDK-21 monitor pinning (`synchronized` + block) would stall the single carrier — none observed
across the suite (the engine's task queues are `ReentrantLock`-based); a stall would surface as the harness
deadline abort, never a hang.

=== The one issue found — a HARNESS bug, not an engine bug (triaged class (b))

* **What broke:** `Invariants.assertCommittedHistorySurvivesCrash` (INV-3), called by `WorkerCrashFault`
  / `RestartFault` after a recovery, compared the two committed logs by **absolute global index**.
  Message shape: `committed event at index 7 changed across recovery:
  before=order-wf0:reserveInventory:STARTED after=order-wf4:reserveInventory:STARTED`.
* **Why it is a harness bug:** the fuzz drives 5 concurrent `OrderWorkflow` instances. The
  cross-instance interleaving of the *single* global log is the F-2 surface the harness deliberately
  factors out **everywhere else** (`assertDeterministicReplay`, the intra-run prefix check, the
  fingerprint all group by `workflowId`). Two *independent* instances swapping their global position
  across a crash+replay is not a durability break; each instance's own committed subsequence was
  intact. **Timing-dependent, not seed-determined** — re-running the same seeds standalone passed; only
  under repeated passes did seeds `74` and `104` trip, confirming it is scheduling-derived global order,
  not engine non-determinism.
* **Fix (harness-only, no production change):** `assertCommittedHistorySurvivesCrash` now compares
  **per-`workflowId` subsequences** (each instance's pre-crash committed history must be a prefix of
  its post-recovery history), matching INV-3's real meaning and the harness's documented per-instance
  contract. Secondary hardening: a fault that asserts an invariant in-line now routes its
  `InvariantViolation` through the same `enrich(...)` path as every other check, so a fault-raised
  break also prints the seed + reproduce command + fault trace + committed log (previously it
  propagated bare). Validated: 120 seeds × 5 passes = 600 runs with **0** failures, then the clean
  500- and 1000-seed campaigns above.
* **Regression locked:** `RegressionSeedsTest` (12 tests) — a fixed full-fuzz seed-set incl. the two
  triggering seeds `74`/`104` asserted green, plus two deterministic pins on the assertion itself: a
  cross-instance interleave must be tolerated, and a genuine per-instance loss must still throw.

=== A second same-class harness artifact, surfaced by the invariant-expansion campaign (class (b))

While extending the invariant set (INV-14 `CombinatorConsistency`, INV-15 `EventCorrelationExact`), a
500-seed fuzz tripped `CommittedHistorySurvivesCrash` (INV-3) on the new `CombinatorWorkflow` instance
at seed `370`: `committed event for 'comb-c0' at index 3 changed across recovery:
before=comb-c0:branchB:STARTED after=comb-c0:branchB:COMPLETED`.

* **Why it is a harness bug (not an engine/durability defect):** both events were present, exactly once,
  and the instance completed correctly — every *other* invariant held. It is the **same class** as the
  Phase-6 finding (a timing-dependent global-append-order artifact), now manifesting *intra-instance*:
  the `ControllableEventStorageEngine` kept **two parallel ordered lists** — a workflow-only
  `committedLog` (read by the INV-3 before-crash snapshot and every assertion) and `committedTagged`
  (the source `recoveredFrom` rebuilds the recovered store from). The two `.add()`s were not atomic, so
  under the combinator workflow's **rapid back-to-back commits** the two lists could capture one
  instance's `STARTED`/`COMPLETED` in *different* relative order; INV-3 then compared a `committedLog`
  ordered *before* against an *after* rebuilt from `committedTagged` and saw a spurious "reorder."
  **Timing-dependent, not seed-determined** — re-running seeds `0..400` standalone passed with `0` trips
  (`DST fuzz: 400 seeds passed all invariants`), exactly the Phase-6 signature. This refines **F-2**: the
  per-instance *global-append* order of events committed close together is part of the non-deterministic
  surface, not just the cross-instance interleaving.
* **Fix (harness-only, no production change):** collapse to a **single source of truth** —
  `committedWorkflowLog()` is now *derived* from the one `committedTagged` list (filtered to workflow
  events), and the parallel `committedLog` field is removed. The before-crash snapshot and the recovery
  rebuild now read the *same* ordered source, so they can never diverge — INV-3's per-`workflowId`
  comparison is unchanged and not weakened (a genuine lost/duplicated event is still caught; the existing
  `…_stillDetectsPerInstanceLoss` pin still passes).
* **A second manifestation, same root cause (INV-7 `TerminalIsFinal`, seeds `252` then `18`):** after the
  single-source fix, a further 500-seed fuzz tripped `TerminalIsFinal` on tightly-committing instances —
  seed `252` on `CorrelatedWaitWorkflow` (`recordMatch:COMPLETED` appended *after* `<workflow>:COMPLETED`:
  `… recordMatch:STARTED [81], <workflow>:COMPLETED [87], recordMatch:COMPLETED [89]`), and later seed `18`
  on the pre-existing `MigratingOrderWorkflow` (a late `processV2:STARTED` appended after the terminal
  status, its `COMPLETED` already committed before it). Same class: the engine publishes events
  durably-async, so a step committed close to the workflow-completion commit can have its own commit —
  *either* its terminal record (252) *or* its STARTED (18) — land just after it run-to-run (the F-2
  append-order non-determinism, intra-instance). The engine's terminal guards forbid *starting* new work
  after terminal, so a step that began before terminal cannot be new work; its late-appended event is an
  ordering artifact, not a finality break. **Fix (harness-only):** `assertTerminalIsFinal` now flags only
  genuine new work after the terminal status — a workflow-status event, or a step event whose step has *no*
  pre-terminal event (a step appearing wholly after terminal) — and tolerates *any* late-appended event
  (STARTED or terminal record) of a step that began before terminal (a *duplicate* terminal record is still
  caught by INV-2). And, to keep the same intra-instance append-order non-determinism from causing a
  *cross-run* flake, `assertDeterministicReplay` (INV-4) and the seed-reproducibility fingerprint now compare
  each instance's committed events as a **multiset** (content, with multiplicity) rather than by global-append
  order; the intra-run prefix-stability check keeps append order (sound — within one run the log only grows,
  never reorders).
* **Regression locked:** seeds `370` (INV-3), `252` and `18` (INV-7) added to `RegressionSeedsTest`'s fixed
  full-fuzz set, plus the existing `…_stillDetectsPerInstanceLoss` pin and two new `Inv7TerminalIsFinalTest`
  pins (a late COMPLETED and a late STARTED of a step that began before terminal are tolerated; a step
  appearing *wholly* after terminal, and a second workflow-status event, still throw). The structural fixes
  are the real guard (the trips were timing-dependent, so the seeds are coverage, not deterministic
  reproductions). Validated by clean re-runs after the fixes (1000-seed fuzz green).

This refines **F-2** decisively: the single global log's append order is non-deterministic *both* across
instances *and*, for events one instance commits close together, within the instance — because the engine
publishes durably-async. The DST harness therefore asserts per-instance **content** (multisets) and
*logical* finality (no new work after terminal), never the raw global-append order. No engine behaviour is
at fault — all of this is the harness reading more order into the log than the async-publish engine
guarantees.

| Finding | In plain terms | Verdict

| **F-0** `EffectAtMostOnce`
| A step's side effect (e.g. charging a card) can run **twice** if the process crashes right after doing it but before its `COMPLETED` event is recorded.
| 🔴 **Bug** — effects are at-least-once, not at-most-once. Confirmed by TLA+ **and** DST. Modeled fix exists (transactional outbox / optimistic append-condition); not yet applied.

| **F-1** `AtMostOneOwner`
| Two nodes can both believe they own the same workflow (**split-brain**) — the ownership claim is in-memory, not durable/shared.
| 🔴 **Bug** for multi-node (a single node is fine). Confirmed by TLA+ **and** DST. Modeled fix exists (durable single-writer lease).

| **F-2** `DeterministicReplay` residual (incl. the live-switch boundary)
| The *global* order of events across **different** workflows isn't fixed run-to-run, and a live-switch boundary race was suspected in recon — but each individual workflow replays identically.
| 🟢 **Works as expected** — determinism holds **per `workflowId`** (cross-instance global ordering is non-deterministic *by design*); the suspected race did **not** reproduce across 1000+ fuzz seeds. Its only effect was an over-strict harness assertion, since fixed.

| **F-3** terminated-id re-spawn
| A redelivered *start* event for an **already-finished** workflow id starts a **brand-new** instance instead of ignoring it (dedup checks only *live* instances, not the durable history).
| 🟠 **Bug / design question** — idempotency gap. Found by DST; engine left unchanged, documented + pinned by a test. Decide: dedup against the durable log, or accept restart as intended.

| **F-4** terminal COMPLETED hook dropped — **FIXED**
| The COMPLETED lifecycle hook (`@WorkflowStatusChangedHandler` / a registered status-change listener) could be **silently skipped** on the happy completion path — the body returned and cleared its task queue before the COMPLETED event's listener callback ran. STARTED and the `ctx.fail`/`ctx.cancel`/timeout terminal hooks fired reliably (those paths wait for the status before returning); COMPLETED did not.
| 🟢 **Fixed** — a *lost* lifecycle-hook fire (opposite of F-0's duplication). Found by DST (INV-17); the no-re-fire / at-most-once guarantee the invariant targeted always **held** (no hook ever re-fired on replay). **Fix (engine):** the happy completion path now `awaitStateChange`s on the terminal status before `finishWorkflow` clears the queue, symmetric with the other terminal paths, so the COMPLETED hook fires reliably exactly once. Verified: DST `Inv17StatusHookFiresOncePerStatusTest` flipped from "COMPLETED in {0,1}, may be dropped" to **COMPLETED == 1** (new `assertCompletedHookFiredExactlyOnce`); baseline + simulation green. Design-level TLA+ corroboration: `HookOnCompletion.tla` — `MC_hook.cfg` violates `StatusHookFiresOncePerStatus` with the exact clear-before-notify happy-path counterexample (the old behaviour); `MC_hook_fixed.cfg` (the await-terminal-state toggle) passes with `No error`.

| **F-5** nested primitive not guarded (candidate)
| A workflow that breaks the §3.1 rule — calling a primitive *inside* another primitive's action lambda — gets **no clear error**. Depending only on the body executor's threading, it either **silently works** (default virtual-thread executor: the inner step gets its own thread) or **silently hangs forever** (single-threaded executor: the inner task can never be consumed, the per-instance queue deadlocks). The engine never says "you can't do that" up front.
| 🟠 **Bug (candidate)** — a *robustness* gap (no self-protecting guard), not a corruption bug: the committed history is never torn/corrupted in either case (the `EngineSelfProtection` no-corruption property **holds**). Found by DST (INV-23), both halves characterized end-to-end. A common authoring mistake caught only by liveness / a watchdog deadline, never by a guard. Engine left unchanged, documented + pinned by a test. Candidate fix: a re-entrancy guard on `appendTask` that throws a clear exception when a task is appended from inside a task being consumed on the same instance.

| **F-6** unexpected runtime exception wedges the instance (candidate; generalized by S-4)
| Any **unexpected `RuntimeException` from a user lambda between primitives gets stuck forever** — the engine logs it but does *not* turn it into a terminal status, so the instance never finishes (and a crash + recover does not rescue it). The clearest trigger (S-4) is a `modifyPayload` modifier that does `throw new RuntimeException(...)`; the original trigger was the narrower `null`-payload-value-under-`combine` case (a `Map.copyOf` NPE at completion). Both reach the **same** `handleWorkflowException` `default`-branch sink. `ctx.fail`/`ctx.cancel`/timeout/drift are handled; *only* an arbitrary runtime exception wedges.
| 🟠 **Bug (candidate)** — a *robustness / liveness* gap at the `handleWorkflowException` `default` branch, **partly by design** (the `:313` "we agreed not to drive the workflow to terminal state on any other exception" comment), not a corruption bug. Found by DST (INV-19 reducer-edge work, generalized by S-4); the committed history isn't corrupted (only a well-formed `<workflow>:STARTED`), but the workflow is wedged non-terminally with the exception only logged. Engine left unchanged, documented + pinned by tests (the null-value case and the general `RuntimeException` case). Candidate fix: drive the instance to FAILED on an unexpected runtime exception in the `default` branch (closing the whole trigger family); plus, for the null case, make the payload read null-tolerant.

| **F-7** `modifyPayload` re-records a duplicate terminal step — **FIXED**
| _Was:_ if the process crashes after a `modifyPayload` step's `COMPLETED` is recorded but before the workflow itself finishes, the post-crash re-run recorded the **same step's `COMPLETED` a second time** — two terminal records for one step. `modifyPayload` was the *only* state-publishing primitive missing the "step already present → skip re-publish" gate, and it published its event *directly* (bypassing the terminal-publish guard the others go through). _Now:_ `modifyPayload` gates its publish on `!containsStep(stepName)` like every other primitive, so the post-crash re-run **skips** the re-publish — the terminal-record count stays 1 and INV-2 holds. The same window built on an ordinary `execute` step never duplicated and still does not.
| ✅ **FIXED** — was a genuine duplicate terminal *record* (an INV-2 `AtMostOnceRecording` violation), distinct from F-0 (which duplicates an *effect*, never the record). DST-reachable on a **single node**, deterministic (seed 0). Found by DST settling the S-1 candidate. **Fix:** `PayloadDelegate.modifyPayload` now gates both the drift guard AND its `appendTask` publish on the single `!containsStep(stepName)` check (`PayloadDelegate.java:83`) — the replay-skip gate every other state-publishing primitive has. Design-level TLA+ corroboration: `PayloadRepublish.tla` — `MC_payload.cfg` violates `AtMostOnceRecording` with the exact crash-then-re-publish counterexample (the gated execute-style contrast step stays at 1), `MC_payload_fixed.cfg` (`CONTAINS_STEP_GATE=TRUE`) passes with `No error`. DST `F7DuplicatePayloadRecordTest` flipped to assert the count stays 1 / INV-2 holds across the crash/recover.

| **F-8** blocking-convenience timeout mis-classified (candidate, minor)
| When a step **times out** on a blocking convenience call, *which* exception you get depends on the overload. `awaitExecute(...)` (typed and untyped) and the **untyped** `awaitEvent(stepName, EventCondition)` throw a `StepFailedException` whose **cause is `null`** — so the caller cannot tell a timeout from a real failure. Only the **typed** `awaitEvent(stepName, Class, ...)` throws the clean `StepTimedOutException`. The timeout-surfacing fix was applied to that one overload only; the others fall through to the generic "throw the step's error" path, and a timed-out step's error is `null`.
| 🟠 **Bug (candidate), minor** — a *wrong exception classification* / API-consistency inconsistency, **not** corruption: the `TIMED_OUT` step *record* is written correctly on every path (INV-9's recording facet **holds**); only the surfaced exception type differs. DST-reachable on a **single node**, deterministic (seed 0): all three `StepFailedException(null)` paths and the correct typed-`awaitEvent` path observed. Found by DST settling the S-2 candidate; engine left unchanged, documented + pinned by a characterizing test (and as the sharpened surfacing facet of INV-9). Candidate fix: special-case `result.timeout()` → `StepTimedOutException` in `resolveStepPayload` / the `awaitExecute` helpers, symmetric with the typed `awaitEvent` fix.

| **F-9** `BackoffStrategy.exponential` overflows at large attempt counts — **FIXED**
| _Was:_ a step with a **large `maxRetries`** (e.g. `maxRetries(70)`) and `BackoffStrategy.exponential(base, …)` that kept failing **got stuck forever** once the backoff computation overflowed. The delay is `base × 2^(attempt-1)`, capped *after* the multiply; for a seconds/minutes-scale base the multiply overflowed `Duration`'s capacity around attempt ~60 and threw `ArithmeticException`, which — computed on the workflow thread — wedged the instance non-terminally (the same "logged but never finished" sink as F-6/S-4). (For a small base, instead of throwing, attempt 64 produced a *negative* delay the cap didn't clamp, and attempt 65+ wrapped to a tiny garbage delay via the JVM's `mod 64` shift masking.) _Now:_ `exponential` clamps to `max` **before** any overflowing/negative/wrapped shift or multiply, so `delay(attempt)` returns the capped `max` for every large attempt and never throws — the always-failing step retries on the clamped schedule to exhaustion and goes terminal `FAILED` instead of wedging.
| ✅ **FIXED** — was a *liveness* wedge at the backoff arithmetic, **extreme-config / LOW real-world likelihood** (needs a minute-scale base with a very large `maxRetries`). The *record* bound (INV-8 `RetryBound`) always **held** — the overflow stopped recording early, never recorded MORE than the policy allows; the gap was liveness. DST-reachable on a **single node**, deterministic (seed 0). Found by DST settling the S-3 candidate. **Fix:** `BackoffStrategy.exponential` (`BackoffStrategy.java:72-81`) clamps the shift exponent (`1L << min(max(attempt-1,0),62)`) and returns `max` whenever `factor > max/base` (or `base ≤ 0`), so the `multipliedBy` can never overflow, go negative, or wrap — preserving `min(base·2^(attempt-1), max)` for the in-range attempts. No TLA+ model (INV-8/INV-21 are DST-only — the leasing/crash-recovery spec models no retries/backoff/time, see `formal/tla/README.md` "Scope & limits"). DST `S3BackoffExponentialOverflowTest` flipped from "wedges non-terminally / overflow throws" to: the unit arithmetic now clamps to `max` (no throw / no negative / no wrap across attempts 1..200) and the `BackoffOverflowScenario` instance retries to exhaustion, the step records terminal `FAILED`, the workflow reaches a terminal status, and INV-8's bound is exact (`maxRetries` `RETRYING` + 1 `STARTED` = `maxRetries + 1` attempt records).

| **F-10** `anyMatch` no-match-all-completed winner reads `results[0]` (candidate, minor)
| For `anyMatch(predicate, a, b, c)` where **all** branches completed but **none** matches the predicate, the categorized `matched()` (empty) / `unmatched()` (all three) lists are **correct** — but the *winner-derived* accessors aren't: `success()` returns `true` and `result()`/`resultAs()` return **branch `a`'s** payload (the first completed branch, `fallback.orElse(results[0])`). An author who reads `anyMatch(...).result()` on this path silently reads branch `a`'s data as if it were "the" result, even though nothing matched.
| 🟠 **Bug (candidate), minor** — a *winner-result-semantics* contract gap, **not** corruption and **not** a decision inconsistency: the `matched()`/`unmatched()` categorization (the documented way to read a combinator result) is sound, so INV-14's decision facet **holds**. It only bites if the winner accessors (`success()`/`result()`/`resultAs()`) are read instead. DST-reachable on a **single node**, deterministic (seed 0). Found by DST settling the S-5 candidate (extends INV-14); engine left unchanged, documented + pinned. Candidate fix: make the winner empty / the result accessors `Optional.empty()` (and `success()==false`) explicitly on the no-match path.

| **F-11** non-terminal instance pins the engine safe point (candidate)
| **One stuck (parked / long-running / abandoned) workflow instance freezes the engine's recovery anchor forever.** The engine safe point is the *minimum* restart token over **every** live instance (`determineEngineSafePoint` = `lowerBound` over `findAll()`), and an instance is removed from that set **only** when it reaches a terminal status. So a single instance parked in a never-arriving `waitForEvent` (a legitimate long-running wait, an abandoned instance, or a wedge that *parks*) sits at its early token forever and pins the safe point there — even as **every other** instance completes and is evicted. On each crash/restart the processor resets to that pinned early token and **replays the whole log from there**, and the parked instance is retained in memory indefinitely; both grow without bound while it lives.
| 🟠 **Bug (candidate)** — a *liveness / unbounded-retention* gap (replay cost + memory grow without bound while a stuck instance lives), **not** a correctness bug: INV-3 (`CommittedHistorySurvivesCrash`) still **holds** — recovery replays *more* than necessary, never less (ADR-004). | **F-34a** a resume event arriving before a restored body re-registers its wait is dropped — **FIXED**

| **F-38** a graceful engine shutdown was recorded as a durable workflow FAILED — **FIXED**
| **The shutdown interrupt reached workflow bodies as a step failure.** `WorkflowEngine.shutdown()` promises an interrupt, not a cancellation: no terminal event, the step resumes on the next start. But `stopForShutdown()` interrupts the driver parked in `awaitStateChange`, `StateBasedWorkflowStepResult.await()` turns that into `StepInterruptedException`, and `StepInterruptedException extends StepFailedException`. Any body that catches `StepFailedException` and calls `ctx.fail(e)` (the harness bodies did; user code will) therefore published `<workflow>:FAILED` during shutdown. The publish raced the coordinator's shutting-down scheduler (`RejectedExecutionException`), which `isRejected` did not classify as a lost writer, so FAILED landed 0, 1 or 2 times per instance, and `finishWorkflow` ran on a non-terminal instance (the F-17 path), releasing a parked instance's recovery anchor.
| ✅ **FIXED on `poc/tla_dst`** — `SimpleWorkflowExecution.stopForShutdown()` sets `shuttingDown`; `transitionToTerminalState` publishes nothing while it is set; `isLostWriter` extends the fence branch of `handleWorkflowException` to `RejectedExecutionException`. Harness bodies rethrow `StepInterruptedException` ahead of their `StepFailedException` catch. | **F-40** a restored parked instance on a quiet segment is never started after a restart (candidate)
| **Catch-up is detected only from a delivered event.** After a restart the engine restores every non-terminal instance into the repository, but starts a segment's restored bodies only when that segment either claimed at the stream head (`WorkflowEngineCatchUpSupport.startsAfterClaim`) or receives a *delivered* event whose token covers the startup head (`recordDelivery`, reached from `WorkflowEngine.handle` only). Proper fix needs a delivery-independent per-segment caught-up signal (Axon computes it in `WorkPackage`'s tracker status; the engine's `SegmentChangeListener` seam has only claim and release). Do not simply drop the claim gate: it is what keeps a restored body from racing the replay of its own events.

replay-stable** (F-22, confirmed three ways — reading, DST, TLA+); the **decision** (verdict / `anyMatch` winner /
`allMatch` violator) **is** replay-stable, because it derives from the durable first-completed order
(`firstCompletedAmong` over event-sourced timestamps). Pins (`CombinatorReplayScenario` + `CombinatorReplayTest`,
all deterministic, seed 0): the allMatch late-completion divergence (the F-22 expected gap); the `anyMatch` winner
stability with BOTH branches cached on the recovered run (healthy); the C-2 `noneMatch(failure)` foot-gun over a
TIMED_OUT branch, now pinned, with a replay-stable verdict. Design-level corroboration: `CombinatorReplay.tla` —
`MC_combinator.cfg` violates `CategoriesReplayStable` with the exact late-completion counterexample;
`MC_combinator_fixed.cfg` (record-at-decision toggle) passes. Code-reading notes beyond the documented C-1..C-5/F-10:
the three delegates are structurally symmetric (winner/violator + lazily-cached categories per result object); a
`noneMatch`/`allMatch` with a never-completing branch and no early violator blocks until ALL branches complete (a
guard parked on an eternal branch — composes with F-11's safe-point pin).

=== The most useful conclusion: four of six inherited defects, not new code

Established by diffing each defective construct between the pre-sharding base and the sharding branch. Only **F-29 and
F-30** are genuinely new code. **F-25, F-26, F-27 and F-28 are pre-existing single-segment code that was correct while
there was exactly one segment and became wrong the moment sharding introduced N** — one trigger, one live-mode flag, one
unscoped predicate, one segment-0 scan. The base is explicit about the assumption it was written under
(`initializeTokenSegments(moduleName, 1, firstToken, null); // FIXME #190 -> should be configurable?`).

So the review question for a change like this is not only "is the new code right" but **"was every place that assumed one
segment found and updated?"** On this evidence, four were missed.

=== Vehicles this campaign added

* **A multi-JVM rig** — `examples/multijvm-rig`, 16 `*IT` classes, real forked node JVMs, one shared Postgres
  `JdbcTokenStore`, one real Axon Server, split over two failsafe executions because the full suite no longer fits one
  invocation. Assertions read from the **claim rows and the step log**, never from node logs, so an idle-but-broken
  cluster cannot pass by silence. This is the **sole** vehicle for claim exclusivity, no-work-after-release, real
  `kill -9`, real per-node clocks and real partition. Plus `examples/shardlab`, a two-node startup/catch-up example.
* **Three TLA+ models** in `formal/tla/sharding/` — `SegmentClaim.tla` (claim / release / expiry / join / boot),
  `WfShard.tla` (instance ownership, spawn, wake, broadcast, replay boundary) and `Holdback.tla` (checkpoint holdback,
  handover, shutdown ordering). `SegmentClaim` and `WfShard` were built independently from the code by modellers
  deliberately isolated from each other; both reproduced the known defects and between them found three new ones and
  corrected two planned fixes.
* **`formal/tla/tools/tla2tools.jar`**, which was absent from this checkout — until it was fetched, no TLC command in
  these docs ran as written.

=== Precise negatives — documented so they are not re-hunted

* **Timers RESUME across a segment handover at their original deadline; they are not restarted and not dropped.** Both
  `waitForEvent` timeouts and retry backoff: a 60 000 ms timeout fired at 60 110 ms from arming on the node that *took*
  the segment, and retry backoff at 30 018 ms from the first attempt. Deadlines come from the durable step timestamp,
  not from arming time. This was the highest silent-failure risk on the production-shape list. `TimerAcrossHandoverIT`.
* **Duplicate start events are exactly-once**, on both the hash-routed and the broadcast path — 8 duplicate starts and
  8 duplicate resumes committed, effect once. `DuplicateStartEventsIT`.
* **Claim renewal is not event-driven.** Across a 120 s idle gap with nothing on the stream, maximum claim age was
  6 014 ms against a 10 s timeout and owners were unchanged; placement after idleness still routes by hash, not to the
  warm node. `IdleClusterSparseTrafficIT`.
* **BROADCAST fan-in is safe.** `SpawnExactlyOnce` and `WakeExactlyOnce` hold in `WfShard.tla` with **all four modelled
  defects enabled**, at 3 segments / 3 instances / **1,722,131 distinct states, depth 31**. Deleting the
  `shouldHandle`/`shouldSpawn` guards makes both fail within 8 steps, so the green is not vacuous. This closes off a
  whole line of enquiry: the duplication risk lives in the release/claim window, not in broadcast routing.
* **The durable wait survives a rebalance, including `kill -9`.** Five kill runs, three graceful runs over three rounds,
  one control, ~1000 instance-level observations, **zero losses**. The protection is **delivery-scoped, not
  wait-scoped**: `handle` calls `onEvent` before requesting the checkpoint, `onEvent` *enqueues* the match, and the
  match enqueues the durable completion behind it — so the token cannot pass an event until both its wake and its
  completion are durable. A parked instance needs no holdback because nothing is outstanding.
  `DurableWaitAcrossRebalanceIT`.
* **S-8 REFUTED** — the processor's *unnamed* `TokenStore` lookup and the enhancer's *named* `TokenStore["<module>"]`
  lookup **resolve to the same instance**; the processor module registers the application's store under the
  module-scoped name. Runtime evidence: F-25's reproduction threw from `JdbcTokenStore` via the *named* lookup while the
  processor's own claims appeared as owner rows in the same Postgres, in the same run. There is no silent in-memory
  fallback and no fix is needed. This was the item most likely to invalidate every multi-node result; it does not.

=== Framework findings — Axon Framework / Axoniq Framework 5.3.0

**Not this repo's code.** They are recorded as findings in their own right rather than absorbed into engine
workarounds, because a workaround that hides a framework defect leaves the next caller to rediscover it. **Vehicle:
upstream** — each is written up as a ready-to-file issue in `FRAMEWORK_ISSUES.md`; none is filed yet. Checkpointing is
new in Axoniq Framework 5.3.0 and unproven, so a defect that looks like engine misuse may be partly the framework's.

[cols="1,3a,1"]
|===
| ID | Finding | Confidence

| **FW-1**
| `Context#resources()` mixes plain data (tracking token, segment, correlation data) with **handles bound to the
  lifecycle of the unit of work that created them**, notably `EventStoreTransaction`, and nothing distinguishes them.
  Propagating resources between units of work is a normal pattern; doing so carries the transaction across and the next
  `appendEvent` registers on the original, already-committed context, failing far away with a message naming neither the
  resource nor the offending context. **This was the root cause of F-30.** The engine half is fixed, but the fix is a
  deny-list of exactly one type, so a second lifecycle-bound handle would break it silently — a stated dependency, not a
  hidden one.
| high — caused a real defect

| **FW-2**
| Claim callbacks omit the token; release callbacks carry it. `SegmentChangeListener.onSegmentClaimed(Segment)` and
  `Checkpointing.onSegmentClaimed(Segment, CheckpointTrigger)` carry no position, while
  `Checkpointing.onSegmentReleased(Segment, TrackingToken upTo)` does — although
  `Coordinator.createWorkPackage(Segment, TrackingToken)` and `CheckpointingProgressStrategy` both hold it. A handler
  restoring state on claim must therefore choose between acting at head during replay (a safety bug) and parking
  forever (a liveness bug). **No correct third option is available to a caller**, which is what blocks the cross-node
  half of **F-33**.
| high — blocks a correct implementation

| **FW-3**
| `initializeTokenSegments` raises different exception types per store: `JdbcTokenStore` raises
  `UnableToClaimTokenException`, `JpaTokenStore` leaks a raw Hibernate `ConstraintViolationException`. A catch narrowed
  to the Axon exception looks correct, passes on JDBC and fails on JPA — which is why the **F-25** fix deliberately does
  *not* narrow its catch.
| medium — observed at runtime

| **FW-4**
| A checkpoint request beyond the segment's `lastConsumedToken` is stored verbatim. `onCheckpointRequested` does not
  clamp, and `WorkPackage#storeIfAdvanced` checks monotonicity only — its own javadoc says the guard exists so a
  misbehaving component can never *rewind* progress; overshooting **forward** is not defended, not logged and not
  rejected. This turns a caller-side mistake into silent event loss rather than a loud error, and **is what gave F-26
  its blast radius**. Fixing the caller does not make the framework safe.
| high — read in source

=== What this campaign could not cover

* **The DST harness models no segments and no nodes.** `SimulationConfig` has no field for either, segment count cannot
  be configured from outside the engine, and `InMemoryTokenStore` has a no-op `releaseClaim` and no owner column, so two
  in-JVM nodes cannot contend. `Invariants.assertAtMostOneOwner` is still called with a literal `1`. Consequently
  **INV-24…INV-28 have no DST assertion** — they are carried by TLA+ plus unit tests plus the rig. Adding the segment
  dimension to the harness is the largest outstanding gap.
* **One JVM cannot fake multiple nodes**, and this was the campaign's own initial mistake: `ClockUtils.instant()` is a
  JVM-global static so skewing one node's clock skews all; the default token-store `nodeId` is `pid@host`, identical for
  in-JVM nodes, so every steal/expiry arm passes vacuously; and `context.close()` releases claims, so a "crash" that
  releases its claims is not a crash. The repo's existing `RealStoreSplitBrainIT` makes exactly this mistake — both
  "nodes" are Spring contexts in one JVM with their own databases, so they cannot contend for a claim even in principle.
* **The models do not cover** token positions and the `lowerBound` computation itself, real time (expiry is a fair
  action, not a clock), segment split/merge, more than one handover, DCB consistency markers, the real `Segment.matches`
  mask, or multiple instances per segment (except where `Holdback.tla` varies `InstPerSeg`).
* **Multi-JVM results are never reproducible by seed.** Every statement carrying the *confirmed on real infrastructure*
  label is a single observed run or a small repeat count, and a single non-reproducing failure is recorded as
  non-deterministic rather than dismissed.
