= Your First Workflow
:navtitle: First Workflow

A workflow definition is just imperative Java code.
You write the business logic; the engine records every step as a durable event.
If the application crashes, the engine replays those events and resumes exactly where it left off.

== Defining a workflow

Here's the simplest possible workflow — a single durable step:

[source,java]
.src/main/java/io/axoniq/example/order/OrderFulfillmentWorkflow.java
----
public class OrderFulfillmentWorkflow {

    @Workflow(idProperty = "orderId", startOnEvent = "OrderPlaced")
    public void execute(SimpleWorkflowContext ctx) {

        ctx.awaitExecute("reserveStock", Boolean.class,
                          InventoryService::reserveStock); // <1>
    }
}
----

<.> `awaitExecute` calls the action, waits for it to finish, and returns the typed result.
The engine records a STARTED and COMPLETED event for this step automatically.

That's it — one line of business logic, and the engine gives you event sourcing, crash recovery, and an audit trail.

Now let's make it more realistic by handling the result and passing payload:

[source,java]
.src/main/java/io/axoniq/example/order/OrderFulfillmentWorkflow.java
----
public class OrderFulfillmentWorkflow {

    Logger logger = LoggerFactory.getLogger(OrderFulfillmentWorkflow.class);

    @Workflow(idProperty = "orderId", startOnEvent = "OrderPlaced")
    public void execute(SimpleWorkflowContext ctx) {

        var customerId = ctx.workflowPayload().get("customerId");
        var amount = ctx.workflowPayload().get("amount");

        var reserved = ctx.awaitExecute("reserveStock",
                payload("customerId", customerId, "amount", amount).getValues(),
                Boolean.class,
                InventoryService::reserveStock); // <1>
        if (!reserved) {
            ctx.fail("Stock unavailable"); // <2>
            return;
        }

        logger.info("Stock reserved for order {}", ctx.workflowPayload().get("orderId"));
    }
}
----

<.> `awaitExecute` runs the action synchronously and returns the typed result.
The params (payload) passed to the step (`customerId`, `amount`) are recorded in the STARTED event.
<.> If stock reservation fails, we fail the workflow.
Standard Java control flow — `if`, loops, try/catch — all work exactly as you'd expect.

When this workflow executes successfully, the engine records the following events in the event store:

[source]
----
[0]: io.namespace.OrderPlaced: {orderId=123, customerId=456, email=joe@example.com, amount=99.95} // <1>
[1]: io.namespace.OrderFulfillmentWorkflow#ExecuteStarted (STARTED): {}              // <2>
[2]: io.namespace.ReserveStockStarted (STARTED): {customerId=456, amount=99.95}       // <3>
[3]: io.namespace.ReserveStockCompleted (COMPLETED): {__reserveStock=true}            // <4>
[4]: io.namespace.OrderFulfillmentWorkflow#ExecuteCompleted (COMPLETED): {}
----

<.> The triggering event — its `orderId` becomes the workflow instance ID (from `idProperty`).
<.> The engine starts tracking the workflow instance.
<.> The STARTED event captures the payload passed to the step — `customerId` and `amount` from the workflow payload.
<.> Once the action returns, a COMPLETED event captures the result. The `__reserveStock` key stores the typed return value (`true`).

Every primitive call becomes a pair of durable events.
This is what gives you audit trails, crash recovery, and replay — with zero extra code.

== The @Workflow annotation

The `@Workflow` annotation tells the engine how to wire up your workflow:

[horizontal]
`idProperty = "orderId"`:: Extracts the workflow instance ID from the triggering event's payload.
Each unique `orderId` gets its own workflow instance.
`startOnEvent = "OrderPlaced"`:: The qualified event name that triggers a new workflow instance.

[TIP]
====
You can also use `startOnConditions` to filter which events trigger the workflow.
For example, `startOnConditions = {"amount>100"}` would only process high-value orders.
====

== What happens under the hood

Each `awaitExecute` call produces two durable events: a STARTED event when the step begins, and a COMPLETED (or FAILED, TIMED_OUT) event when it finishes.

The engine records everything.
On crash recovery, it replays those events and resumes execution from where it left off — no manual state management needed.

[NOTE]
====
You write simple imperative code.
The engine translates each primitive call into durable events.
This gives you event sourcing, audit trails, and crash recovery for free.
====

== Adding more steps

Let's extend our workflow to initiate payment after reserving stock:

[source,java]
.src/main/java/io/axoniq/example/order/OrderFulfillmentWorkflow.java
----
@Workflow(idProperty = "orderId", startOnEvent = "OrderPlaced")
public void execute(SimpleWorkflowContext ctx) {

    var customerId = ctx.workflowPayload().get("customerId");
    var amount = ctx.workflowPayload().get("amount");

    var reserved = ctx.awaitExecute("reserveStock",
            payload("customerId", customerId, "amount", amount).getValues(),
            Boolean.class,
            InventoryService::reserveStock);
    if (!reserved) {
        ctx.fail("Stock unavailable");
        return;
    }

    ctx.awaitExecute("initiatePayment",                         // <1>
                     payload("customerId", customerId,
                             "amount", amount).getValues(),
                     PaymentService::initiatePayment,
                     Duration.ofSeconds(30),
                     baseName("InitiatingPaymentForCustomer"));  // <2>
}
----

<.> A second step that initiates payment processing, passing `customerId` and `amount` as input.
<.> `baseName(...)` replaces the step name in the event name — its events will appear as `InitiatingPaymentForCustomerStarted` instead of `InitiatePaymentStarted`.

Here's the event store after a successful run:

[source]
----
[0]: io.namespace.OrderPlaced: {orderId=123, customerId=456, email=joe@example.com, amount=99.95}
[1]: io.namespace.OrderFulfillmentWorkflow#ExecuteStarted (STARTED): {}
[2]: io.namespace.ReserveStockStarted (STARTED): {customerId=456, amount=99.95}
[3]: io.namespace.ReserveStockCompleted (COMPLETED): {__reserveStock=true}
[4]: io.namespace.InitiatingPaymentForCustomerStarted (STARTED): {customerId=456, amount=99.95} // <1>
[5]: io.namespace.InitiatingPaymentForCustomerCompleted (COMPLETED): {}
[6]: io.namespace.OrderFulfillmentWorkflow#ExecuteCompleted (COMPLETED): {}
----

<.> The `baseName("InitiatingPaymentForCustomer")` customizer changed the event name from the default `InitiatePayment` to `InitiatingPaymentForCustomer`.

== Kotlin DSL

If you prefer Kotlin, the same workflow looks like this:

[source,kotlin]
.src/main/kotlin/io/axoniq/example/order/OrderFulfillmentWorkflow.kt
----
class OrderFulfillmentWorkflow {

    @Workflow(idProperty = "orderId", startOnEvent = "OrderPlaced")
    fun Kontext.onExecute() {
        val customerId = payload["customerId"]
        val amount = payload["amount"]

        val reserved = awaitExecute(
            "reserveStock",
            { InventoryService.reserveStock() },
            local = mapOf("customerId" to customerId, "amount" to amount)
        )
        if (!reserved) {
            fail("Stock unavailable")
            return
        }

        awaitExecute(
            "initiatePayment",
            { PaymentService.initiatePayment() },
            local = mapOf("customerId" to customerId, "amount" to amount),
            timeout = 30.seconds,
            eventNameCustomizer = baseName("InitiatingPaymentForCustomer")
        )
    }
}
----

The Kotlin DSL uses extension functions on `Kontext`, giving you a clean, idiomatic API with named parameters and `kotlin.time.Duration` support (e.g., `30.seconds`).
