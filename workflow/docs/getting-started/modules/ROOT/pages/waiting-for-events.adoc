= Waiting for Events
:navtitle: Waiting for Events

Many business processes need to pause and wait for something external — a payment confirmation, an approval decision, a callback from a third-party system.
The `awaitEvent` method lets your workflow suspend until a matching event arrives.

[NOTE]
====
The events that `awaitEvent` listens for are standard Axon Framework events.
They can be published from anywhere — a command handler, an `EventGateway`, a REST controller, a webhook endpoint, or any other component that has access to the event bus.
For example, a payment provider callback could publish a `PaymentConfirmed` event directly via `eventGateway.publish(...)`, and that will unblock the waiting workflow.
====

== The awaitEvent method

After initiating payment, we need to wait for a `PaymentConfirmed` event before continuing:

[source,java]
----
var confirmation = ctx.awaitEvent("awaitPayment",
                                   PaymentConfirmed.class,   // <1>
                                   Duration.ofMinutes(15));   // <2>
----

<.> The event type to wait for.
The engine subscribes to the event bus and watches for events of this type.
<.> Maximum time to wait.
After 15 minutes, the step completes with `StepStatus.TIMED_OUT`.

When a matching event arrives, the workflow resumes and `awaitEvent` returns the deserialized event object.

Here's what the event store looks like when a `PaymentConfirmed` event arrives before the timeout:

[source]
----
[5]: io.namespace.AwaitPaymentStarted (STARTED): {startTime=2026-03-25T10:00:00Z}                  // <1>
[6]: io.namespace.PaymentConfirmed: {orderId=123, transactionId=txn-456}                           // <2>
[7]: io.namespace.AwaitPaymentCompleted (COMPLETED): {orderId=123, transactionId=txn-456}           // <3>
----
<.> The engine records when the wait began — `startTime` is used internally to calculate the remaining timeout on replay.
<.> The external `PaymentConfirmed` event arrives — this is what unblocks the waiting workflow.
<.> The engine records the COMPLETED event with the matched event's payload.

If no matching event arrives within 15 minutes:

[source]
----
[5]: io.namespace.AwaitPaymentStarted (STARTED): {startTime=2026-03-25T10:00:00Z}
[6]: io.namespace.AwaitPaymentTimedOut (TIMED_OUT): 2026-03-25T10:15:00Z                            // <1>
----
<.> The TIMED_OUT event records the timestamp when the timeout occurred.

== Filtering with associations

There's a problem with the code above.
Without filtering, _any_ `PaymentConfirmed` event would wake up _every_ waiting workflow.
That's clearly not what we want.

Associations let you correlate events to specific workflow instances:

[source,java]
----
var confirmation = ctx.awaitEvent("awaitPayment",
        PaymentConfirmed.class,
        associate(                                 // <1>
            payloadProperty("orderId"),            // <2>
            equalsTo(ctx.workflowPayload().get("orderId"))  // <3>
        ),
        Duration.ofMinutes(15));
----

<.> `associate(...)` combines a value extractor and a matcher into an event predicate.
<.> `payloadProperty("orderId")` extracts the `orderId` field from the incoming event's payload.
<.> `equalsTo(...)` creates an equality matcher.
Only `PaymentConfirmed` events whose `orderId` equals this workflow's `orderId` will match.

[NOTE]
====
Without associations, event matching is based solely on the event type.
For production workflows, you will almost always want to use associations to ensure events reach the correct workflow instance.
====

== Timeouts

When a `waitFor` step times out, it completes with `StepStatus.TIMED_OUT`.
You can use this to implement fallback logic:

[source,java]
----
var confirmation = ctx.awaitEvent("awaitPayment",
        PaymentConfirmed.class,
        associate(payloadProperty("orderId"),
                  equalsTo(ctx.workflowPayload().get("orderId"))),
        Duration.ofMinutes(15));
----

[TIP]
====
You can branch on the timeout outcome — cancel the order, retry payment, or escalate to manual review.
The right strategy depends on your business requirements.
====

== Waiting for multiple events

`awaitEvent` blocks until a single event arrives.
If you need to wait for multiple events concurrently, use the non-blocking `waitFor` and combine results with a combinator:

[source,java]
----
var payment = ctx.waitForEvent("awaitPayment",                  // <1>
        PaymentConfirmed.class, Duration.ofMinutes(15));

var approval = ctx.waitForEvent("awaitApproval",                // <1>
        ManagerApproved.class, Duration.ofMinutes(30));

ctx.allMatch(WorkflowStepResult::isCompleted, payment, approval)   // <2>
   .await();

logger.info("Both payment and approval received — proceeding!");
----
<.> `waitForEvent` returns a `WorkflowStepResult` immediately without blocking — both waits start concurrently.
<.> `allMatch` blocks until both events have arrived. See xref:step-orchestration.adoc[] for more on combinators.

== Sleep — a simple delay

Sometimes you just need to pause for a while.
The `sleep` method provides a durable delay:

[source,java]
----
ctx.sleep("cooldownPeriod", Duration.ofDays(10)); // <1>
----

<.> Pauses the workflow for 10 days.
Under the hood, this is a `waitFor` with an event condition that never matches — so it always times out after the specified duration.

[source]
----
[4]: io.namespace.CooldownPeriodStarted (STARTED): {startTime=2026-03-25T10:00:00Z}
[5]: io.namespace.CooldownPeriodTimedOut (TIMED_OUT): 2026-04-04T10:00:00Z            // <1>
----
<.> `sleep` always produces a STARTED followed by a TIMED_OUT — that's by design, since the "event" it waits for never arrives.

== Updated workflow

Here's our workflow with the payment step added.
Notice the order — we subscribe to the event *before* initiating payment, to avoid a race condition where the confirmation arrives before we're listening:

[source,java]
.src/main/java/io/axoniq/example/order/OrderFulfillmentWorkflow.java
----
@Workflow(idProperty = "orderId", startOnEvent = "OrderPlaced")
public void execute(SimpleWorkflowContext ctx) {

    var reserved = ctx.awaitExecute("reserveStock", Boolean.class,
                                     InventoryService::reserveStock);
    if (!reserved) {
        ctx.fail("Stock unavailable");
        return;
    }

    // First: subscribe to the payment confirmation event (non-blocking)
    var paymentConfirmation = ctx.waitForEvent("awaitPayment",  // <1>
            PaymentConfirmed.class,
            Duration.ofMinutes(15));

    // Then: initiate payment (non-blocking) — this triggers the external service
    var paymentInitiation = ctx.execute("initiatePayment",      // <2>
            ctx.workflowPayload(),
            PaymentService::initiatePayment,
            Duration.ofSeconds(30), defaults());

    // Wait for both to complete
    ctx.allMatch(WorkflowStepResult::isCompleted,                   // <3>
                 paymentConfirmation, paymentInitiation).await();

    logger.info("Payment initiated and confirmed for order {}",
                ctx.workflowPayload().get("orderId"));
}
----

<.> `waitForEvent` starts listening for `PaymentConfirmed` immediately and returns a `WorkflowStepResult` without blocking.
<.> `execute` calls the payment service — this may trigger a third-party provider that eventually publishes a `PaymentConfirmed` event.
<.> `allMatch` blocks until both the payment initiation completes and the confirmation event arrives.

[TIP]
====
By subscribing to the event *before* calling the service that produces it, you guarantee no events are missed — even if the external service responds instantly.
====

Here's the full event store for this workflow:

[source]
----
[0]: io.namespace.OrderPlaced: {orderId=123, customerId=456, email=joe@example.com, amount=99.95}
[1]: io.namespace.OrderFulfillmentWorkflow#ExecuteStarted (STARTED): {}
[2]: io.namespace.ReserveStockStarted (STARTED): {}
[3]: io.namespace.ReserveStockCompleted (COMPLETED): {__reserveStock=true}
[4]: io.namespace.AwaitPaymentStarted (STARTED): {startTime=2026-03-25T10:00:05Z}                  // <1>
[5]: io.namespace.InitiatePaymentStarted (STARTED): {orderId=123, customerId=456, email=joe@example.com, amount=99.95}
[6]: io.namespace.InitiatePaymentCompleted (COMPLETED): {}
[7]: io.namespace.PaymentConfirmed: {orderId=123, transactionId=txn-456}                           // <2>
[8]: io.namespace.AwaitPaymentCompleted (COMPLETED): {orderId=123, transactionId=txn-456}           // <3>
[9]: io.namespace.OrderFulfillmentWorkflow#ExecuteCompleted (COMPLETED): {}
----
<.> The event subscription starts *before* initiatePayment — no race condition.
<.> The external `PaymentConfirmed` event arrives after the payment service processes the request.
<.> The workflow records the matched event's payload and resumes.
