# Ideas to explore


Current DSL:

```java
  public static class UserSignupWorkflow implements TestDefinition {

    @Override
    public String association(@Nonnull Map<String, Object> trigger) {
      return "signup-" + trigger.get("id").toString();
    }

    @Override
    public void execute(TestWorkflowContext ctx) {

      logger.info("User signup workflow started at {} for {}", Instant.now(ctx.getClock()), ctx.getPayload());

      // -> start
      if (!ctx.execute("createUser", Boolean.class, UserService::createUser)) {
        return;
      }
      ctx.execute("activateUser", UserService::activateUser);
      ctx.execute("sendWelcomeEmail", NotificationService::sendEmail);
      ctx.wait("waitASecond", Duration.ofSeconds(1));
      var magic = ctx.waitForEvent("waitForMagicToHappen", MagicHappenedEvent.class);
      logger.info("Magic happened because of the magician {}", magic.magician);
      // -> end

      logger.info("User signup workflow ended at {} for {}", Instant.now(ctx.getClock()), ctx.getPayload());
    }
  }
```


1. Is it possible to use imperative workflow definition?
   - Does it influence the execution model or is that an independent question?

2. What is the mental model of the workflow runtime?
   - Definition repository is not part of the runtime - it might have additional persistence
   - Every workflow is started by event
   - The engine executes steps from the definition
   - The instance has its instance state, changes are stored as events
   - Every step has its lifecycle and the step state changes are stored as events
   - Instance contains executed steps with request/response data.
   - The step execution becomes idempotent once it is executed (returns result if the step is in the history)
   - There is nothing more than this - the stream of workflow lifecycle events and step lifecycle events can be used to event-source the state of the engine

3. Are two primitives `Execute` and `WaitFor` sufficient?
   - Execute:
     - Executes customer code
     - As a state transition from (STARTED) -> {COMPLETED, FAILED, TIMED_OUT, CANCELLED}
     - STARTED: state before the execution
     - COMPLETED: code executed and returned (a result)
     - FAILED: code executed but raised an exception (no result)
     - TIMED_OUT: code executed and interrupted by the engine on behalf of time (no result)
     - CANCELLED: code executed and interrupted by the engine on behalf of event (no result)
   - WaitFor:
     - Waits until an event is received
     - Always with a time constraint
     - As a state transition from (STARTED) -> {COMPLETED, TIMED_OUT, CANCELLED}
     - STARTED: state before the execution
     - COMPLETED: event received (a result)
     - TIMED_OUT: interrupted by the engine on behalf of time (no result)
     - CANCELLED: interrupted by the engine on behalf of event (no result)

4. How do we decide to switch from replay to execution phase?
   - Currently, there is no AF5 hook a listener for caught-up event

7. Is the runtime is driven by the event stream (event-handler) for any change?
   - No direct changes of the WorkflowState (workflowStatus, steps)
   - Restore is the same as execution

8. How the restore of the engine is working?
     - We have no idea which events are relevant (any business event might cause have caused a workflow to start)
     - How do we know what workflow instances are there after restart (replay from 0 would solve it) => not working for production
     - Can we just create a workflow-engine-snapshot containing the list of `workflow ids` of unfinished workflows + the event `global index`?
       - Disable event receive (this makes state read-only)
       - Make a snapshot
       - Continue to receive
     - Once we have a `workflowId` might source the state instead of streaming -> fast recovery, only relevant workflows.
     - Then replay from the `global index`
     - Question: how do we find all events? No types, no search based on metadata!
     - No tags:
       - Workflow id should be the 'entity identifier'
     - Tags:
       - Every event relevant to workflow will get the event tag "workflow" with `workflowId` as value.
     - Other ideas?

     - How to timeout if no events are received? Heartbeat?
